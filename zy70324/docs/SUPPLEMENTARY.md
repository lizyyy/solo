# 回调地址健康巡检API - 补充说明

## 一、主要边界说明

### 1.1 回调地址状态边界

回调地址存在三种状态，每种状态有明确的边界条件：

**状态转换图：**
```
active <--resume-- paused
  |                    ^
  |                    |
blocked --- (手动操作) --> active
```

**边界条件：**

| 状态 | 进入条件 | 退出条件 | 行为边界 |
|------|----------|----------|----------|
| `active` | 注册成功、恢复巡检 | 连续失败≥5次 → `blocked`；客户暂停 → `paused` | 正常执行定时巡检，记录历史，发送告警 |
| `paused` | 客户主动暂停 | 客户主动恢复 | 停止所有巡检任务，保留所有历史数据和失败计数 |
| `blocked` | 连续失败≥5次 | 运营手动解除封禁 | 停止所有巡检任务，保留封禁时间戳，需要人工干预 |

### 1.2 失败计数边界

失败计数是系统的核心指标，存在以下边界：

- **重置边界：** 连续失败次数在成功一次后立即重置为0
- **告警边界：** 连续失败次数≥2次时发送首次告警
- **升级边界：** 连续失败次数≥5次时自动封禁
- **冷启动边界：** 首次注册时失败计数为0
- **暂停恢复边界：** 暂停期间不增加失败计数，恢复后从原计数继续判断升级

### 1.3 通知发送边界

为防止告警风暴，通知系统有明确的发送边界：

- **冷却时间边界：** 同一类型通知在60分钟内只发送一次
- **证书提醒边界：** 证书剩余天数≤14天开始提醒，过期后立即发送紧急通知
- **慢响应边界：** 响应时间>1000ms标记为慢响应，记录但不频繁告警
- **网络抖动边界：** 单次失败不立即告警，连续失败≥2次才触发告警

### 1.4 巡检频率边界

- **最小值边界：** 最低巡检频率为1分钟
- **最大值边界：** 最高巡检频率为1440分钟（24小时）
- **默认值边界：** 未指定时使用15分钟
- **实时执行边界：** 手动执行`/run`接口不受频率限制

### 1.5 数据存储边界

- **查询限制边界：** 历史记录查询默认返回100条，最大可指定
- **时间范围边界：** 汇总查询默认使用最近60分钟的数据
- **客户隔离边界：** 所有数据按客户ID严格隔离，查询必须指定客户上下文

## 二、典型失败路径分析

### 2.1 路径概述

**场景：** 客户注册了一个回调地址，但服务器已停止服务，导致连续失败并最终被封禁。

**完整路径：**
```
注册成功 → 第1次失败（不告警）→ 第2次失败（首次告警）→ 
第3次失败（无新告警，冷却期）→ 第4次失败（无新告警）→ 
第5次失败（封禁告警 + 状态变更为blocked）
```

### 2.2 详细执行步骤

#### 步骤1：注册回调地址
**输入：**
```json
POST /callback-urls
{
  "customerId": "customer-001",
  "url": "https://down.example.com/callback",
  "frequencyMinutes": 1
}
```

**系统行为：**
1. 数据库层：创建回调地址记录，`consecutiveFailures = 0`，`status = 'active'`
2. 调度层：创建cron任务，每分钟执行一次
3. 内存状态：初始化通知冷却时间map

**关键检查点：**
- [x] 验证URL格式合法性
- [x] 检查同一客户下是否已存在相同URL（防重复）
- [x] 验证频率参数在[1, 1440]范围内
- [x] 验证客户ID确实存在

#### 步骤2：第1次巡检失败（T+1分钟）
**触发：** cron任务自动执行

**探测过程：**
1. 发起HTTP请求 → 连接超时（10秒后）
2. 捕获异常：`getaddrinfo ENOTFOUND down.example.com`
3. 记录巡检结果：
   - `status = 'failed'`
   - `errorMessage = 'getaddrinfo ENOTFOUND down.example.com'`
   - `responseTimeMs = 10000`
   - `certificateStatus = 'valid'`（非HTTPS或无法检查）

**规则处理：**
```
currentFailures = 0 + 1 = 1

检查告警边界：
  failures >= 2? → 1 >= 2? → NO → 不发送告警

检查封禁边界：
  failures >= 5? → 1 >= 5? → NO → 不封禁

更新回调地址：
  consecutiveFailures: 1
  lastFailureAt: 当前时间
```

**状态变更：**
- `consecutiveFailures`: 0 → 1
- 通知状态：无
- 地址状态：仍为`active`

**关键检查点：**
- [x] 网络抖动容忍：单次失败不告警，给系统恢复机会
- [x] 失败计数递增正确
- [x] 巡检历史记录完整

#### 步骤3：第2次巡检失败（T+2分钟）
**探测结果：** 同样失败

**规则处理：**
```
currentFailures = 1 + 1 = 2

检查告警边界：
  failures >= 2? → YES
  冷却时间检查：最近60分钟内是否发送过consecutive_failures? → NO
  → 发送连续失败告警

检查封禁边界：
  failures >= 5? → 2 >= 5? → NO → 不封禁
```

**通知发送：**
- 类型：`consecutive_failures`
- 严重性：`error`
- 内容："您的回调地址 https://down.example.com/callback 已连续失败 2 次，请检查服务是否正常。"
- 冷却时间记录：当前时间

**状态变更：**
- `consecutiveFailures`: 1 → 2
- 通知状态：已发送连续失败告警
- 地址状态：仍为`active`

**关键检查点：**
- [x] 连续失败告警触发正确
- [x] 冷却时间记录正确
- [x] 客户信息关联正确

#### 步骤4：第3-4次巡检失败（T+3 ~ T+4分钟）
**探测结果：** 持续失败

**规则处理：**
```
第3次：
  failures = 3
  告警边界：YES，但冷却时间检查 → 60分钟内已发送 → 跳过
  封禁边界：3 >= 5? → NO

第4次：
  failures = 4
  告警边界：YES，但冷却时间检查 → 仍在冷却期 → 跳过
  封禁边界：4 >= 5? → NO
```

**状态变更：**
- `consecutiveFailures`: 2 → 3 → 4
- 通知状态：无新通知（冷却期）
- 地址状态：仍为`active`

**关键检查点：**
- [x] 告警风暴防护有效
- [x] 失败计数持续递增
- [x] 历史记录持续累积

#### 步骤5：第5次巡检失败（T+5分钟）
**探测结果：** 仍然失败

**规则处理：**
```
failures = 4 + 1 = 5

检查封禁边界：
  failures >= 5? → YES
  当前状态为active? → YES
  → 执行封禁流程

封禁流程：
  1. 发送封禁通知
  2. 更新状态为'blocked'
  3. 记录lastBlockedAt
  4. 停止cron调度任务
```

**通知发送：**
- 类型：`blocked`
- 严重性：`critical`
- 内容："您的回调地址 https://down.example.com/callback 因连续失败次数过多已被封禁..."

**状态变更：**
- `consecutiveFailures`: 4 → 5
- `status`: `active` → `blocked`
- `lastBlockedAt`: 当前时间
- cron任务：已停止

**关键检查点：**
- [x] 封禁条件判断正确
- [x] 封禁通知发送
- [x] 调度任务停止
- [x] 所有历史数据保留

### 2.3 失败路径总结

这个路径展示了系统如何：
1. **容忍短时故障：** 第1次失败不告警，允许网络抖动
2. **渐进式告警：** 第2次失败开始告警，给客户响应时间
3. **防止告警风暴：** 60分钟冷却期内不重复发送
4. **自动保护机制：** 连续5次失败自动封禁，避免资源浪费
5. **完整可追溯：** 每一步都有历史记录和状态变更

## 三、重复执行路径分析

### 3.1 路径概述

**场景：** 同一客户多次尝试注册完全相同的回调地址，期望系统能够正确处理重复注册。

**路径包括两种子场景：**
- **场景A：** 完全相同的URL重复注册
- **场景B：** URL大小写不同（如`https://Example.com/Callback`）

### 3.2 场景A：完全相同的URL重复注册

#### 执行步骤

**第1次注册（成功）：**
```json
POST /callback-urls
{
  "customerId": "customer-002",
  "url": "https://api.example.com/webhook",
  "description": "首次注册",
  "frequencyMinutes": 5
}
```

**系统行为：**
1. 数据库查询：`SELECT * FROM callbackUrls WHERE customerId = 'customer-002' AND url = 'https://api.example.com/webhook'`
2. 查询结果：空 → 无重复
3. 创建新记录，分配新ID
4. 调度cron任务

**返回结果（201 Created）：**
```json
{
  "success": true,
  "data": {
    "id": "url-001",
    "customerId": "customer-002",
    "url": "https://api.example.com/webhook",
    "status": "active",
    "consecutiveFailures": 0,
    "isDuplicate": false
  }
}
```

**第2次注册（重复，失败）：**
```json
POST /callback-urls
{
  "customerId": "customer-002",
  "url": "https://api.example.com/webhook",
  "description": "第二次注册，描述不同",
  "frequencyMinutes": 10
}
```

**系统行为：**
1. 数据库查询：相同的查询条件
2. 查询结果：找到记录`url-001` → 存在重复
3. 不创建新记录
4. 不修改原有记录的任何字段（包括frequencyMinutes）
5. 不创建新的调度任务

**返回结果（409 Conflict）：**
```json
{
  "success": false,
  "message": "Callback URL already exists for this customer",
  "data": {
    "id": "url-001",
    "customerId": "customer-002",
    "url": "https://api.example.com/webhook",
    "status": "active",
    "consecutiveFailures": 0,
    "isDuplicate": true
  }
}
```

**关键检查点：**
- [x] 重复检测基于`customerId + url`组合，而非单独URL
- [x] 重复时返回原有记录的完整信息
- [x] `isDuplicate`标记为true，便于调用方识别
- [x] 新的`frequencyMinutes`参数被忽略
- [x] 不创建重复的调度任务
- [x] HTTP状态码为409（冲突），而非400（错误请求）

### 3.3 场景B：不同客户注册相同URL

**第1次注册（客户A）：**
```json
POST /callback-urls
{
  "customerId": "customer-A",
  "url": "https://shared.example.com/webhook"
}
```
→ 成功创建（201）

**第2次注册（客户B，相同URL）：**
```json
POST /callback-urls
{
  "customerId": "customer-B",
  "url": "https://shared.example.com/webhook"
}
```
→ 成功创建（201），因为`customerId`不同

**关键检查点：**
- [x] 不同客户可以注册相同的URL（多租户隔离）
- [x] 每个客户有独立的失败计数和状态
- [x] 调度任务独立创建和管理

### 3.4 重复路径的设计意图

1. **幂等性考虑：** 
   - 客户可能因网络超时重试注册请求
   - 返回原有记录而非报错，便于重试场景
   - 但使用409状态码明确告知这是重复操作

2. **数据一致性：**
   - 避免同一客户下出现多条相同URL的记录
   - 防止巡检任务重复执行（浪费资源）
   - 保证失败计数的准确性（不会分散到多条记录）

3. **客户体验：**
   - 返回原有记录的ID，客户可以直接使用
   - 明确的错误信息，客户知道应该调用`PUT`接口更新
   - 不静默忽略，也不造成数据混乱

## 四、其他重要边界场景

### 4.1 暂停恢复路径

**流程：**
1. 客户注册地址，连续失败3次（`consecutiveFailures = 3`）
2. 客户暂停巡检（`status = 'paused'`，保留失败计数）
3. 暂停期间：不执行巡检，失败计数保持3
4. 客户恢复巡检（`status = 'active'`）
5. 恢复后第1次失败 → `consecutiveFailures = 4`（从3继续）
6. 恢复后第2次失败 → `consecutiveFailures = 5` → 封禁

**关键检查点：**
- [x] 暂停期间不重置失败计数
- [x] 恢复后继续使用原有计数判断升级
- [x] 暂停期间停止所有调度任务
- [x] 恢复时重新创建调度任务

### 4.2 成功重置路径

**流程：**
1. 连续失败3次（`consecutiveFailures = 3`）
2. 第4次巡检成功
3. `consecutiveFailures` 立即重置为0
4. 第5次即使失败，也从0开始计数（不会直接触发封禁）

**关键检查点：**
- [x] 一次成功完全重置失败计数
- [x] 给客户修复后重新开始的机会
- [x] 不累积历史失败记录

## 五、复查检查清单

下一轮复查时，可按以下清单逐项验证：

### 重复注册检查
- [ ] 同一客户相同URL → 返回409，`isDuplicate: true`
- [ ] 不同客户相同URL → 各自独立创建
- [ ] 重复注册时不修改原有记录
- [ ] 重复注册时不创建重复调度任务

### 连续失败检查
- [ ] 失败1次 → 不告警，计数=1
- [ ] 失败2次 → 发送首次告警，计数=2
- [ ] 失败3-4次 → 冷却期内不重复告警，计数递增
- [ ] 失败5次 → 发送封禁告警，状态变为blocked，停止调度
- [ ] 失败记录完整保留

### 暂停恢复检查
- [ ] 暂停时记录暂停原因
- [ ] 暂停期间停止调度任务
- [ ] 暂停期间失败计数保持不变
- [ ] 恢复后继续原有失败计数
- [ ] 恢复后重新创建调度任务

### 通知系统检查
- [ ] 60分钟内同类型通知只发送一次
- [ ] 不同类型通知独立冷却
- [ ] 证书过期前14天开始提醒
- [ ] 证书过期后立即发送紧急通知
- [ ] 通知记录持久化到数据库

### 数据隔离检查
- [ ] 客户A无法查询客户B的回调地址
- [ ] 客户A无法查询客户B的巡检历史
- [ ] 客户A无法操作客户B的通知
- [ ] 汇总统计按客户维度正确隔离
