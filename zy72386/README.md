# 粮仓通风阻力复盘

粮仓通风阻力复盘工具，面向设备工程师和安全员，解决维修群截图一晚到后原始判断变化、返工无痕迹、传感器重启后编号变更难以追踪等痛点。

## 快速开始

```bash
# 安装依赖
npm install

# 启动开发服务器（前端 + 后端同时启动）
npm run dev
```

前端访问 http://localhost:5173，后端 API 运行在 http://localhost:3001。

## 从样例跑到报告

### 第一步：导入设备铭牌参数

1. 打开 http://localhost:5173/import
2. 填写批次标签（如"1号仓首次导入"）
3. 填写操作人（如"何工"）
4. 上传 `sample/first_import.csv`，点击上传
5. 系统显示导入结果：5 条记录，0 重复，0 异常

### 第二步：传感器重启后再次导入

1. 再次上传 `sample/second_import_after_restart.csv`
2. 系统按"物理设备匹配"检测（安装位置 + 设备名称），每条记录标记来源：
   - **♻️ 复用**：S-001、S-003，与历史记录完全一致，直接复用
   - **🔄 编号变更**：S-002-B（原 S-002），同一台物理设备但传感器重启后编号变了
   - **🆕 新增**：S-006，新设备
3. 编号变更的记录自动创建"待复核"记录，状态 = sensor_id_changed，卡在步骤2（维修群截图补看）
4. 此时异常数 = 1（S-002 编号变更待审核）

### 第三步：复盘工作台审核

1. 进入 http://localhost:5173/review，选择刚导入的批次
2. 步骤指示器显示当前进度
3. 传感器编号变更卡片显示：
   - S-002 → S-002-B：传感器重启后编号变更（卡在步骤2：维修群截图补看）
4. 数据明细表中每条记录都有"记录来源"标签：新增/复用/编号变更
5. **安全员**无需询问设备工程师，即可看到每条变更卡在哪一步
6. 确认后，记录进入步骤3（安全提醒更新），状态变为 normal
7. 驳回则退回步骤2

### 第四步：运行自检

1. 进入 http://localhost:5173/selfcheck，选择批次
2. 点击"运行自检"
3. 查看四项自检结果：重复导入、编号变更、补录重算、导出一致性

### 第五步：导出报告

1. 进入 http://localhost:5173/export，选择批次
2. 选择导出范围（全部/仅异常/仅待复核）
3. 点击"导出"下载 CSV
4. 点击"一致性校验"验证数据一致性

## 功能概览

| 页面 | 路径 | 功能 |
|------|------|------|
| 首页仪表盘 | / | 待复核事项概览、摘要卡片、最近导入 |
| 数据导入 | /import | CSV/Excel 上传、重复检测、导入历史 |
| 复盘工作台 | /review | 三步工作流、编号变更卡片、数据明细、手动编辑 |
| 自检面板 | /selfcheck | 四项自检：重复导入、编号变更、补录重算、导出一致 |
| 审计追踪 | /audit | 变更时间线、原始行号对照 |
| 导出报告 | /export | CSV 导出、一致性校验 |

## 记录来源分类

同一批设备第二次导入时，系统自动区分每条记录的来源：

| 来源 | 说明 | 标记 |
|------|------|------|
| 新增 | 历史中没有的新设备 | 🆕 蓝色 |
| 复用 | 与历史记录完全一致的设备 | ♻️ 灰色 |
| 编号变更 | 同一台物理设备（安装位置+设备名称匹配）但传感器ID变了 | 🔄 琥珀色 |

页面、导出、接口均包含此分类，方便安全员快速识别。

## 自检覆盖

1. **重复导入**：跨批检测 sensor_id 重复
2. **传感器编号变更**：检测待复核的编号变更记录
3. **补录后重算**：检测已编辑但未推进步骤的记录
4. **导出一致性**：SHA256 哈希校验导出数据与数据库一致

## 数据一致性保证

导出明细、页面展示、接口返回均读取同一份 SQLite 数据。导出时通过 `X-Consistency-Hash` 头和一致性校验接口确保数据不会出现"一个地方显示异常、另一个地方消失"的问题。

## 审计追踪

每条记录保留完整证据链，安全员追问时可追溯：
- 原始行号（original_row_number）
- 记录来源（new / reused / id_changed）
- 人工改动（manual_edits 表，含字段、旧值、新值、操作人、时间）
- 当前处理状态（status + current_step）
- 完整变更时间线（audit_log 表）

审计事件类型包括：
- `record_created`：记录创建
- `sensor_id_changed`：传感器编号变更检测
- `status_updated`：状态变更
- `step_advanced`：步骤推进
- `sensor_change_confirmed`：安全员确认编号变更
- `sensor_change_rejected`：安全员驳回编号变更
- `manual_edit`：手动编辑字段

## 交接体验

安全员打开复盘结果时：
- 顶部横幅显示"待复核事项 N 项"
- 传感器编号变更卡片明确标注"卡在步骤2：维修群截图补看"
- 数据明细表每条记录都有"记录来源"标签（新增/复用/编号变更）
- 底部交接信息框汇总：N 条记录 / 新增 X / 复用 Y / 编号变更 Z / 待复核 M
- 无需询问设备工程师即可理解完整上下文

## 技术栈

- 前端：React 18 + TypeScript + Tailwind CSS + Zustand
- 后端：Express 4 + TypeScript (ESM)
- 数据库：SQLite (better-sqlite3)
- 文件解析：papaparse (CSV) + xlsx (Excel)
