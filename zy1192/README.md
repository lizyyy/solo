# 并发原语可视化实验台

一个用于教学演示并发编程原语的可视化实验台，帮助理解 **Mutex、读写锁、自旋锁、CAS、无锁队列** 和 **ABA 问题**。

## 功能特性

### 🔐 支持的并发原语

| 原语类型 | 描述 |
|---------|------|
| **互斥锁 (Mutex)** | 最基本的线程同步原语，一次只允许一个线程访问临界区 |
| **读写锁 (RWLock)** | 允许多个读者同时访问，写操作互斥，适用于读多写少场景 |
| **自旋锁 (SpinLock)** | 通过忙等待获取锁，避免上下文切换开销，适用于短临界区 |
| **比较并交换 (CAS)** | 无锁编程的基础原子操作，实现乐观并发控制 |
| **无锁队列** | 基于 CAS 实现的无锁数据结构，高性能并发队列 |

### 🎯 核心功能

- **可视化配置**：配置线程数、操作序列、竞争强度、ABA 复现步骤
- **实时模拟**：模拟线程调度、锁状态变化、CAS 成败、队列入出队
- **多维度可视化**：
  - 时间线视图：显示所有事件的发生顺序
  - 等待/自旋成本对比：分析不同锁的性能开销
  - 吞吐对比：比较不同原语的吞吐量
  - 事件类型分布：饼图展示各类事件比例
- **ABA 问题演示**：
  - CAS 场景 ABA 复现
  - 无锁队列 ABA 复现
  - 版本戳解决方案演示
- **报告导出**：支持导出 Markdown 和 JSON 格式的报告
- **内置示例**：6 个预设教学示例
- **异常输入提示**：完善的表单验证和错误提示

## 原语详解

### 互斥锁 (Mutex)

**概念**：互斥锁是最基本的线程同步原语，确保一次只有一个线程可以访问临界区。

**特点**：
- 持有锁的线程执行临界区代码
- 其他线程尝试获取锁时会被阻塞
- 锁释放后，等待的线程会被唤醒
- 存在上下文切换开销

**适用场景**：
- 临界区执行时间较长
- 线程数量较多
- 需要避免 CPU 空转

### 读写锁 (Read-Write Lock)

**概念**：读写锁允许多个线程同时读取共享数据，但写操作是互斥的。

**特点**：
- 读读共享：多个线程可以同时持有读锁
- 读写互斥：写线程会阻塞所有读线程
- 写写互斥：写线程之间互斥
- 通常支持锁升级（读锁升级为写锁）

**适用场景**：
- 读多写少的场景
- 数据读取频率远高于写入频率
- 需要提高并发读性能

### 自旋锁 (Spin Lock)

**概念**：自旋锁在获取锁失败时不会阻塞，而是循环检查锁是否可用。

**特点**：
- 忙等待而不是阻塞
- 避免上下文切换开销
- 长时间自旋会浪费 CPU 资源
- 可能导致优先级反转问题

**适用场景**：
- 临界区非常短
- 锁持有时间很短
- 多核 CPU 环境

### 比较并交换 (CAS)

**概念**：CAS 是一种原子操作，比较内存值与期望值，如果相等则更新为新值。

**操作逻辑**：
```
function CAS(addr, expected, newValue):
    if *addr == expected:
        *addr = newValue
        return true
    return false
```

**特点**：
- 无锁编程的基础
- 属于乐观并发控制
- 由硬件指令支持（如 x86 的 CMPXCHG）
- 可能存在 ABA 问题

**适用场景**：
- 实现无锁数据结构
- 高性能并发计数器
- 乐观锁实现

### 无锁队列 (Lock-Free Queue)

**概念**：基于 CAS 操作实现的队列，不需要传统的锁机制。

**实现方式**：
- 使用 head 和 tail 指针
- 入队操作：CAS 更新 tail 指针
- 出队操作：CAS 更新 head 指针
- 使用版本戳或引用计数避免 ABA 问题

**特点**：
- 高并发下性能优异
- 不存在死锁问题
- 实现复杂度较高
- 需要处理 ABA 问题

**适用场景**：
- 高性能消息队列
- 生产者-消费者模式
- 高并发数据处理

### ABA 问题

**概念**：当一个值从 A 变成 B，又变回 A 时，CAS 操作会误以为值没有变化而错误地成功。

**典型场景**：

```
时间线：
T0: 线程 1 读取值 = A (版本 1)
T1: 线程 2 将值修改为 B (版本 2)
T2: 线程 2 将值修改回 A (版本 3)
T3: 线程 1 执行 CAS，预期为 A，成功！
```

**问题**：虽然值都是 A，但实际上数据已经被修改过了，CAS 无法检测到这一点。

**解决方案**：
1. **版本戳 (Version Tagging)**：每次修改都增加版本号，CAS 同时比较值和版本号
2. **引用计数 (Reference Counting)**：跟踪指针的引用，避免过早回收
3. **危险指针 (Hazard Pointers)**：记录正在使用的指针，防止被回收

## 常见问题

### Q: 为什么自旋锁在高竞争下性能不好？

**A**: 自旋锁在等待时会持续占用 CPU 检查锁状态。高竞争下，大量线程同时自旋会导致：
- CPU 资源浪费
- 内存总线竞争
- 缓存一致性开销

而互斥锁会让等待线程睡眠，让出 CPU 给其他线程。

### Q: 读写锁一定比互斥锁好吗？

**A**: 不一定。读写锁的优势在读多写少场景。如果写操作频繁：
- 写线程会阻塞所有读线程
- 锁本身的开销更大
- 可能出现写饥饿问题

需要根据实际读写比例选择。

### Q: 什么情况下应该使用无锁编程？

**A**: 无锁编程适用于：
- 极高的并发需求
- 不能容忍锁带来的延迟
- 临界区非常短小
- 需要避免死锁风险

但无锁编程实现复杂，容易出错，需要谨慎使用。

### Q: 版本戳一定能解决 ABA 问题吗？

**A**: 版本戳（或引用计数）是目前最常用的 ABA 解决方案，但需要注意：
- 版本号可能溢出（使用 64 位版本号可缓解）
- 需要原子地同时修改值和版本号
- 在某些语言/平台上需要特殊处理
