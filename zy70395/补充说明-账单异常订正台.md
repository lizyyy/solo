# 账单异常订正台 - 补充说明文档

## 系统概览

本系统是一个完整的账单异常订正管理平台，提供以下核心功能：

### 前端页面功能
- **概览面板**：展示账单、异常、订正、版本、通知的统计数据
- **账单管理**：查看所有账单、导入账单、查看账单详情、标记异常、发起订正
- **订正申请**：查看所有订正申请、审批、驳回、发布
- **异常记录**：查看所有异常记录

### 后端API功能
- **账单导入**：支持CSV格式导入账单数据
- **异常标记**：标记账单异常
- **订正试算**：模拟不同规则下的计算结果
- **生成新版本**：创建新版本（不覆盖旧版本）
- **审批流程**：支持审批通过/驳回
- **回滚功能**：回滚到历史版本
- **客户通知**：支持发送通知及重发机制

## 主要边界条件

### 边界1：账单版本不可覆盖

**业务规则**：
- 任何时候都不能覆盖已存在的账单版本
- 每次订正都会生成新的版本号（v1 → v2 → v3...）
- 旧版本永远保留在数据库中

**技术实现**：
- `bill_versions` 表使用 `(bill_id, version_number)` 联合唯一索引
- 发布订正时，先将所有版本 `is_active=0`，再插入新版本 `is_active=1`
- 版本号通过 `MAX(version_number) + 1` 计算，永不重复

**检查要点**：
```
✅ 确认每次订正后版本号递增
✅ 确认旧版本的 is_active 被设置为 0
✅ 确认旧版本的 created_by 和 created_at 保留不变
✅ 确认同一账单不能有两个版本号相同的记录
```

### 边界2：已支付账单只能做差额调整

**业务规则**：
- 已支付账单（status='paid'）不能直接修改金额
- 只能生成"差额调整单"，单独记录差额
- 原账单金额保持不变

**技术实现**：
- 订正前检查 `bill_versions.is_paid` 字段
- 如果已支付，`correction_type = 'adjustment'`，记录 `adjustment_amount`
- 发布时仍生成新版本，但系统知道这是"差额调整"而非"全额重算"
- 客户通知类型为 `adjustment_notice` 而非 `bill_updated`

**检查要点**：
```
✅ 确认已支付账单的 correction_type 为 'adjustment'
✅ 确认 adjustment_amount 字段有正确值
✅ 确认原版本的 is_paid 状态保持为 1
✅ 确认新版本也继承 is_paid=1
✅ 确认客户通知类型正确
```

### 边界3：未审批的新版本不能通知客户

**业务规则**：
- 订正申请处于 draft 或 pending_approval 状态时，不能发送通知
- 只有审批通过（approved）并发布（published）后才能创建通知
- 通知创建后状态为 pending，需要手动触发发送

**技术实现**：
- 客户通知只在 `publishCorrection` 函数中创建
- 通知创建后状态为 `pending`，需要调用 `sendNotification` API
- UI 上"重发"按钮只对 failed 或 pending 状态的通知显示
- 通知状态：pending → sent/failed

**检查要点**：
```
✅ 确认 draft/pending_approval 状态的订正没有通知记录
✅ 确认只有 published 状态的订正才创建通知
✅ 确认通知初始状态为 pending
✅ 确认已发送（sent）的通知不能再次发送
✅ 确认失败（failed）的通知可以重发
```

### 边界4：同一账单重复订正要合并

**业务规则**：
- 同一账单不能同时有多个活跃的订正申请
- 如果已有 draft/pending_approval 的申请，新申请会被拒绝
- 但可以对同一个账单发起多轮订正（前一轮结束后）

**技术实现**：
- `checkActiveCorrection` 函数检查是否有活跃申请
- 如果存在，抛异常："该账单已有活跃的订正申请，请先处理"
- 前一轮订正被 rejected 或 published 后，可以再次发起

**检查要点**：
```
✅ 确认已有活跃申请时，新申请被拒绝
✅ 确认申请被 rejected 后可以再次发起
✅ 确认申请被 published 后可以再次发起（版本迭代）
✅ 确认多轮订正生成多个版本号（v1→v2→v3）
```

### 边界5：回滚后保留旧版本

**业务规则**：
- 回滚不会删除任何版本
- 回滚只是切换哪个版本是 active
- 回滚记录单独存储在 version_rollbacks 表中

**技术实现**：
- 回滚时，将所有版本 is_active=0，然后将目标版本 is_active=1
- 插入记录到 version_rollbacks 表，记录被回滚的版本和恢复的版本
- 所有历史版本（包括被回滚的）都在数据库中保留

**检查要点**：
```
✅ 确认回滚后目标版本 is_active=1
✅ 确认被回滚的版本 is_active=0 但记录仍然存在
✅ 确认 version_rollbacks 表有记录
✅ 确认回滚记录包含 rolled_back_version_id 和 restored_version_id
✅ 确认回滚后可以继续发起新订正
```

### 边界6：客户通知失败时流程未完成

**业务规则**：
- 通知失败（status='failed'）意味着订正流程"没有完全完成"
- UI 必须提示用户存在未完成的通知
- 必须提供"重发"机制

**技术实现**：
- 订正申请详情页顶部显示红色警告："订正流程未完全完成 - 存在客户通知失败"
- 概览面板中"通知失败"统计显示红色
- 通知失败状态显示红色脉冲动画（pulse-dot）
- 每条失败通知都有"重发"按钮

**检查要点**：
```
✅ 确认概览面板通知失败数显示红色
✅ 确认订正详情页有警告提示
✅ 确认失败状态有脉冲动画
✅ 确认重发按钮可用
✅ 确认重发成功后状态变为 sent
✅ 确认通知完全成功后警告消失
```

## 一个失败路径

### 路径描述：订正审批通过 → 发布 → 通知失败

### 详细步骤

**步骤1：发现异常并创建订正申请**
- 账单：BILL-2024-003（未支付，v1）
- 当前规则：错误折扣规则-5%（金额：￥14,250）
- 目标规则：高级客户折扣-15%
- 申请人：analyst2

**系统状态检查**：
```
✅ correction_requests 表新增记录
✅ status = 'draft'
✅ trial_result = 2250（15%折扣金额）
✅ trial_final_amount = 12750
✅ source_version_id 指向 v1
```

**步骤2：审批通过**
- 审批人：manager2
- 意见：同意订正

**系统状态检查**：
```
✅ correction_requests.status = 'approved'
✅ correction_approvals 表新增记录
✅ action = 'approve'
```

**步骤3：发布订正**
- 发布人：manager2

**系统状态检查**：
```
✅ bill_versions 表新增 v2
✅ v2.is_active = 1, v1.is_active = 0
✅ correction_requests.status = 'published'
✅ customer_notifications 表新增记录
✅ notification.status = 'pending'
✅ bill_anomalies.status = 'resolved'（如果有）
```

**步骤4：发送通知（失败）**
- 调用 sendNotification API
- 模拟：邮件服务器连接超时

**系统状态检查**：
```
✅ notification.status = 'failed'
✅ notification.error_message = '邮件服务器连接超时（模拟）'
✅ notification.sent_at 有值（发送时间，即使失败）
✅ 概览面板"通知失败"计数 +1
```

**步骤5：系统行为**

**预期的UI行为**：
1. 概览面板中"通知失败"数字显示为红色
2. 打开订正申请详情时，顶部显示红色警告：
   ```
   ⚠️ 订正流程未完全完成 - 存在客户通知失败
   请点击下方"重发"按钮重试通知
   ```
3. 通知状态显示"发送失败"，并有红色脉冲动画
4. 每条失败的通知旁边有"重发"按钮

**步骤6：重发通知**
- 点击"重发"按钮
- 这次模拟成功（70%概率）

**系统状态检查**：
```
✅ notification.status = 'sent'
✅ notification.error_message = null（保留原值？需要确认业务需求）
✅ 概览面板"通知失败"计数 -1，"已发送"计数 +1
✅ 订正详情页警告消失
```

### 失败路径复查清单

```
□ 创建订正申请（draft状态）
□ 审批通过（approved状态）
□ 发布（published状态，生成新版本v2，激活v2，停用v1）
□ 发送通知失败（failed状态，记录错误信息）
□ 确认UI显示"流程未完成"警告
□ 确认概览面板显示失败数
□ 重发通知成功（sent状态）
□ 确认警告消失
□ 确认旧版本v1仍然存在（is_active=0）
```

## 一次重复执行路径

### 路径描述：对同一账单连续发起两次订正，中间有一次回滚

### 场景设定

**账单**：BILL-2024-003（王五网络科技）
**初始状态**：
- v1：错误折扣-5%，金额 ￥14,250，is_active=1
- 未支付，可以全额重算

### 详细步骤

**第一轮订正**

**步骤1：第一次申请订正**
- 目标规则：高级客户折扣-15%
- 试算：金额从 ￥14,250 → ￥12,750
- 差额：-￥1,500（客户少付）

**步骤2：审批通过并发布**
- 生成 v2：15%折扣，金额 ￥12,750，is_active=1
- v1.is_active = 0
- 客户通知创建成功（假设发送也成功）

**此时系统状态**：
```
v1: 错误折扣-5%, ￥14,250, is_active=0
v2: 高级客户-15%, ￥12,750, is_active=1  ✅ 当前活跃
```

**发现问题**：
- 业务团队发现王五网络科技其实是"标准客户"而非"高级客户"
- 应该用10%折扣，不是15%折扣
- 需要回滚 v2，然后重新用正确规则订正

**步骤3：回滚到 v1**
- 操作人：manager3
- 原因："重复订正回滚"
- 目标版本：v1

**系统状态检查（回滚后）**：
```
✅ v1.is_active = 1  ✅ 恢复为活跃
✅ v2.is_active = 0  ✅ 被回滚
✅ version_rollbacks 表新增记录
   - rolled_back_version_id = v2.id
   - restored_version_id = v1.id
   - reason = '重复订正回滚'
✅ v2 记录仍然存在（没有被删除）
```

**第二轮订正**

**步骤4：第二次申请订正（用正确规则）**
- 检查：是否已有活跃订正申请？→ 没有（第一轮已 published）
- 目标规则：正确折扣规则-10%
- 试算：从 v1 的 ￥14,250 → ￥13,500
- 差额：-￥750

**步骤5：审批通过并发布**
- 生成 v3：10%折扣，金额 ￥13,500，is_active=1
- v1.is_active = 0（再次被停用）

**最终系统状态**：
```
v1: 错误折扣-5%, ￥14,250, is_active=0
v2: 高级客户-15%, ￥12,750, is_active=0  ✅ 被回滚
v3: 正确折扣-10%, ￥13,500, is_active=1    ✅ 当前活跃

version_rollbacks 表有记录：
  - rolled_back_version: v2
  - restored_version: v1
```

### 重复路径复查清单

```
□ 第一轮订正创建 v2（高级客户15%）
□ v2 发布后是 active，v1 是 inactive
□ 回滚操作后，v1 恢复 active，v2 变为 inactive
□ 确认 v2 记录仍然存在（没有被删除）
□ 确认 version_rollbacks 表有回滚记录
□ 第二轮订正可以创建（因为第一轮已完成）
□ 第二轮订正生成 v3（正确折扣10%）
□ v3 发布后是 active，v1 再次变为 inactive
□ 确认三个版本都存在，版本号连续递增
□ 确认每个版本的 created_by 和 created_at 都正确
□ 确认回滚记录包含被回滚版本和恢复版本
```
