# 冷库入库预约排队系统 - 重跑操作说明

## 一、失败场景概览

系统在以下三个关键环节可能会出现失败情况，失败后会自动记录到 `failed_tasks` 表中，而不是让整个预约流程中断：

1. **仓位锁定失败**：预约创建时，如果没有可用的匹配仓位
2. **检测排队失败**：车辆签到时，如果没有可用的检测窗口
3. **开始装卸失败**：检测合格后准备开始装卸时，如果仓位不可用

---

## 二、失败后的状态说明

当某个环节失败时，系统不会强制用户取消预约或重新开始，而是：

- 预约状态会停留在失败前的状态
- 系统会在 `failed_tasks` 表中记录详细的失败信息
- 用户可以在问题解决后，通过重跑接口继续处理

### 各环节失败后的预约状态

| 失败环节 | 预约状态 | 说明 |
|---------|---------|------|
| 仓位锁定失败 | `pending` (待确认) | 预约已创建，等待仓位分配 |
| 检测排队失败 | `confirmed` (已确认) | 仓位已锁定，等待加入检测排队 |
| 开始装卸失败 | `inspection_passed` (检测合格) | 检测已通过，等待开始装卸 |

---

## 三、重跑操作步骤

### 第一步：查看失败任务列表

**接口**：`GET /failed-tasks`

**查询参数**：
- `is_resolved` (可选)：`false` 表示只查看未解决的任务，`true` 表示只查看已解决的

**返回内容**：
- 任务 ID、关联的预约编号
- 失败类型、失败原因
- 重试次数、最大重试次数
- 发生时间、最后重试时间

**示例返回**：
```json
[
  {
    "id": 1,
    "appointment_id": 5,
    "appointment_no": "APPT-20250510-143025",
    "task_type": "storage_lock",
    "task_description": "锁定仓位失败",
    "error_message": "当前没有可用仓位，请稍后重试或联系管理员",
    "error_details": "尝试锁定仓位: FREEZE-001",
    "occurred_at": "2025-05-10T14:30:25.123456",
    "retry_count": 0,
    "max_retries": 3,
    "last_retry_at": null,
    "is_resolved": false
  }
]
```

---

### 第二步：分析失败原因并解决问题

根据返回的失败信息，采取相应的解决措施：

#### 场景 1：仓位锁定失败
- **失败原因**：`没有可用的匹配仓位`
- **解决方法**：
  1. 查看现有仓位使用情况：`GET /master/storage-bays`
  2. 确认是否有其他预约完成后释放了仓位
  3. 或新增符合要求的仓位：`POST /master/storage-bays`
  4. 或调整现有仓位的状态为可用：`PUT /master/storage-bays/{bay_id}`

#### 场景 2：检测排队失败
- **失败原因**：`没有可用的检测窗口`
- **解决方法**：
  1. 查看检测窗口状态：`GET /master/inspection-windows`
  2. 启用已停用的窗口：`PUT /master/inspection-windows/{window_id}`
  3. 或新增检测窗口：`POST /master/inspection-windows`

#### 场景 3：开始装卸失败
- **失败原因**：`没有可用的仓位`
- **解决方法**：
  1. 检查是否有其他预约完成后释放了仓位
  2. 确认预约所需的温区是否有可用仓位
  3. 确认仓位容量是否满足需求

---

### 第三步：执行重跑操作

#### 方式一：单个任务重跑（推荐用于精确处理）

**接口**：`POST /failed-tasks/{task_id}/retry`

**请求体**：
```json
{
  "operator_name": "张三"
}
```

**参数说明**：
- `operator_name` (可选)：执行重跑的操作人员姓名

**返回内容**：
```json
{
  "success": true,
  "message": "仓位锁定成功",
  "action_taken": "锁定仓位: FREEZE-002"
}
```

**可能的返回结果**：
1. **成功**：`success = true`，任务状态变为已解决
2. **仍失败**：`success = false`，重试次数 +1，可以再次重试
3. **达到最大重试次数**：返回错误，需要人工处理

#### 方式二：批量重跑（推荐用于多个同类失败任务）

**接口**：`POST /failed-tasks/batch-retry`

**请求体**：
```json
{
  "task_ids": [1, 2, 3],
  "operator_name": "张三"
}
```

**参数说明**：
- `task_ids`：要批量重跑的任务 ID 列表
- `operator_name` (可选)：执行重跑的操作人员姓名

**返回内容**：
```json
{
  "total": 3,
  "success": 2,
  "failed": 1,
  "details": [
    {"task_id": 1, "success": true, "message": "仓位锁定成功", "action_taken": "锁定仓位: FREEZE-002"},
    {"task_id": 2, "success": true, "message": "重新加入检测排队成功", "action_taken": "重新签到并分配排队号"},
    {"task_id": 3, "success": false, "message": "当前没有可用仓位，请稍后重试或联系管理员", "action_taken": "重试失败"}
  ]
}
```

#### 方式三：人工标记为解决（问题已通过其他方式处理）

**接口**：`POST /failed-tasks/{task_id}/resolve-manually`

**适用场景**：
- 已达到最大重试次数
- 问题已通过其他方式解决
- 需要跳过系统自动处理流程

**请求参数**（Query 参数）：
- `resolution_notes`：解决说明（必填）
- `operator_name`：操作人姓名（可选）

**示例**：
```
POST /failed-tasks/5/resolve-manually?resolution_notes=已手动分配仓位FREEZE-003&operator_name=张三
```

## 四、各环节重跑后的自动处理逻辑

### 1. 仓位锁定失败的重跑

重跑时系统会自动执行以下操作：
1. 再次查找符合以下条件的仓位：
   - 状态为 `available` (可用)
   - 温区与预约的温度要求一致
   - 仓位容量 >= 预约所需体积
2. 如果找到可用仓位：
   - 锁定该仓位（状态变为 `locked`）
   - 创建仓位锁定记录
   - 更新预约状态为 `confirmed` (已确认)
   - 标记失败任务为已解决
3. 如果仍未找到：
   - 重试次数 +1
   - 任务状态保持为待解决

### 2. 检测排队失败的重跑

重跑时系统会自动执行以下操作：
1. 查找状态为 `active` 的检测窗口
2. 分配新的排队号（当天的下一个可用号）
3. 创建或更新检测排队记录
4. 更新预约状态为 `checked_in` (已签到)
5. 标记失败任务为已解决

### 3. 开始装卸失败的重跑

重跑时系统会自动执行以下操作：
1. 检查预约当前是否有已锁定的仓位
   - 如有：直接使用该仓位
   - 如无：重新查找并锁定可用仓位
2. 更新仓位状态为 `occupied` (已占用)
3. 更新预约状态为 `in_loading` (装卸中)
4. 标记失败任务为已解决

---

## 五、重试次数限制说明

- **默认最大重试次数**：3 次
- **每次重跑**：重试次数 +1
- **达到上限**：无法再通过重跑接口处理，必须使用「人工标记为解决」方式

**如何查看重试状态**：
在失败任务列表中查看：
- `retry_count`：已重试次数
- `max_retries`：最大允许重试次数
- `last_retry_at`：最后一次重试时间

---

## 六、完整操作示例

### 场景：农产品入库时仓位已满

1. **创建预约**（失败，无可用仓位）
   ```
   POST /appointments
   → 预约创建成功，状态为 pending
   → 自动记录失败任务：storage_lock 类型
   ```

2. **查看失败任务**
   ```
   GET /failed-tasks?is_resolved=false
   → 看到任务 ID: 1，类型: storage_lock，重试次数: 0
   ```

3. **释放/新增仓位**
   ```
   PUT /master/storage-bays/5
   → 将某个仓位状态改为 available
   ```

4. **执行重跑**
   ```
   POST /failed-tasks/1/retry
   {
     "operator_name": "库管员小李"
   }
   → 返回成功，仓位已锁定
   ```

5. **确认预约状态**
   ```
   GET /appointments/5
   → 状态变为 confirmed，可以继续后续流程
   ```

## 七、注意事项

1. **重跑顺序**：失败任务是按发生时间记录的，重跑时不需要按顺序，但建议先解决资源问题再重跑

2. **资源冲突**：如果多个失败任务需要同一资源，系统会按重跑顺序依次分配

3. **数据一致性**：重跑操作是原子性的，要么全部成功，要么全部失败，不会出现中间状态

4. **日志追踪**：所有重跑操作都会记录在 `failed_tasks` 表的 `resolution_notes` 字段中，包含操作人和时间

5. **导出复核**：所有失败和重跑记录都会包含在每日业务复核报告中（Excel 的「异常处理记录」工作表）

## 八、API 接口速查

| 操作 | 方法 | 接口 | 说明 |
|-----|------|------|------|
| 查看失败任务列表 | GET | /failed-tasks | 查看所有未解决的失败任务 |
| 查看单个任务详情 | GET | /failed-tasks/{task_id} | 查看特定任务的详细信息 |
| 单个任务重跑 | POST | /failed-tasks/{task_id}/retry | 对单个任务执行重跑 |
| 批量任务重跑 | POST | /failed-tasks/batch-retry | 同时对多个任务执行重跑 |
| 人工标记解决 | POST | /failed-tasks/{task_id}/resolve-manually | 跳过自动处理，手动标记完成 |

---

## 九、与过号处理的区别

需要注意区分「失败任务」和「过号处理」：

| 类型 | 触发场景 | 处理方式 |
|-----|---------|---------|
| 失败任务 | 系统异常、资源不足等技术问题 | 通过重跑接口继续处理 |
| 过号处理 | 车辆迟到、司机不在场等业务场景 | 通过跳过接口过号，然后重新分配排队号 |

### 过号后的重新分配方式

如果是过号（Skip），使用以下接口：
```
POST /appointments/skip-records/{skip_record_id}/reassign
```

这个接口会：
1. 找到该过号记录
2. 分配新的排队号（排到队尾）
3. 更新预约状态为已签到
4. 可以继续检测流程

---

**总结**：系统的设计理念是「保存状态，等待恢复」，而不是「失败即终止」。所有失败都会被记录，问题解决后可以无缝继续，无需取消预约或重新创建。
