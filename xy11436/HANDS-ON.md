
## 二、失败路径演示

### 场景1: 重复提交 (Duplicate)

**现象**: 同一房间同一天从多个来源导入相同类型的清洁任务

**触发条件**:
```bash
# 第一次导入订单
node src/cli.js import samples/订单日历_20260523.csv

# 再次导入同一份文件（或包含相同房间日期的其他文件）
node src/cli.js import samples/订单日历_20260523.csv
```

**检测结果**:
- `check` 命令会标记为 `duplicate` 冲突
- 报表中会显示重复任务的来源文件和行号
- 来源证据不会被覆盖，全部保留

**错误输出示例**:
```
发现冲突: 3 条
  duplicate: 2 条
  overlap: 1 条

--- 冲突详情 ---
1. duplicate: 房间101-2026-05-23-退房清洁存在2条重复任务
2. duplicate: 房间102-2026-05-23-退房清洁存在2条重复任务
```

---

### 场景2: 撤回后再提交

**现象**: 先导入一份数据，撤回（删除）后，修正后重新导入

**操作流程**:
```bash
# 1. 导入原始数据
node src/cli.js import samples/订单日历_20260523.csv

# 2. 查看快照（找到导入前的快照）
node src/cli.js history --snapshots

# 3. 重置或回滚（实际操作中可能是删除特定任务）
node src/cli.js init --force

# 4. 修正后重新导入（假设我们修改了CSV文件）
node src/cli.js import samples/订单日历_20260523.csv
```

**关键点**:
- 每次操作都会生成快照，可以回滚对比
- 原始证据链完整保留在历史快照中
- 重新导入不会丢失历史操作记录

---

### 场景3: 部分失败 (Partial Failure)

**现象**: 导入文件中部分行解析失败，其他行成功导入

**构造失败数据** (`samples/部分失败示例.csv`):
```csv
房间号,入住日期,退房日期,客人
101,2026-05-22,2026-05-23,张三
无效房间,2026-05-22,2026-05-23,李四  # 解析失败：无效房间号
103,invalid-date,2026-05-23,王五    # 解析失败：日期格式错误
104,2026-05-22,2026-05-23,赵六
```

**导入结果**:
```
✓ 成功解析: 2 条
✗ 解析失败: 2 条
  行2: 无法提取房间号
  行3: 入住日期无效: invalid-date
```

**关键点**:
- 失败行不会导致整个导入中断
- 失败行的原始内容和行号完整记录
- 成功导入的行正常处理

---

### 场景4: 多源数据重叠 (Overlap)

**现象**: 订单日历和保洁群消息都包含同一房间的清洁安排

**触发条件**:
```bash
# 先导入订单日历
node src/cli.js import samples/订单日历_20260523.csv

# 再导入保洁群消息（包含重叠房间）
node src/cli.js import samples/保洁群消息_20260523.txt

# 执行检测
node src/cli.js check
```

**检测到的冲突**:
- 101号房: 订单日历的"退房清洁" vs 群消息的"退房清洁"
- 102号房: 两个来源都有记录
- 103号房: 订单显示退房，群消息显示续住（数据不一致）

**报表重点**:
```
【失败任务】共 5 条
┌──────┬──────────┬──────────┬──────┬──────────────┬──────────────────┐
│ 房间 │ 日期     │ 类型     │ 状态 │ 未解决冲突   │ 来源文件:行号    │
├──────┼──────────┼──────────┼──────┼──────────────┼──────────────────┤
│ 101  │2026-05-23│退房清洁  │failed│overlap       │订单日历.csv:2;   │
│      │          │          │      │              │群消息.txt:2      │
└──────┴──────────┴──────────┴──────┴──────────────┴──────────────────┘
```

### 场景5: 连住换布草冲突 (Linen Change)

**现象**: 客人连续入住多天，中间是否需要换布草的标记不一致

**触发数据**:
- 订单日历 106号房: 备注"不换布草-续住" (5月22日-24日)
- 订单日历 103号房: 连住3天 (5月20日-23日)

**检测逻辑**:
- 连续入住超过1天，且标记"不换布草"
- 系统自动检测是否符合规定

**冲突描述**:
```
linen_change: 房间106连住期间未换布草: 2026-05-23 - 2026-05-24
```

---

### 场景6: 临时退房冲突 (Early Checkout)

**现象**: 客人入住当天就退房，可能是临时取消

**触发数据**:
- 105号房钟点房: 入住和退房在同一天
- 无扫码完成记录

**冲突描述**:
```
early_checkout: 房间105(2026-05-23)疑似临时退房，无扫码验证
```

## 三、修正方式详解

### 3.1 自动修复 (Auto Fix)

**适用场景**: 重复提交、多源重叠、布草冲突

**命令**:
```bash
node src/cli.js fix --auto --operator 店长
```

**修复策略**:

| 冲突类型 | 修复策略 |
|----------|----------|
| duplicate | 合并为一条任务，保留所有来源证据 |
| overlap | 以订单日历为准，合并群消息证据 |
| linen_change | 自动开启换布草标记 |
| early_checkout | 标记警告，需人工确认 |

**修复后效果**:
```
尝试修复: 5 条失败任务
自动修复: 3 条
无法自动修复: 2 条
```

---

### 3.2 人工改判 (Manual Override)

**适用场景**: 无法自动修复的冲突，需要人工判断

**查看修复建议**:
```bash
# 先找到任务ID
node src/cli.js report

# 查看该任务的修复建议
node src/cli.js fix --task <task-id>
```

**建议输出示例**:
```
任务 xxxxxxxx 的修复建议:

1. early_checkout: 房间105(2026-05-23)疑似临时退房，无扫码验证
   1.1 确认为临时退房，保留任务
   1.2 取消任务（订单取消）
   1.3 人工改判
```

**执行人工改判**:
```bash
node src/cli.js fix --task <task-id> --override --reason "客人确认今天退房"
```

**交互式输入**:
```
新日期 (留空保持不变): 
新类型 (留空保持不变): 钟点清洁
需要换布草? (yes/no/留空): yes

✓ 人工改判已应用
```

**关键点**:
- 原始证据**不会被覆盖**，永久保留
- 改判原因和操作者完整记录在审计轨迹中
- 可随时通过 `history` 命令追溯改判记录

---

### 3.3 修正后再导入

**场景**: 发现原始导入文件有误，修正文件后重新导入

**步骤**:
```bash
# 1. 修正原始CSV/TXT文件（比如修正房间号、日期等）

# 2. 重新导入
node src/cli.js import samples/修正后的文件.csv

# 3. 系统会自动匹配并更新已有任务
#    - 如果是同一来源同一行号：跳过（防重复）
#    - 如果是新行号：添加为新证据或新任务

# 4. 重新检测
node src/cli.js check

# 5. 对比前后变化
node src/cli.js history --diff <修正前的快照文件名>
```

**对比报告示例**:
```
对比: 2026-05-23T10:00:00 -> 当前
变更数: 3

+ 104 (2026-05-23)    # 新增任务
~ 102 (2026-05-23)     # 修改任务
   failed -> fixed
- 999 (2026-05-23)    # 移除的任务
```

## 五、边界情况处理

### 5.1 导出前冻结

**操作**:
```bash
node src/cli.js export --date 2026-05-23 --freeze --operator 店长
```

**冻结效果**:
- 所有任务状态变为 `frozen`
- 无法修改、删除、重新导入
- 无法执行新的check/fix操作
- 尝试修改会报错: `Data is frozen for export`

**解冻**:
```bash
node src/cli.js freeze --unfreeze --operator 店长
```

**为什么要冻结**:
- 防止导出后数据被意外修改
- 确保发给保洁的排班表与系统一致
- 翻旧账时有据可依（冻结时间、操作者记录）

---

### 5.2 异常不吞没原则

系统设计遵循 **"异常可见、可追溯"** 原则:

1. **导入异常** - 不跳过，明确记录失败行号和原因
2. **解析异常** - 不try-catch吞掉，抛出给用户看
3. **冲突检测** - 不自动静默修复，先报告再人工/自动处理
4. **自动修复失败** - 明确标记为"无法自动修复"，不假装成功

## 七、常见问题

### Q: 为什么报表一定要显示原始行号？
**A**: 因为翻旧账时，店长会拿着原始的Excel/TXT文件来核对。如果报表只给汇总数字，说"有3个冲突"，店长无法验证。必须能精确到"订单日历第5行"、"群消息第3行"，才能快速定位原始材料，确认是系统误报还是真的有问题。

### Q: 人工改判会不会覆盖原始证据？
**A**: 绝对不会。`manualOverride` 只是在任务上附加一个改判记录，`sourceEvidences` 数组永久保留所有原始导入的证据。导出报表时可以选择显示"原始值"还是"改判后值"。

### Q: 为什么要冻结才能导出？
**A**: 防止"导出的排班表"和"系统里的数据"不一致。如果导出后有人改了数据，过几天翻旧账时就对不上了。冻结确保了"导出那一刻"的快照被永久保留。

### Q: 重复导入同一份文件会怎样？
**A**: 系统会检测 `文件名 + 行号` 的组合。如果已存在，会跳过并提示，不会创建重复任务。但如果是**修正后重新导入**（同一行号内容改了），需要先撤回（删除原有任务）再重新导入。

## 八、命令速查

```bash
# 初始化
hci init
hci init --force    # 重置所有数据

# 导入
hci import <文件>                   # 自动识别类型
hci import <文件> --type order      # 强制指定类型
hci import <文件> --operator 店长   # 记录操作者

# 检测
hci check
hci check --date 2026-05-23

# 修复
hci fix --auto                      # 自动修复
hci fix --task <id>                 # 查看修复建议
hci fix --task <id> --override --reason "原因"  # 人工改判

# 报表
hci report                          # 控制台输出
hci report --format csv             # 导出CSV（推荐）
hci report --format json            # 导出JSON
hci report --date 2026-05-23        # 指定日期

# 历史
hci history                         # 最近操作
hci history --snapshots             # 所有快照
hci history --diff <快照文件>       # 对比变化

# 导出/冻结
hci export --date 2026-05-23        # 导出排班
hci export --freeze                 # 导出前冻结
hci freeze                          # 仅冻结
hci freeze --unfreeze               # 解冻
```
