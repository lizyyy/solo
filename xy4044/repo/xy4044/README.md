# 多路音视频延迟校准台

为远程乐队排练和小型直播团队设计的本地浏览器工具，用于校准多路音视频源的延迟问题。

## 功能特性

- **三栏布局工作区**：左侧源清单、中间时间线视图、右侧校准结果
- **多源类型支持**：麦克风、摄像头、远程WebRTC流、本地文件
- **多种证据类型**：音频拍手峰值、视频闪光帧、RTP时间戳、人工锚点
- **自动校准算法**：基于多种证据计算每路源的延迟偏移和置信度
- **问题检测**：时钟漂移、丢帧、采样率不一致、源重复导入、锚点冲突、抖动过大
- **回放预演**：按校准后的时间轴播放，标记不同步片段
- **本地持久化**：数据保存在浏览器 localStorage，刷新不丢失
- **导入导出**：完整会话JSON导入导出，带版本校验
- **报告生成**：Markdown校准报告和CSV偏移表

## 技术栈

- React 18 + TypeScript 5
- Vite 5 (构建工具)
- uuid (生成唯一ID)

## 核心使用流程

### 1. 导入示例数据

应用内置了三个预设场景，可以快速体验功能：

1. 打开右侧面板（校准结果/问题/回放日志标签页）
2. 滚动到底部找到「示例数据」区域
3. 点击任意场景加载：
   - **乐队排练场景**：包含鼓手、主唱、摄像头、远程贝斯手和伴奏轨，各源有预设延迟
   - **网络抖动场景**：对比稳定源和有网络抖动的远程源
   - **时钟漂移场景**：模拟三个源，其中两个有不同方向的时钟漂移

### 2. 自动校准

加载示例数据后，执行自动校准：

1. 点击顶部工具栏的「🔍 自动校准」按钮
2. 系统将执行以下步骤：
   - 选择或确认主时钟源（默认为事件最多的源）
   - 按时间分组同步事件（拍手峰值、闪光帧、RTP时间戳、人工锚点）
   - 计算每路源相对主时钟的延迟偏移（加权平均 + 异常值过滤）
   - 检测潜在问题（时钟漂移、抖动过大、采样率不一致等）
3. 校准完成后，右侧「校准结果」标签页会显示每路源的延迟偏移和置信度

**校准算法说明：**
- **证据加权**：人工锚点(1.0) > 闪光帧(0.9) > 拍手峰值(0.8) > RTP时间戳(0.7)
- **异常值过滤**：使用 IQR 方法过滤偏离中位数超过 1.5 * IQR 的证据点
- **置信度计算**：基于证据数量、证据分散程度、异常值比例综合评分

### 3. 手动覆盖校准结果

如果自动校准结果不理想，可以手动调整：

1. 在右侧「校准结果」标签页找到需要调整的源
2. 点击「编辑」按钮
3. 在弹出的输入框中输入新的延迟值（毫秒）
   - **正值**：表示该源滞后于主时钟，需要提前播放
   - **负值**：表示该源超前于主时钟，需要延后播放
   - **0**：表示与主时钟同步
4. 手动覆盖的结果会显示「手动覆盖」标记，置信度设为 1.0（非常高）

### 4. 回放预演

校准完成后，可以通过回放预演验证效果：

#### 播放控制
- **播放/暂停**：点击时间线控制栏的「▶️ 播放」或「⏸️ 暂停」
- **跳转**：点击时间轴下方的进度条任意位置
- **调速**：点击速度按钮选择播放速度（0.5x、1x、2x）

#### 时间线视图
- **事件标记**：时间轴上的圆点代表各类事件
  - 🔴 红色：音频拍手峰值
  - 🟡 黄色：视频闪光帧
  - 🟣 紫色：RTP时间戳
  - 🟢 绿色：人工锚点
- **播放头**：红色垂直线表示当前播放位置
- **轨道颜色**：每路源有独立的颜色标识

#### 同步检测
回放过程中系统会自动检测同步状态：
- **时间阈值**：默认 30ms 内认为同步
- **同步事件**：如果某时间点有 2 个或更多不同源的事件在阈值内，视为同步
- **不同步警告**：如果事件在阈值外，会在回放日志中记录

#### 回放日志
切换到右侧「回放日志」标签页查看：
- **sync_check**：同步检测结果
- **event**：检测到事件
- **issue**：检测到同步问题

### 5. 刷新恢复

项目数据自动保存在浏览器的 localStorage 中：

- **自动保存**：任何会话变更（添加源、添加事件、校准结果）都会自动保存
- **恢复机制**：刷新页面或重新打开浏览器，上次的会话数据会自动恢复
- **新建会话**：点击右侧面板底部的「➕ 新建会话」可以清除当前数据

### 6. 导入导出

#### 导出会话

1. 点击顶部工具栏的「📤 导出」按钮
2. 下载完整的会话 JSON 文件
3. 文件包含：源配置、所有事件、校准结果、问题记录、同步问题

#### 导入会话

1. 点击顶部工具栏的「📥 导入」按钮
2. 拖拽 JSON 文件到导入区域，或点击选择文件
3. 系统会执行以下校验：
   - **版本校验**：检查会话版本是否兼容
   - **源ID校验**：确保所有事件引用的源ID都存在
   - **时间戳单位**：检查时间戳单位是否有效
   - **必填字段**：检查所有必填字段是否存在
4. 校验通过后数据会导入，失败则显示错误信息

**导入安全机制：**
- 坏数据不会覆盖当前会话
- 导入时保留当前会话的 ID 和创建时间
- 错误信息详细说明具体问题

### 7. 生成报告

#### Markdown 校准报告

1. 在右侧「校准结果」标签页点击「📄 导出报告」
2. 下载的报告包含：
   - 会话基本信息（名称、时间、源数量、事件数量）
   - 校准摘要（主时钟源、校准时间、置信度分布）
   - 详细校准结果（每路源的延迟、置信度、证据数量）
   - 问题列表（所有检测到的问题，包括已解决的）
   - 同步问题统计
   - 建议（基于检测到的问题）

#### CSV 偏移表

1. 点击「📊 导出偏移表」
2. CSV 文件包含列：
   - `sourceId`：源唯一ID
   - `sourceName`：源名称
   - `sourceType`：源类型
   - `delayOffset`：延迟偏移（毫秒）
   - `confidence`：置信度（0-1）
   - `confidenceLevel`：置信度等级
   - `evidenceCount`：证据数量
   - `isManualOverride`：是否手动覆盖
   - `isMaster`：是否为主时钟

#### 事件 CSV

1. 点击「📋 导出事件」
2. 包含所有事件的详细信息

## 示例数据格式

### 会话 JSON 格式

```json
{
  "id": "uuid",
  "name": "会话名称",
  "description": "会话描述",
  "version": "1.0.0",
  "createdAt": 1700000000000,
  "updatedAt": 1700000000000,
  "timestampUnit": "ms",
  "masterClockSourceId": "source-uuid",
  "sources": [...],
  "events": [...],
  "calibrationResults": [...],
  "problems": [...],
  "syncIssues": [...]
}
```

### 源 (Source) 格式

```json
{
  "id": "uuid",
  "name": "鼓手麦克风",
  "type": "microphone",
  "sampleRate": 48000,
  "frameRate": null,
  "color": "#e94560",
  "isInMix": true,
  "createdAt": 1700000000000
}
```

**源类型 (type)：**
- `microphone`：麦克风
- `camera`：摄像头
- `remote_stream`：远程WebRTC流
- `local_file`：本地文件

### 事件 (Event) 格式

```json
{
  "id": "uuid",
  "sourceId": "source-uuid",
  "type": "clap_peak",
  "timestamp": 1000,
  "value": 0.95,
  "rtpTimestamp": null,
  "description": "鼓点击峰值 #1",
  "confidence": 0.95,
  "createdAt": 1700000000000
}
```

**事件类型 (type)：**
- `clap_peak`：音频拍手峰值
- `flash_frame`：视频闪光帧
- `rtp_timestamp`：RTP时间戳
- `manual_anchor`：人工锚点

### 问题 (Problem) 类型

| 类型 | 说明 | 严重程度 |
|------|------|----------|
| `clock_drift` | 时钟漂移 | warning |
| `frame_drops` | 丢帧 | warning |
| `sample_rate_mismatch` | 采样率不一致 | warning |
| `duplicate_source` | 源重复导入 | critical |
| `anchor_conflict` | 锚点冲突 | critical |
| `jitter_too_high` | 抖动过大 | warning |
| `insufficient_anchors` | 锚点不足 | info |
| `sync_issue` | 同步问题 | warning |

## 校准算法详解

### 延迟计算

1. **事件分组**：将所有事件按时间戳聚类，时间差在 100ms 内的视为同一时刻的事件组
2. **主时钟选择**：优先使用用户指定的主时钟，否则选择事件最多的源
3. **证据收集**：对每个源，收集与主时钟事件的时间差作为延迟证据
4. **异常值过滤**：使用 IQR 方法过滤异常值
5. **加权平均**：按证据类型的权重计算平均延迟

### 漂移检测

使用线性回归检测时钟漂移：

```
漂移率 (PPM) = (斜率 - 1) * 1,000,000
```

- 正值：该源时钟比主时钟快
- 负值：该源时钟比主时钟慢
- 阈值：超过 ±100 PPM 视为显著漂移

### 抖动计算

```
抖动 = 事件间隔的标准差
```

- 高抖动（> 50ms）可能导致校准不稳定
- 抖动过大的源会被标记问题

## 常见问题

### Q: 为什么校准结果置信度低？

可能原因：
- 该源的事件数量太少（< 3个）
- 事件之间的延迟差异太大
- 存在较多异常值

解决方法：
- 添加更多事件（拍手峰值、人工锚点）
- 检查事件时间戳是否正确
- 使用手动覆盖功能

### Q: 如何添加自己的数据？

有两种方式：
1. **手动添加**：
   - 点击「➕ 添加源」创建输入源
   - 点击「➕ 添加锚点」添加人工标记点
   
2. **导入数据**：
   - 准备符合格式的 JSON 或 CSV 文件
   - 使用「📥 导入」功能导入会话

### Q: 时间戳单位是什么？

默认使用毫秒 (ms)。导入时可以指定其他单位，但系统内部统一转换为毫秒处理。

### Q: 主时钟源有什么作用？

主时钟源是延迟计算的参考基准：
- 所有其他源的延迟都是相对于主时钟计算的
- 主时钟源的延迟始终为 0
- 建议选择事件最多、最稳定的源作为主时钟
