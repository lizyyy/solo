# 游泳池换热负荷系统

可追溯的换热负荷计算与审核流程管理系统

## 核心设计原则

> 结论看着很满不可怕，追证据时断在半路才可怕。

本系统的核心设计目标是**可追溯性**，而非单纯的计算功能。每一个换热负荷数值都必须能追溯到原始证据。

---

## 边界规则（必须严格遵守）

### 1. 传感器重启编号变化处理

#### 判定规则
- **触发条件**：传感器物理ID相同，但当前编号与历史编号不一致
- **判定方法**：通过 `physicalId`（物理唯一标识）+ `时间戳` 进行双重追溯
- **历史查询**：调用 `Sensor.getNumberAtTime(timestamp)` 获取指定时间点的有效编号

#### 修改流程
```
检测到编号变化 → 自动记录历史编号 → 标记异常 → 触发安全员复核
     ↓
  不许自动归正常，必须等待人工确认
```

#### 回滚机制
- 支持将传感器编号回滚到任意历史版本
- 回滚操作会记录到修改历史，不可删除
- 回滚后需重新走审核流程

### 2. 工况照片防重复导入

#### 判定规则
- **去重键**：`SHA256文件哈希 + 拍摄时间戳`
- **重复判定**：相同哈希+相同时间戳视为同一张照片
- **批量导入**：同一批次导入自动跳过重复项，不报错

#### 处理结果
```javascript
{
  imported: [/* 成功导入列表 */],
  duplicates: [/* 被跳过的重复项 */],
  errors: [/* 导入失败项 */]
}
```

### 3. 巡检备注版本追踪

#### 修改历史
- 每次修改自动递增版本号
- 保留所有历史版本的内容、修改人、修改时间
- 支持查看任意两个版本的行级差异

#### 回滚操作
- 可回滚到任意历史版本
- 回滚本身也算一次新版本（vN → vN+1）
- 回滚记录标记 `isRollback: true`

## 三步审核工作流

### 工作流图示
```
    ┌─────────────────┐
    │   Step 1: 草稿   │  操作员创建记录，上传工况照片
    │  workflowStep=1  │
    └────────┬────────┘
             │ 提交审核
             ▼
    ┌─────────────────┐
    │ Step 2: 工程审核 │  设备工程师何工补看手写巡检备注
    │  workflowStep=2 │
    └────────┬────────┘
             │
     ┌───────┴───────┐
     │ 有传感器重启？ │
     └───┬───────┬───┘
  是  │       │  否
     ▼       ▼
┌─────────┐  ┌─────────┐
│ Step 3: │  │ Step 4: │
│ 安全复核 │  │  完成   │
│ 安全员  │  │         │
└────┬────┘  └─────────┘
     │ 复核通过
     ▼
┌─────────┐
│ Step 4: │
│  完成   │
└─────────┘
```

### 各阶段权限

| 阶段 | workflowStep | 可操作角色 | 主要操作 |
|------|--------------|------------|----------|
| 草稿 | 1 | 创建人、管理员 | 编辑数据、上传照片、提交审核 |
| 工程审核 | 2 | 工程师、管理员 | 审核通过/驳回、补充备注 |
| 安全复核 | 3 | 安全员、管理员 | 复核通过/驳回、添加安全提醒 |
| 完成 | 4 | 仅查看 | 不可修改，只读 |

### 关键约束

1. **传感器重启时必须走安全复核**：
   - 工程审核阶段检测到传感器重启记录，自动进入第三步
   - 不许跳过安全复核直接完成

2. **完成后不可修改**：
   - workflowStep = 4 的记录冻结
   - 如需修改，需创建新版本重新走流程

3. **修改必须留痕**：
   - 所有状态变更记录到 `history` 数组
   - 包含：版本号、操作人、时间、变更描述

## 数据追溯设计

### 追溯链结构
```
换热负荷记录
    ├─→ 工况照片（photoIds）
    │     └─→ 拍摄时间、传感器编号、上传人
    ├─→ 巡检备注（noteIds）
    │     └─→ 传感器编号、手写内容、记录人、版本历史
    ├─→ 传感器数据
    │     └─→ 物理ID、编号历史、重启次数
    └─→ 修改历史
          └─→ 每一步的操作人、时间、变更原因
```

### 3D/图表展示约束

**服务复核优先，漂亮画面其次**：

1. 点击图表数据点必须能跳转至原始记录详情
2. 详情页必须展示完整证据链（照片、备注、传感器历史）
3. 传感器重启的数据点必须高亮标记（橙色）
4. 鼠标悬停必须显示关键信息

### API 追溯接口

```
GET /api/heat-loads/:id/evidence    # 获取完整证据链
GET /api/heat-loads/:id/history     # 获取修改历史
GET /api/sensors/physical/:id/history  # 获取传感器编号历史
GET /api/notes/:id/diff/:v1/:v2     # 备注版本差异对比
GET /api/photos/:id/trace           # 照片追溯信息
```

## 关键类与方法

### Sensor 传感器

```javascript
// 处理重启，自动记录历史编号
sensor.handleRestart(newNumber)

// 查询指定时间点的有效编号
sensor.getNumberAtTime(timestamp)
```

### InspectionNote 巡检备注

```javascript
// 更新内容，自动保存历史版本
note.updateContent(newContent, editor)

// 回滚到指定版本（生成新版本）
note.rollback(toVersion, editor)

// 获取两个版本的差异
note.getVersionDiff(v1, v2)
```

### HeatLoadRecord 换热负荷记录

```javascript
// 提交工程审核
record.submitForEngineeringReview(editor)

// 工程审核通过（检测到传感器重启自动进入安全复核）
record.engineerApprove(engineer, notes)

// 安全复核通过
record.safetyApprove(safetyOfficer, reminders)

// 获取完整证据链
record.getTraceableEvidence()
```

## 常见问题

### Q: 传感器重启后编号变了，旧数据怎么办？
A: 系统通过 `physicalId + 时间戳` 自动追溯，旧数据关联的是当时的编号，数据比对不受影响。

### Q: 重复导入照片会不会导致换热负荷数量翻倍？
A: 不会。系统通过 `SHA256哈希 + 时间戳` 去重，重复照片会被自动跳过。

### Q: 何工改了一条备注，怎么看改了什么？
A: 在备注详情页点击"查看版本差异"，系统会显示行级别的修改对比。

### Q: 为什么有些记录多了一步安全复核？
A: 因为该记录涉及的传感器有重启历史，按规则必须经过安全员复核。

### Q: 3D视图很好看，但我想知道原始数据在哪？
A: 点击3D视图中的闪烁传感器点，或点击图表中的数据点，可直接跳转到证据链页面。
