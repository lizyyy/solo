# 数据保留策略服务

## 项目概述

本服务用于管理高峰发票红冲记录与短信发送记录的数据保留策略，支持：
- 真实部门样例数据（非foo/bar）
- 三级审批流程（部门初审→财务复核→终审）
- 候选清单保护机制（清理/回滚必须先生成候选清单，避免误伤真实数据）
- 人工修正（保留系统判断，不覆盖，留痕）
- 报告口径变更（失败路径完整处理）
- 完整导出功能（短信发送清单修正前后值，按审批节点回查）
- SQLite持久化（本地重启后所有处理结论和材料摘要可查询）

## 技术栈

- **后端框架**: FastAPI
- **数据库**: SQLAlchemy + SQLite
- **数据验证**: Pydantic

## 主流程

### 数据保留策略执行流程

```
1. 数据导入（真实部门样例）
   ↓
2. 生成候选清单
   ↓ 系统自动判断：保留/清理，设置执行权限保护
3. 部门初审
   ↓
4. 财务复核
   ↓
5. 终审
   ↓ 仅终审通过后可执行，can_execute=True
6. 执行清理/回滚操作
   ↓
7. 保存处理结论和材料摘要
   ↓
8. 导出执行结果
```

### 关键步骤说明

1. **候选清单生成保护机制**
   - 所有清理/回滚操作必须先生成候选清单
   - 未通过三级审批的清单无法执行
   - 系统自动设置 `can_execute=False`，保护真实数据

2. **三级审批流程**
   - 部门初审 → 财务复核 → 终审
   - 每步审批留痕：审批人、时间、意见、状态
   - 全部通过后 `can_execute=True`，方可执行

3. **系统自动判断**
   - 高峰时段记录：保留（大型企业）
   - 非高峰时段记录：建议清理（小型企业/个体户）

4. **数据持久化**
   - 所有处理结论和材料摘要保存在SQLite数据库
   - 本地重启后所有记录可完整查询

## 失败路径：报告口径变更

### 场景描述

当上级部门调整报告口径时，需要对已生成的候选清单进行特殊处理。常见变更场景：
- 数据保留期限从3年改为5年
- 高峰时段定义调整
- 保留条件变化
- 合规要求变更

### 处理流程

```
1. 发现口径变更需求
   ↓
2. 触发口径变更API
   ↓
3. 系统自动：
   - 设置清单状态为 caliber_changed
   - 更新口径版本号
   - 设置 can_execute=False（禁止执行）
   - 记录变更原因
   ↓
4. 批量更新所有项目系统判断
   - 标记为"口径变更，需重新判断"
   - 强制设置 is_kept=True（全部保留，避免误删）
   ↓
5. 清单摘要追加变更记录
   ↓
6. 需重新生成候选清单（使用新口径）
```

### 变更影响验证

| 字段 | 变更前 | 变更后 | 说明 |
|------|--------|--------|------|
| approval_status | approved | caliber_changed | 审批状态重置 |
| caliber_version | V1.0 | V2.0 | 口径版本更新 |
| can_execute | True | False | 禁止执行，保护数据 |
| execution_status | executed | failed | 执行状态更新 |
| 系统判断 | 保留/清理 | 口径变更，需重新判断 | 所有项目统一更新 |
| is_kept | 按规则 | True | 全部强制保留 |

## 人工修正机制

### 核心规则

1. **不覆盖系统判断**
   - `system_decision` 字段保留原始值
   - 新增 `manual_decision` 字段记录人工判断
   - 系统判断与人工判断并存，可对比审计

2. **完整修改留痕**
   修改记录包含：
   - 原始值（`original_value`）
   - 修改后值（`modified_value`）
   - 修改人（`modifier`）
   - 修改时间（`modification_time`）
   - 修改备注（`modification_remark`）
   - 修改原因（`reason`）

3. **值变更标记**
   - 导出时自动标记 `value_modified=True/False`
   - 清晰展示哪些项目经过人工调整

4. **审批状态联动**
   - 人工修正后清单状态变更为 `manual_modified`
   - 需重新审批后方可执行

### 使用示例

```json
POST /manual-modify/
{
  "candidate_list_id": 1,
  "candidate_item_id": 3,
  "field_name": "final_value",
  "modified_value": "{\"invoice_no\":\"031002100011\",\"buyer_name\":\"人工修正后客户\"}",
  "modifier": "数据管理员",
  "modification_remark": "该客户为重要合作伙伴，特殊保留",
  "reason": "重要客户豁免"
}
```

## 导出功能

### 导出内容结构

```
├── 清单基本信息
│   ├── 名称、数据源、口径版本
│   ├── 审批状态、执行状态
│   ├── 材料摘要、创建时间
│
├── 项目详情（保留/清理标记）
│   ├── 原始值、建议值、最终值
│   ├── 系统判断、人工判断
│   ├── 值变更标记（value_modified）
│   ├── 动作类型（keep/clean/rollback）
│   └── 关联短信详情（短信发送清单）
│
├── 短信发送清单（修正前后对比）
│   ├── 批次号、手机号码、短信内容
│   ├── 发送时间、发送状态
│   ├── 发送部门、操作人
│   └── 关联发票号
│
├── 修改记录（完整留痕）
│   ├── 修改字段、修改人
│   ├── 原始值、修改后值
│   ├── 修改时间、修改备注
│   └── 修改原因
│
├── 审批历史（按节点回查）
│   ├── 部门初审
│   ├── 财务复核
│   └── 终审
│
└── 执行记录
    ├── 执行类型、执行人
    ├── 执行时间、执行状态
    ├── 成功/失败数量
    └── 执行摘要
```

### 按审批节点回查

```json
POST /export/
{
  "candidate_list_id": 1,
  "include_sms_details": true,
  "filter_by_node": "财务复核"  # 可指定仅查看某节点审批记录
}
```

### 导出关键验证点

1. ✅ **短信详情数量** - 所有关联短信完整导出
2. ✅ **修改记录数** - 所有人工修正可追溯
3. ✅ **值变更标记** - 清晰标识哪些项目被人工修改
4. ✅ **原始值保留** - 修正前的值完整保留
5. ✅ **修改后值** - 修正后的值完整保留
6. ✅ **审批历史完整** - 按节点回查各层级审批意见
7. ✅ **系统判断不覆盖** - 导出时可看到系统原始判断

| 方法 | 路径 | 说明 |
