# 政务材料预审 API 服务使用说明

## 一、项目概述

本服务是一个完整的政务材料预审 API 系统，以材料目录为入口，通过预审规则和补正任务推进业务流程，解决补正、退回和窗口受理状态混乱的问题。

### 核心设计理念

1. **材料目录作为入口**：所有业务从材料目录开始，明确需要提交哪些材料
2. **预审规则驱动**：每个材料关联预审规则，指导审核标准
3. **补正任务推进**：材料需要补正时，创建补正任务明确处理人和截止日期
4. **完整状态记录**：所有状态变更都有历史记录，可追溯
5. **失败可重试**：补正任务失败后可以重试，无需清库重来
6. **持久化存储**：使用 SQLite 轻量数据库，重启后历史数据不丢失

## 三、核心概念

### 1. 办件状态流转

```
草稿 ──提交──> 已提交 ──开始预审──> 预审中
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
                 需补正         已退回          窗口受理
                    │
                    └──补正完成──> 已补正──重新预审──> 预审中
```

**状态说明**：
- **草稿**：办件刚创建，材料上传中
- **已提交**：材料上传完成，提交预审，生成受理号
- **预审中**：审核人员正在审核材料
- **需补正**：部分材料需补正，进入补正流程
- **已补正**：所有补正任务完成，等待重新预审
- **已退回**：办件被退回，需重新提交
- **窗口受理**：所有材料审核通过，正式受理

### 2. 材料状态

- **已上传**：材料刚上传
- **预审中**：正在审核
- **通过**：审核通过
- **不通过**：审核不通过
- **需补正**：需要补充或修改
- **已补正**：补正完成

### 3. 补正任务状态

- **待处理**：任务已创建，未开始
- **处理中**：正在处理
- **已完成**：补正完成
- **失败**：处理失败，可重试

## 四、使用流程

### 场景1：正常办理流程（全部通过）

**步骤**：
1. 查看材料目录 → 了解需要什么材料
2. 创建办件 → 上传所需材料
3. 提交预审 → 生成受理号
4. 开始预审 → 审核人员介入
5. 审核材料 → 逐个标记通过
6. 窗口受理 → 全部通过后自动受理

**关键接口**：
```
GET    /api/v1/materials                    # 查看材料目录
POST   /api/v1/applications                 # 创建办件
POST   /api/v1/applications/submit          # 提交预审
POST   /api/v1/applications/{id}/start-review  # 开始预审
POST   /api/v1/materials/review             # 审核材料
GET    /api/v1/applications/{id}            # 查看办件详情
```

### 场景2：需补正流程（有材料需要修改）

**步骤**：
1. 正常创建、提交、开始预审
2. 审核发现部分材料需补正
3. 办件状态变为「需补正」
4. 创建补正任务（指定负责人、截止日期）
5. 处理补正任务 → 完成补正
6. 所有补正任务完成后，办件状态变为「已补正」
7. 重新开始预审 → 再次审核

**关键接口**：
```
POST   /api/v1/materials/review             # 标记材料需补正
POST   /api/v1/correction-tasks             # 创建补正任务
POST   /api/v1/correction-tasks/{id}/start  # 开始处理任务
POST   /api/v1/correction-tasks/{id}/complete # 完成任务
POST   /api/v1/applications/{id}/start-review  # 重新预审
```

### 场景3：任务失败重试

**步骤**：
1. 补正任务执行失败（如网络问题、系统错误）
2. 标记任务为「失败」状态，记录错误信息
3. 调用重试接口，任务恢复为「处理中」
4. 重新执行补正操作
5. 完成任务

**关键接口**：
```
POST   /api/v1/correction-tasks/{id}/fail   # 标记失败
POST   /api/v1/correction-tasks/retry       # 重试任务
```

### 场景4：办件退回

**步骤**：
1. 审核发现重大问题，无法通过补正解决
2. 选择退回原因（如不符合申请条件）
3. 填写详细退回说明
4. 办件状态变为「已退回」
5. 记录退回历史

**关键接口**：
```
GET    /api/v1/reject-reasons               # 查看退回原因列表
POST   /api/v1/applications/reject          # 退回办件
GET    /api/v1/applications/{id}/history    # 查看退回历史
```

### 场景5：办件查询和复查

**查询方式**：
1. 按受理号查询 → 精确查找
2. 按申请人查询 → 查看某人所有办件
3. 按状态筛选 → 查看某状态的所有办件
4. 查看历史记录 → 完整追溯

**关键接口**：
```
GET    /api/v1/applications/by-no/{no}      # 按受理号查询
GET    /api/v1/applications?applicant_name=张三  # 按申请人查询
GET    /api/v1/applications?status=预审中   # 按状态筛选
GET    /api/v1/applications/{id}/history    # 查看状态历史
GET    /api/v1/applications/summary         # 汇总统计
```

## 五、验收规则（用户应看到的内容）

### 1. 办件状态可视化

用户查看办件时，应能清楚看到：

**当前状态卡片**：
- 大字号显示当前状态（如「需补正」「预审中」）
- 当前所在步骤（如「材料补正」「窗口受理」）
- 受理号（提交后生成）
- 关键时间点（提交时间、受理时间等）

**状态流转历史**：
- 完整的状态变更时间线
- 每条记录包含：变更时间、原状态、新状态、变更原因、操作人
- 从创建到当前的完整轨迹

**材料状态列表**：
- 每个材料的单独状态
- 材料名称、审核结果、审核时间、审核人
- 哪些材料通过、哪些需补正一目了然

### 2. 补正任务管理

查看补正任务时，应能看到：

**任务详情**：
- 任务名称和补正内容（明确要做什么）
- 关联的材料（哪个材料需要补正）
- 负责人和截止日期
- 当前状态和重试次数

**失败任务处理**：
- 失败任务用醒目标记（如红色）
- 显示最后一次错误信息（便于定位问题）
- 提供「重试」按钮，点击即可恢复
- 记录重试历史（第几次重试）

**任务汇总**：
- 总数：待处理、处理中、已完成、失败
- 按负责人筛选（查看某人负责的任务）
- 按办件关联（查看某个办件的所有任务）

### 3. 查询和复查功能

查询时，应提供：

**多维度查询**：
- 按受理号精确查询（最常用）
- 按申请人姓名模糊查询
- 按业务类型筛选
- 按状态批量查看

**汇总统计**：
- 办件总数
- 各状态数量分布（草稿、已提交、预审中、需补正等）
- 补正任务汇总（待处理、处理中、已完成、失败）

**历史追溯**：
- 任何时间点都能查历史数据
- 重启服务后数据不丢失
- 可查看已完成、已退回的历史办件

### 4. 下一步指引

普通用户查看办件后，应明确知道下一步：

**状态对应的下一步**：
| 当前状态 | 用户应做什么 | 去哪里操作 |
|---------|-------------|-----------|
| 草稿 | 补充材料并提交 | 创建/修改办件 → 提交预审 |
| 已提交 | 等待预审 | 查看办件详情 → 等待审核 |
| 预审中 | 等待审核结果 | 查看办件详情 → 查看材料状态 |
| 需补正 | 处理补正任务 | 查看补正任务 → 处理失败重试 |
| 已补正 | 等待重新预审 | 查看办件详情 → 等待再次审核 |
| 已退回 | 根据退回原因重新申请 | 查看退回原因 → 重新创建办件 |
| 窗口受理 | 等待办结 | 查看办件详情 → 查看受理时间 |

**失败任务的下一步**：
- 看到「失败」标记 → 知道需要处理
- 查看错误信息 → 了解失败原因
- 点击重试 → 任务恢复处理中
- 多次重试失败 → 联系管理员

## 七、数据存储说明

### 数据库文件

使用 SQLite 轻量级数据库，文件位于：
```
pre_review.db
```

### 数据持久化

- 所有数据写入本地数据库文件
- 服务重启后数据完整保留
- 历史办件、状态记录、任务信息都可查询
- 无需额外配置数据库服务器

### 清库操作（慎用）

如需重新开始，删除数据库文件即可：
```bash
rm pre_review.db
```

然后重新初始化：
```bash
python init_data.py
```

## 八、常见问题

### Q1: 补正任务失败了怎么办？
A: 不需要清库，调用重试接口即可：
```
POST /api/v1/correction-tasks/retry
Body: {"task_id": 1}
```

### Q2: 怎么查某个办件的完整历史？
A: 调用状态历史接口：
```
GET /api/v1/applications/{id}/history
```

### Q3: 受理号是怎么生成的？
A: 格式为：前缀 + 日期 + 6位序号
示例：YW20260510000001
每天从 000001 开始计数

### Q4: 如何快速定位混乱的状态？
A: 
1. 先看办件详情 → 了解当前状态
2. 查看状态历史 → 了解怎么到的当前状态
3. 查看材料列表 → 看哪些材料有问题
4. 查看补正任务 → 看有什么待处理

### Q5: 服务重启后数据还在吗？
A: 是的，所有数据保存在 `pre_review.db` 文件中，重启不丢失。
