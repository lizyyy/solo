# 贷款展期审批服务 - 自然语言验收点

## 一、主流程验收点

### 1. 展期申请提交流程

**验收点 1.1：成功提交展期申请**
- 当我为一个状态为「ACTIVE」且「未达展期次数上限」的贷款账户提交展期申请时
- 系统应该：
  1. 生成唯一的展期申请编号（格式：EXT + 时间戳 + 随机数）
  2. 自动执行所有规则检查（账户状态、展期次数、展期期限、无待处理申请等）
  3. 将申请状态设置为「PENDING（待初审）」
  4. 生成并保存规则检查快照（包含所有检查项的详细结果）
  5. 记录审计日志（操作类型：SUBMIT，操作人、操作时间、前后状态）

**验收点 1.2：申请状态流转正确性**
- 当我依次完成「提交申请 → 初审通过 → 终审通过 → 执行展期」的完整流程时
- 系统应该依次将申请状态变更为：
  PENDING → FIRST_APPROVED → FINAL_APPROVED → EXECUTING → EXECUTED
- 并且每个状态变更都应该在「审批历史」表中记录完整的审批轨迹

### 2. 还款计划重算流程

**验收点 2.1：展期后还款计划版本管理**
- 当展期申请终审通过并执行后
- 系统应该：
  1. 基于剩余本金和展期月数重新计算等额本息还款计划
  2. 新计划的版本号应该比原计划大1
  3. 原计划的状态应该变为「REPLACED（已替换）」且 is_current 为 false
  4. 新计划的 is_current 应该为 true 且状态为「ACTIVE」
  5. 贷款账户的 current_repayment_plan_id 应该指向新计划
  6. 两个计划的变更历史都应该记录在 RepaymentPlanHistory 表中

**验收点 2.2：还款计划计算准确性**
- 当我为一笔剩余本金 100,000 元、年利率 6%、展期 12 个月的贷款执行展期时
- 系统生成的新还款计划应该满足：
  1. 共有 12 期还款
  2. 每期还款金额约为 8,606.64 元（等额本息公式计算结果）
  3. 12 期本金之和应该精确等于剩余本金 100,000 元
  4. 所有金额都应该四舍五入到小数点后2位

### 3. 罚息快照流程

**验收点 3.1：终审时自动生成罚息快照**
- 当展期申请进入终审环节时
- 系统应该：
  1. 自动计算截至当前时间的逾期本金、逾期利息和逾期天数
  2. 按照罚息利率（默认日利率 0.05%）计算罚息金额
  3. 生成罚息快照并关联到展期申请
  4. 快照中应该包含详细的罚息计算明细（逾期本金罚息、逾期利息罚息）
  5. 罚息快照的状态初始为未结清（settled = false）

**验收点 3.2：罚息金额计算正确性**
- 当某笔贷款有逾期本金 50,000 元、逾期利息 1,000 元、逾期 30 天时
- 系统计算的罚息金额应该为：
  逾期本金罚息 = 50,000 × 0.05% × 30 = 750 元
  逾期利息罚息 = 1,000 × 0.05% × 30 = 15 元
  合计罚息 = 765 元

## 二、异常场景验收点

### 4. 规则校验异常

**验收点 4.1：展期次数超限拒绝**
- 当我为一个已展期 2 次且 max_extension_count = 2 的账户提交展期申请时
- 系统应该：
  1. 返回明确的错误信息：「已展期次数已达上限：2/2」
  2. 不创建展期申请记录
  3. 在审计日志中记录失败的申请尝试（operation_result = FAILED）
  4. 贷款账户状态保持不变

**验收点 4.2：账户状态非法拒绝**
- 当我为一个状态为「PAID_OFF（已结清）」或「FROZEN（已冻结）」的账户提交展期申请时
- 系统应该拒绝申请并说明具体原因

**验收点 4.3：存在待处理申请时拒绝**
- 当某个贷款账户已有一个状态为「PENDING」或「FIRST_APPROVED」的展期申请时
- 我再次为该账户提交新的展期申请时
- 系统应该拒绝并提示：「当前有待处理的展期申请」

### 5. 审批流程异常

**验收点 5.1：状态机保护 - 初审后才能终审**
- 当我尝试对一个状态为「PENDING」的申请直接执行终审操作时
- 系统应该拒绝并提示：「申请状态不允许终审」

**验收点 5.2：驳回操作的可逆性**
- 当我对一个状态为「PENDING」或「FIRST_APPROVED」的申请执行驳回操作时
- 系统应该：
  1. 将申请状态设置为「REJECTED」
  2. 记录驳回人、驳回时间和驳回原因
  3. 在审批历史中记录完整的驳回轨迹
  4. 该申请后续不能再进行任何审批或执行操作

**验收点 5.3：撤销操作的适用范围**
- 当我尝试对一个状态为「EXECUTED」或「REJECTED」的申请执行撤销操作时
- 系统应该拒绝并提示：「申请状态不允许撤销」
- 只有状态为「PENDING」或「FIRST_APPROVED」的申请才能被撤销

### 6. 数据一致性异常

**验收点 6.1：执行展期失败时的状态回滚**
- 当展期执行过程中发生异常（如数据库连接失败）时
- 系统应该：
  1. 自动回滚所有数据库事务
  2. 将申请状态设置为「EXECUTE_FAILED」
  3. 记录详细的错误信息到 execution_error 字段
  4. 贷款账户状态和还款计划保持不变
  5. 在审计日志中记录失败的执行尝试

**验收点 6.2：乐观锁并发控制**
- 当两个用户同时对同一个贷款账户的版本进行更新时
- 系统应该：
  1. 只允许第一个更新成功
  2. 第二个更新应该失败并提示「数据版本不匹配」
  3. 防止出现脏写和数据不一致

## 三、数据一致性验收点

### 7. 账户与计划一致性

**验收点 7.1：执行成功后账户状态同步**
- 当展期申请执行成功后
- 我查询贷款账户时应该看到：
  1. extension_count 比执行前增加 1
  2. current_maturity_date 应该等于新还款计划的 end_date
  3. status 应该变为「EXTENDED（已展期）」
  4. current_repayment_plan_id 应该指向新计划
  5. version 应该递增

**验收点 7.2：还款计划与账户的双向关联**
- 贷款账户的 current_repayment_plan_id 应该始终指向一个 is_current = true 的还款计划
- 同时，该还款计划的 is_current 必须为 true 且 loan_account_id 应该匹配

### 8. 额度管理一致性

**验收点 8.1：展期执行后的额度占用更新**
- 当展期申请执行成功后
- 系统应该：
  1. 在 CreditLimitRecord 表中记录一条类型为「EXTEND」的额度变更记录
  2. 变更金额 = 剩余本金 × 展期月数 ÷ 12
  3. before_used + change_amount 应该等于 after_used
  4. before_limit - change_amount 应该等于 after_limit
  5. 记录应该关联到对应的展期申请

**验收点 8.2：额度记录的完整性**
- 每一笔额度变更都应该有完整的前后快照
- 通过额度历史记录，应该能够追溯任意时间点的客户可用额度和已用额度

### 9. 审计追踪完整性

**验收点 9.1：所有关键操作都有审计记录**
- 当我执行以下任一操作时：提交申请、初审、终审、执行、驳回、撤销
- 系统应该在 AuditLog 表中记录：
  1. 操作类型和业务类型
  2. 操作人 ID 和姓名
  3. 操作时间
  4. 操作前后的数据快照（JSON 格式）
  5. 操作结果（成功/失败）
  6. 失败时的错误信息

**验收点 9.2：审批历史的完整性**
- 对于一个完整执行的展期申请
- ApprovalHistory 表中应该至少有 3 条记录：
  1. 提交申请（SUBMIT）
  2. 初审通过（FIRST_APPROVE）
  3. 终审通过（FINAL_APPROVE）
  4. 执行成功（EXECUTE）
- 每条记录都应该包含：操作阶段、操作人、操作时间、前后状态、规则检查结果

### 10. 对账与可复查性

**验收点 10.1：规则检查可复查**
- 当我查看任意一个展期申请的详情时
- 我应该能够看到：
  1. 提交时的所有规则检查结果（通过/不通过，原因说明）
  2. 每个规则检查的详细参数（如：展期次数 1/2，展期月数 3/6）
  3. 规则检查时的贷款账户快照（用于复查当时的状态）
- 这些信息应该持久化存储，而不是临时计算的

**验收点 10.2：对账数据导出**
- 当我请求导出「展期申请对账」Excel 时
- 导出的文件应该包含：
  1. 申请编号、贷款账号、客户名称
  2. 展期月数、展期原因
  3. 申请状态、各环节时间（申请、初审、终审、执行）
  4. 审批次数、罚息金额
  5. 驳回原因（如适用）
- 数据应该与数据库中的实际记录完全一致

**验收点 10.3：数据一致性自检**
- 当我调用数据一致性检查接口时
- 对于一个已执行成功的展期申请
- 系统应该验证：
  1. 贷款账户的 extension_count 等于实际执行的展期次数
  2. 新还款计划的 is_current = true
  3. 贷款账户的 current_repayment_plan_id 等于新计划的 ID
  4. 至少存在一条罚息快照
  5. 审批历史记录数量符合预期
- 所有检查项都应该通过

## 四、后台任务验收点

### 11. 任务执行与重试

**验收点 11.1：任务状态追踪**
- 当我创建一个「执行展期」的后台任务时
- 系统应该：
  1. 在 TaskRecord 表中创建任务记录
  2. 初始状态为「PENDING」
  3. 记录任务参数（application_no）
  4. 记录预期执行时间

**验收点 11.2：任务失败与自动重试**
- 当后台任务执行失败时
- 系统应该：
  1. 将任务状态设置为「RETRYING」或「MAX_RETRY_EXCEEDED」
  2. 记录详细的错误信息和堆栈跟踪
  3. 如果重试次数未达上限，设置下次执行时间（指数退避：60s, 120s, 180s...）
  4. 记录首次错误时间和最近错误时间
  5. 记录执行次数

**验收点 11.3：任务手动重试**
- 当一个任务状态为「FAILED」或「MAX_RETRY_EXCEEDED」时
- 我调用重试接口后
- 系统应该：
  1. 将任务状态重置为「PENDING」
  2. 清空错误信息
  3. 重置执行计数为 0
  4. 设置下次执行时间为当前时间
- 任务可以重新执行

**验收点 11.4：任务执行结果持久化**
- 当任务执行成功或失败后
- 我查询任务状态时应该看到：
  1. 最终状态（SUCCESS / FAILED / MAX_RETRY_EXCEEDED）
  2. 执行次数
  3. 上次执行时间
  4. 成功时的执行结果（JSON）
  5. 失败时的错误信息

## 五、边界情况验收点

### 12. 特殊场景处理

**验收点 12.1：零剩余本金**
- 当我为一笔剩余本金为 0 的贷款账户提交展期申请时
- 系统应该拒绝并提示：「贷款没有剩余本金可展期」

**验收点 12.2：展期月数为零或负数**
- 当我提交展期月数为 0 或 -3 的申请时
- 系统应该拒绝并提示：「展期月数必须大于 0 且不超过最大限制」

**验收点 12.3：罚息为零的情况**
- 当贷款没有任何逾期时
- 终审时生成的罚息快照应该：
  1. 逾期本金 = 0
  2. 逾期利息 = 0
  3. 逾期天数 = 0
  4. 罚息金额 = 0
  5. 快照仍然被创建（用于记录「无罚息」的事实）

**验收点 12.4：申请详情的完整性**
- 当我查询任意一个展期申请的详情时
- 响应应该包含：
  1. 申请基本信息
  2. 完整的审批历史（所有审批操作）
  3. 规则检查结果（所有检查项）
  4. 罚息快照（如存在）
  5. 各环节的操作人、操作时间
- 不需要阅读源码就能了解申请的完整生命周期

## 六、日志与可观测性验收点

### 13. 日志完整性

**验收点 13.1：操作日志可读**
- 当我查看审计日志时
- 不需要理解代码实现就能看懂：
  1. 谁在什么时间做了什么操作
  2. 操作前后的数据变化
  3. 操作成功还是失败
  4. 失败的原因是什么

**验收点 13.2：历史数据可追溯**
- 对于任意一个已执行的展期申请
- 我应该能够通过查询历史数据回答：
  1. 申请时的贷款账户状态是什么？
  2. 审批时的规则检查结果是什么？
  3. 展期前后的还款计划有什么变化？
  4. 罚息是怎么计算出来的？
  5. 额度占用是如何变化的？
- 这些答案应该能从数据库表中直接获取，而不是靠代码推断
