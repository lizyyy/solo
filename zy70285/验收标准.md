# 巡店问题台 - 验收标准

## 一、系统概述

本系统解决"巡店问题、整改照片和复查意见散落在群里，总部难追踪"的业务痛点。

**核心验证模块**：
1. 门店档案验证 - 确认门店是否可接受巡店
2. 巡店问题可靠检测 - 确认巡店数据完整可靠
3. 整改任务一致性校验 - 确认整改与原始数据对得上

---

## 二、验收场景

### 场景1：正常处理（通过）

当验证结果满足以下条件时，代表通过验收：

```json
{
  "passed": true,
  "score": 85,
  "errors": [],
  "currentBlock": null
}
```

**判定标准**：
- ✅ `passed = true`
- ✅ `score >= 80`
- ✅ `errors` 数组为空
- ✅ 无 `currentBlock`（卡点）

**界面表现**：
- 绿色背景的"通过"标签
- 绿色进度条（>=80%）
- 无错误列表显示

---

### 场景2：失败原因

当验证失败时，需要人工处理：

```json
{
  "passed": false,
  "score": 30,
  "errors": [
    "门店状态为\"inactive\"，不是激活状态",
    "门店未获得巡店授权"
  ],
  "currentBlock": "门店档案验证失败",
  "suggestions": [
    "请在门店管理中将门店状态调整为\"active\"",
    "请在门店管理中开启巡店授权"
  ]
}
```

**判定标准**：
- ❌ `passed = false`
- ❌ `score < 50`（严重问题）
- ❌ `errors` 数组非空
- ❌ 有 `currentBlock`（指明卡点位置）

**界面表现**：
- 红色背景的"未通过"标签
- 红色进度条（<50%）
- 橙色"卡点"提示框
- 红色错误列表
- 蓝色处理建议列表

---

### 场景3：修正后重跑

存在警告或修正失败后，可重新验证：

```json
{
  "passed": true,
  "score": 70,
  "errors": [],
  "warnings": [
    "门店地址未填写",
    "门店负责人未指定"
  ],
  "suggestions": [
    "建议补充完整的门店信息"
  ]
}
```

**判定标准**：
- 🔄 `warnings` 数组非空（建议改进）
- 🔄 `50 <= score < 80`（可改进空间）
- 🔄 根据 `suggestions` 修正后重新验证

**界面表现**：
- 黄色进度条（50%-80%）
- 黄色警告列表
- 验证历史记录追踪每次运行结果

---

## 三、三种验证模块详解

### 3.1 门店档案验证

**验证内容**：
| 检查项 | 权重 | 通过标准 | 失败原因 |
|--------|------|----------|----------|
| 门店存在 | - | 必须存在 | "门店不存在" |
| 状态激活 | 40分 | `status = 'active'` | "门店状态非激活" |
| 已授权 | 30分 | `authorized = true` | "门店未获得巡店授权" |
| 名称存在 | 15分 | 非空 | "门店名称为空" |
| 编码存在 | 15分 | 非空 | "门店编码为空" |
| 地址完整 | 5分 | 非空（警告） | "门店地址未填写"（警告） |
| 负责人 | 5分 | 非空（警告） | "门店负责人未指定"（警告） |

**通过分数**：>= 80分（状态+授权必须通过）

---

### 3.2 巡店记录可靠性验证

**验证内容**：
| 检查项 | 权重 | 通过标准 | 失败原因 |
|--------|------|----------|----------|
| 巡店人 | 20分 | 非空 | "未指定巡店人" |
| 巡店日期 | 20分 | 非空 | "未填写巡店日期" |
| 现场照片 | 30分 | 至少1张 | "巡店记录没有任何现场照片" |
| 问题照片 | 20分 | 每个问题至少1张 | "X个问题缺少佐证照片" |
| 问题描述 | 5分 | >=5字（警告） | "部分问题描述过于简略"（警告） |
| 问题数量 | 10分 | >0（警告） | "未发现任何问题"（警告） |

**通过分数**：>= 80分

---

### 3.3 整改任务一致性校验

**验证内容**：
| 检查项 | 权重 | 通过标准 | 失败原因 |
|--------|------|----------|----------|
| 整改记录 | 40分 | 必须存在 | "问题尚未提交整改记录" |
| 整改照片 | 30分 | 至少1张 | "整改记录缺少整改后照片" |
| 照片数量 | 10分 | >=原始问题（警告） | "整改照片少于原始照片"（警告） |
| 整改描述 | 5分 | >=10字（警告） | "整改描述过于简略"（警告） |
| 整改人 | 5分 | 非空（警告） | "整改人未填写"（警告） |
| 复查意见 | 10分 | 存在（警告） | "尚未提交复查意见"（警告） |

**通过分数**：>= 80分

## 四、业务状态流转

### 状态定义

| 实体类型 | 状态 | 说明 |
|----------|------|------|
| 门店 | active | 激活，可接受巡店 |
| 门店 | inactive | 停用，不可巡店 |
| 巡店记录 | pending | 待提交验证 |
| 巡店记录 | submitted | 已验证通过，问题已生成 |
| 问题 | pending | 待整改 |
| 问题 | rectified | 已整改，待复查 |
| 问题 | completed | 复查通过，问题关闭 |
| 问题 | rejected | 复查驳回，需重新整改 |

### 流转路径

```
门店档案验证 → 巡店记录 → 提交验证 → 生成问题
     ↓              ↓              ↓
  (active)     (可靠检测)     (一致性校验)
                                    ↓
                           整改提交 → 复查意见
                                    ↓
                           复查通过/驳回
```

## 五、前端展示元素

每个验证结果页面包含以下元素：

1. **验证状态标签** - 绿色✓通过 / 红色✗未通过
2. **评分进度条** - 绿(>=80) / 黄(50-80) / 红(<50)
3. **当前卡点** - 橙色边框提示当前阻塞点
4. **错误列表** - 红色圆点，必须修复
5. **警告列表** - 黄色圆点，建议改进
6. **处理建议** - 蓝色圆点，指导下一步操作
7. **历史追踪** - 状态变更时间线 + 验证记录

## 六、API 接口

### 验证接口

```
POST /api/validate/store/:id     # 门店档案验证
POST /api/validate/inspection/:id # 巡店可靠性验证
POST /api/validate/problem/:id   # 整改一致性验证
```

### 统一返回格式

```json
{
  "passed": true | false,
  "score": 0-100,
  "errors": ["具体错误1", "具体错误2"],
  "warnings": ["警告1", "警告2"],
  "suggestions": ["建议1", "建议2"],
  "currentBlock": "卡点描述" | null
}
```

### 历史查询

```
GET /api/history/:entityType/:entityId
```

返回：
- `statusHistory` - 状态变更时间线
- `validationHistory` - 每次验证的完整记录
