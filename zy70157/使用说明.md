# 批任务补偿窗口 API - 使用说明

## 功能概述

这是一个批任务失败后的补跑窗口管理系统，提供以下核心能力：

1. **任务实例管理** - 创建和查询任务实例
2. **依赖图管理** - 定义和校验任务依赖关系
3. **补跑申请流程** - 申请、审批、执行补跑
4. **重入锁机制** - 防止并发重入导致状态混乱
5. **跳过规则** - 灵活配置补跑跳过条件
6. **执行报告** - 记录每次执行详情，影响最终结果
7. **异常记录** - 边界数据不静默吞掉，可查询的异常列表

## 快速开始

### 1. 安装依赖

```bash
pip install -r requirements.txt
```

### 2. 启动服务

```bash
python -m uvicorn app.main:app --reload
```

服务启动后访问：
- API 文档: http://localhost:8000/docs
- 健康检查: http://localhost:8000/health

### 3. 运行测试脚本验证功能

```bash
python test_batch_retry.py
```

## 普通用户验证步骤

照着以下步骤走，你就能知道功能是否可用：

### 第一步：确认服务是否启动

**操作**：访问 http://localhost:8000/health

**期望结果**：返回 `{"status": "healthy", "service": "batch-retry-api"}`

**下一步该查**：如果没返回，检查终端是否有报错，Python 版本是否 >= 3.8

---

### 第二步：创建一个批作业

**操作**：用 POST 调 `http://localhost:8000/api/jobs`

请求体示例：
```json
{
  "id": "MY_DAILY_JOB",
  "name": "每日数据同步",
  "retry_window_hours": 24,
  "max_retries": 3,
  "is_active": true
}
```

**期望结果**：返回 200，包含 `id: "MY_DAILY_JOB"`

**下一步该查**：看响应里的 `retry_window_hours` 是否是你设置的值

---

### 第三步：创建任务实例

**操作**：用 POST 调 `http://localhost:8000/api/task-instances`

请求体示例：
```json
{
  "id": "TASK_001",
  "job_id": "MY_DAILY_JOB",
  "task_name": "extract_data",
  "business_date": "2026-05-10",
  "max_retries": 3
}
```

**期望结果**：返回 200，status 为 `pending`

**下一步该查**：用 GET 调 `/api/task-instances/TASK_001` 确认创建成功

---

### 第四步：模拟任务失败（测试补跑）

**操作**：用 POST 调 `http://localhost:8000/api/task-instances/TASK_001/fail`

参数：`error_message=测试失败`

**期望结果**：返回 `{"status": "failed", "retry_count": 1}`

**下一步该查**：再查任务详情，确认 status 变成 `failed`

---

### 第五步：检查补跑窗口

**操作**：用 GET 调 `http://localhost:8000/api/task-instances/TASK_001/check-window`

**期望结果**：
```json
{
  "is_within_window": true,
  "reason": "在补跑窗口内"
}
```

**下一步该查**：如果返回 false，看 reason 字段说明原因，可能是任务创建时间超出窗口

---

### 第六步：检查重入锁

**操作**：用 GET 调 `http://localhost:8000/api/task-instances/TASK_001/check-reentrancy`

**期望结果**：
```json
{
  "can_acquire": true,
  "reason": "可以获取锁"
}
```

**下一步该查**：如果 false，看 existing_lock 字段，说明有其他进程持有锁

---

### 第七步：创建补跑申请

**操作**：用 POST 调 `http://localhost:8000/api/retry-requests`

请求体示例：
```json
{
  "task_instance_id": "TASK_001",
  "requester": "your_name",
  "reason": "任务失败需要补跑",
  "target_retry_count": 3,
  "skip_rules": {
    "skip_if_already_succeeded": true,
    "skip_if_retry_count_exceeded": true
  }
}
```

**期望结果**：返回 200，status 为 `pending`

**下一步该查**：记录返回的 `id` 字段（以 RETRY_ 开头），后面要用

---

### 第八步：校验补跑条件（预览）

**操作**：用 POST 调 `http://localhost:8000/api/retry-requests/{你的申请ID}/validate`

**期望结果**：
```json
{
  "is_valid": true,
  "errors": [],
  "warnings": []
}
```

**下一步该查**：如果有 errors，看具体错误信息，比如依赖没满足、窗口过期等

---

### 第九步：审批补跑申请

**操作**：用 POST 调 `http://localhost:8000/api/retry-requests/{你的申请ID}/approve`

请求体：
```json
{
  "approved_by": "admin_user"
}
```

**期望结果**：status 变成 `approved`

**下一步该查**：再查申请详情，确认 approved_by 和 approved_at 有值

---

### 第十步：执行补跑

**操作**：用 POST 调 `http://localhost:8000/api/retry-requests/{你的申请ID}/execute`

请求体：
```json
{
  "task_instance_id": "TASK_001",
  "executor_id": "your_executor"
}
```

**期望结果**：
```json
{
  "success": true,
  "status": "success"
}
```

**下一步该查**：
1. 再查任务详情，status 应该变成 `success`
2. 看 `/api/task-instances/TASK_001/reports` 有执行报告

---

### 第十一步：查看执行报告

**操作**：用 GET 调 `http://localhost:8000/api/task-instances/TASK_001/reports`

**期望结果**：至少有一条记录，包含：
- `status: "success"`
- `affected_final_result: true`
- `execution_sequence: 1`

**下一步该查**：看 output_snapshot 字段，确认执行结果被记录

---

### 第十二步：查看异常记录

**操作**：用 GET 调 `http://localhost:8000/api/exceptions?resolved=false`

**期望结果**：如果测试中没有错误，应该是空数组

**下一步该查**：如果有记录，看 exception_type 和 details 字段

---

## 常见问题排查

### Q: 补跑校验失败，提示"重试次数已达上限"
**查哪里**：
1. 看任务详情的 `retry_count` 和 `max_retries`
2. 看补跑申请的 `target_retry_count`
3. 异常记录里会有对应条目

### Q: 依赖检查不通过
**查哪里**：
1. 用 `/api/dependencies/{job_id}` 查看依赖图
2. 用 `/api/task-instances/{id}/check-dependencies` 看具体哪些前置任务失败

### Q: 重入锁获取失败
**查哪里**：
1. 用 `/api/task-instances/{id}/check-reentrancy` 看锁被谁持有
2. 检查是否有执行中的补跑请求

### Q: 执行报告显示 skipped
**查哪里**：
1. 看 `skip_reason` 字段
2. 检查补跑申请的 `skip_rules` 配置
3. 确认 `affected_final_result` 是否为 false（跳过不影响最终结果）

## 核心数据模型

- **BatchJob**：批作业定义，配置补跑窗口时长和最大重试次数
- **TaskInstance**：任务实例，记录每次执行的状态和结果
- **TaskDependency**：任务依赖关系，区分硬依赖和软依赖
- **RetryRequest**：补跑申请，包含跳过规则配置
- **ExecutionReport**：执行报告，记录每次执行的快照
- **ExceptionRecord**：异常记录，边界数据不静默吞掉

## 关键校验规则

1. **补跑窗口**：任务创建时间必须在窗口内（默认24小时）
2. **依赖校验**：硬依赖必须全部成功，软依赖失败不影响
3. **重入锁**：同一任务同一时间只能有一个执行
4. **重试次数**：不能超过任务配置的最大重试次数
5. **跳过规则**：可配置成功后跳过、次数超限跳过、前置失败跳过
