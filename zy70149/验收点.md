# 缓存预热编排 API - 验收点

本文档描述了系统在不同场景下的验收标准，采用自然语言描述，覆盖主流程、异常处理和数据一致性。

---

## 一、主流程验收点

### 1. 任务创建与执行
**场景**: 运营同学在大促前创建商品缓存预热任务并执行

**验收点**:
- 能成功创建预热任务，包含任务名称、数据源配置、缓存键格式
- 任务创建后能在任务列表中看到，状态可正常查询
- 点击开始执行后，任务状态变为 running
- 执行过程中能看到进度（成功数/失败数/总数）
- 执行完成后状态变为 success 或 partial/failed
- 通过 `/api/executions/{id}/report` 能看到完整预热报告

**报告应包含**:
- 执行耗时、成功/失败数量
- 缓存命中率数值
- 失败项列表（含错误信息）
- 命中预期与实际不匹配的项
- 完整的操作历史时间线

---

### 2. 数据版本管理
**场景**: 同一批商品数据需要在大促前多次预热验证

**验收点**:
- 每次执行自动生成版本号（可通过 version_strategy 配置策略）
- 使用 `force_version` 强制指定版本时，同一版本号可用于多次重跑
- 同一版本号 + 同一批数据：重跑时版本校验通过，不会报错
- 同一版本号 + 数据已变化：重跑时报错提示"版本冲突，数据不一致"
- 数据版本记录中包含校验和，可追溯当时数据的完整性

---

### 3. 并发与限速
**场景**: 预热时需要保护数据库和缓存服务不被打垮

**验收点**:
- 创建任务时可设置 `default_concurrency`（默认并发数）
- 启动执行时可覆盖设置 `concurrency`（本次并发数）
- 创建任务时可设置 `default_qps_limit`（默认 QPS 限制）
- 启动执行时可覆盖设置 `qps_limit`（本次 QPS 限制）
- 实际执行时并发数不会超过设置值
- 实际执行时 QPS 不会超过设置值（滑动窗口限流）
- 这些参数会记录在执行报告中，方便事后复盘

---

## 二、异常场景验收点

### 4. 失败隔离（单条失败不影响整体）
**场景**: 100 条商品数据预热，其中 2 条因网络抖动失败

**验收点**:
- 98 条成功的数据正常写入缓存，不受失败影响
- 2 条失败的数据状态标记为 failed，错误信息可查看
- 整体执行状态变为 partial（部分成功），而不是全部失败
- 失败项不会导致整个任务中断回滚
- 通过 `/api/executions/{id}/items?status=failed` 可筛选出所有失败项

---

### 5. 命中校验（预期 vs 实际）
**场景**: 验证预热数据是否真正写入了缓存

**验收点**:
- 预热前已存在的 key：`hit_expected = true`，预热后 `hit_actual = true`
- 预热前不存在的 key：`hit_expected = false`，预热后 `hit_actual = true`
- 如果某条数据预热成功但缓存中不存在（理论上不会发生但用于检测异常）：`hit_actual = false`
- 报告中 `hit_mismatch_count` 统计预期与实际不一致的数量
- 不一致的项会在报告的 `mismatch_items` 中列出，方便排查

---

### 6. 重试失败项
**场景**: 部分项预热失败，网络恢复后想重试

**验收点**:
- 调用 `/api/executions/{id}/retry` 重试所有失败项
- 只有状态为 failed 的项会被重试
- 重试成功的项状态变为 success，重试次数 +1
- 重试后如果全部成功，整体状态变为 success
- 重试操作会记录在历史中，包含"重试开始/完成"等动作

---

### 7. 补录指定失败项
**场景**: 只想补录特定几个失败的 key，不想全部重试

**验收点**:
- 调用 `/api/executions/{id}/patch`，传入指定的 cache_keys 列表
- 只有列表中且状态非 success 的项会被处理
- 不在列表中的失败项保持原样
- 补录操作记录在历史中，包含操作人（可选）和补录的 key 列表

---

## 三、数据一致性验收点

### 8. 撤回本次预热（避免带旧数据上线）
**场景**: 大促前预热了错的数据，需要紧急撤回

**验收点**:
- 调用 `/api/executions/{id}/rollback` 撤回本次预热
- 只有本次执行成功写入且**未被后续操作覆盖**的缓存会被删除
- 如果某条 key 在这次预热后又被其他执行覆盖，不会误删
- 撤回后执行状态变为 rolled_back
- 撤回操作记录在历史中，包含处理的缓存键数量

**可选模式**:
- 不指定目标：直接删除本次预热写入的缓存
- 指定 `target_execution_id`：仅回滚到该执行版本的状态（更安全）

---

### 9. 历史记录可追溯
**场景**: 大促后复盘，想知道谁在什么时候做了什么操作

**验收点**:
- 每次执行有完整的历史记录（execution_history 表）
- 历史记录包含：
  - 动作类型：create/start/complete/error/retry/patch/rollback 等
  - 动作详情：具体做了什么（可读的中文描述）
  - 操作人：可选，用于区分是谁操作的
  - 时间戳：精确到秒
- 通过报告接口的 `history` 字段可直接查看完整时间线
- 不需要读源码就能知道发生了什么

---

### 10. 同一批数据重跑稳定性
**场景**: 同一份数据源，连续运行两次预热

**验收点**:
- 使用相同的 `force_version` 重跑时：
  - 如果数据源未变，版本校验通过，可正常执行
  - 数据的校验和必须一致
- 不使用 force_version 时：
  - 每次会生成新版本号（根据策略：时间戳或校验和）
- 两次预热写入的缓存值应该一致（同一数据源）
- 旧值哈希和新值哈希都会记录，方便对比

---

## 四、API 可观测性验收点

### 11. 报告信息充足
**场景**: 通过 API 报告就能判断预热是否成功，无需查日志

**验收点**:
- 报告中的每个字段都有明确含义（见 Swagger 文档）
- `hit_rate` 直接给出命中率百分比
- `failed_items` 列出前 100 个失败项及错误信息
- `mismatch_items` 列出预期命中与实际不符的项
- `history` 按时间顺序列出所有操作
- 一眼就能看出：成功了吗？失败了多少？为什么失败？谁操作的？

---

### 12. 错误信息友好
**场景**: 操作出错时，能快速定位问题

**验收点**:
- 版本冲突时：明确提示"版本 X 已存在但数据不一致，现有校验和 vs 当前校验和"
- 任务不存在时：返回 404，提示"任务不存在"
- 正在执行中撤回时：提示"正在执行中的任务无法撤回"
- 数据源类型不存在时：提示"未知的数据源类型"
- 所有错误信息都是业务语言，不是技术堆栈（内部异常会记录日志）

## 五、快速使用示例

### 创建预热任务
```bash
curl -X POST http://localhost:8000/api/tasks \
  -H "Content-Type: application/json" \
  -d '{
    "task_name": "大促商品预热",
    "description": "预热大促期间的商品详情数据",
    "data_source_type": "mock",
    "data_source_config": "{\"items\": [{\"sku\": \"1001\", \"value\": {\"name\": \"商品A\", \"price\": 99}}, {\"sku\": \"1002\", \"value\": {\"name\": \"商品B\", \"price\": 199}}]}",
    "cache_key_pattern": "product:{sku}",
    "version_strategy": "timestamp_checksum",
    "default_concurrency": 10,
    "default_qps_limit": 50
  }'
```

### 启动预热
```bash
curl -X POST http://localhost:8000/api/tasks/1/start \
  -H "Content-Type: application/json" \
  -d '{
    "concurrency": 5,
    "qps_limit": 30,
    "force_version": "promo_2024_11_11_v1"
  }'
```

### 查看预热报告
```bash
curl http://localhost:8000/api/executions/1/report
```

### 撤回预热（发现数据错了）
```bash
curl -X POST http://localhost:8000/api/executions/1/rollback \
  -H "Content-Type: application/json" \
  -d '{"operator": "zhangsan@example.com"}'
```
