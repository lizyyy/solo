# 模型发布审批系统

一个简单易用的模型发布审批管理系统，解决模型从训练到上线的版本串问题。

## 核心设计理念

- **模型版本作为入口**：所有操作围绕具体的模型版本展开
- **评测结果推进状态**：评测通过才能进入审批
- **灰度审批作为必经环节**：先灰度观察，再正式发布
- **流量切换灵活调整**：灰度中可随时调整流量比例
- **回滚快速响应问题**：发现问题一键回滚
- **审计日志完整可追溯**：所有操作都有记录
- **重复操作智能处理**：重复调用要么安全忽略，要么明确提示

## 完整使用流程

### 步骤 1：创建模型版本

训练完成后，先在系统中注册模型版本。

**界面操作**：点击「+ 新建版本」，填写模型名称和版本号

**API 调用**：
```bash
curl -X POST http://localhost:8000/api/v1/models \
  -H "Content-Type: application/json" \
  -d '{
    "model_name": "推荐算法模型",
    "version": "v1.2.3",
    "description": "优化了用户冷启动策略"
  }'
```

**创建后状态**：待评测
**下一步提示**：请先提交评测结果

---

### 步骤 2：提交评测结果

评测人员对模型进行全面评测后提交结果。

**评测维度建议**：
- 准确率：模型预测的准确性
- 性能：响应时间、吞吐率
- 稳定性：异常率、资源消耗

**界面操作**：在模型详情页点击「提交评测」

**API 调用**：
```bash
curl -X POST http://localhost:8000/api/v1/models/1/evaluate \
  -H "Content-Type: application/json" \
  -d '{
    "evaluator": "张三",
    "accuracy_score": "96.5%",
    "performance_score": "92ms",
    "stability_score": "优秀",
    "overall_result": "通过",
    "findings": "冷启动场景下表现提升明显，边缘 case 覆盖率98%"
  }'
```

**评测通过后状态**：评测通过
**下一步提示**：请申请灰度审批

**评测不通过后状态**：评测不通过
**下一步提示**：请根据评测问题修复后重新提交评测

**重复调用处理**：已评测通过的版本再次提交会提示无需重复评测

---

### 步骤 3：灰度审批

评测通过后，需申请灰度审批。

**界面操作**：点击「灰度审批」，选择审批结论

**API 调用**：
```bash
curl -X POST http://localhost:8000/api/v1/models/1/approve \
  -H "Content-Type: application/json" \
  -d '{
    "approver": "李四",
    "approval_type": "灰度审批",
    "decision": "通过",
    "comments": "评测数据完备，同意进入灰度观察"
  }'
```

**审批通过后状态**：灰度中
**下一步提示**：灰度观察中，确认稳定后请申请正式发布审批

**审批驳回后状态**：审批驳回
**下一步提示**：请根据审批意见调整后重新申请审批

**重复调用处理**：已在灰度中的版本再次审批会提示无需重复

---

### 步骤 4：灰度观察与流量调整

灰度期间可根据实际情况调整流量比例。

**界面操作**：点击「调整流量」，设置流量比例

**API 调用**：
```bash
curl -X POST http://localhost:8000/api/v1/models/1/traffic \
  -H "Content-Type: application/json" \
  -d '{
    "operator": "王五",
    "traffic_weight": 30,
    "reason": "灰度第一天，先切30%流量观察"
  }'
```

**流量 100% 时**：自动标记为正式生产

**重复调用处理**：设置相同流量比例会提示无需重复切换

---

### 步骤 5：正式发布审批

灰度观察确认稳定后，申请正式发布。

**界面操作**：点击「正式发布审批」

**API 调用**：
```bash
curl -X POST http://localhost:8000/api/v1/models/1/approve \
  -H "Content-Type: application/json" \
  -d '{
    "approver": "赵六",
    "approval_type": "正式发布审批",
    "decision": "通过",
    "comments": "灰度3天数据稳定，线上指标优于旧版本，同意正式上线"
  }'
```

**审批通过后状态**：已上线
**下一步提示**：模型已正式上线，请监控运行状态

---

### 步骤 6：紧急回滚

如果发现线上问题，可随时回滚。

**界面操作**：点击「回滚」，填写回滚原因

**API 调用**：
```bash
curl -X POST http://localhost:8000/api/v1/models/1/rollback \
  -H "Content-Type: application/json" \
  -d '{
    "operator": "王五",
    "reason": "发现高并发场景下内存泄漏风险，紧急回滚"
  }'
```

**回滚效果**：
- 状态变为「已回滚」
- 流量归零
- 标记为非生产

**重复调用处理**：已回滚的模型再次回滚会提示回滚时间

```

   ↓          ↓           ↓           ↓         ↓
评测不通过   可重测      审批驳回    可回滚    审批驳回

              回到待评测   回到待灰度审批        回到待正式审批

```

## 常见问题

**Q: 重复提交相同操作会怎样？**

A: 系统会智能判断：
- 如果是完全重复且无意义的操作（如已评测通过再评测），会明确提示无需重复
- 如果是重复操作但有意义（如评测不通过后重测），会正常执行

**Q: 状态流转错了能改吗？**

A: 系统设计了兜底机制：
- 评测不通过可以重新评测
- 审批驳回可以重新审批
- 上线后发现问题可以回滚

**Q: 如何查看谁做了什么操作？**

A: 在模型详情页的「审计日志」标签页可以看到所有操作记录，包括操作人、操作内容、操作时间和结果。

**Q: 回滚后还能重新上线吗？**

A: 已回滚的模型版本不能再操作。建议创建新版本重新走完整流程，这样可以保证历史记录的可追溯性。

## 推荐的工作习惯

1. **每次训练产出必创建版本**：不要跳过版本管理
2. **评测结论要如实填写**：发现的问题写清楚，避免线上踩坑
3. **灰度观察要有耐心**：不要刚切流量就申请正式发布
4. **操作原因写详细**：审计日志是排查问题的重要依据
5. **回滚不要犹豫**：发现问题先回滚，再慢慢排查
