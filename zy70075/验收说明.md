# 员工离职权限回收服务 - 验收说明

## 服务启动
运行 `npm start` 后，终端会显示：
- 「员工离职权限回收服务已启动，端口：3001」
- 「服务地址：http://localhost:3001」
- 列出所有可用接口的中文说明

---

## 一、核心流程验收

### 1. 创建离职单
**接口：** POST /api/offboarding-forms

**用户看到的结果：**
- 第一次提交：返回「成功: true」，提示信息是「离职单已创建，单号：xxx」，数据里能看到员工姓名、部门、最后工作日，状态显示为「待处理」。
- 同一员工再提交一次（未完成前）：返回「成功: false」，「重复操作: true」，原因会明确说「员工工号「E001」已有未完成的离职流程，工单号：xxx」，同时返回已有的离职单数据。

**应该看到的状态：** 待处理

---

### 2. 生成权限清单
**接口：** POST /api/offboarding-forms/:id/generate-inventory

**用户看到的结果：**
- 第一次生成：返回「成功: true」，提示「已生成 5 项待回收权限」，数据里列出邮箱、VPN、OA、代码仓库、CRM 这 5 个系统的权限，状态都是「待回收」。
- 再点一次生成：返回「成功: false」，「重复操作: true」，原因说「该离职单已生成过权限清单，共 5 项」。

**应该看到的状态：**
- 离职单状态变为「权限清单已生成」
- 每项权限的状态都是「待回收」

---

### 3. 创建回收任务
**接口：** POST /api/offboarding-forms/:id/create-tasks

**用户看到的结果：**
- 第一次创建：返回「成功: true」，提示「已创建 5 个回收任务」，每个任务对应一项权限，状态都是「待执行」。
- 再点一次创建：返回「成功: false」，「重复操作: true」，原因说「回收任务已创建过，共 5 个任务」。

**应该看到的状态：**
- 离职单状态变为「回收任务已创建」
- 每个任务状态都是「待执行」，尝试次数是 0

---

### 4. 执行回收任务
**接口：** POST /api/reclamation-tasks/:id/execute

**用户看到的结果（分两种情况）：**

**情况 A：回收成功（如企业邮箱）**
- 返回「成功: true」，提示「权限回收成功」
- 任务状态变为「已完成」
- 对应权限的状态变为「已回收」
- 记录了执行时间和完成时间

**情况 B：回收失败（如 VPN，模拟了系统超时）**
- 返回「成功: false」，原因是「VPN 系统连接超时，暂时无法回收权限」
- 任务状态变为「执行失败」
- 对应权限的状态变为「回收失败」
- 尝试次数加 1，记录了具体的错误信息

**情况 C：重复执行已成功的任务**
- 返回「成功: false」，「重复操作: true」
- 原因说「该回收任务已经执行成功，无需重复执行」

**应该看到的记录：**
- 每个执行动作都会写入审计日志，包含操作人、时间、成功或失败详情

---

## 二、边界场景验收

### 5. 失败重试
**接口：** POST /api/reclamation-tasks/:id/retry

**用户看到的结果：**
- 对「执行失败」状态的任务点重试：重新执行一次回收逻辑
  - 如果这次成功了：任务状态变为「已完成」，权限变为「已回收」
  - 如果又失败了：尝试次数继续累加，错误信息更新
- 对「已完成」或「待执行」状态的任务点重试：返回原因「当前任务状态是「已完成」，只有「执行失败」状态才能重试」

**应该看到的汇总：**
- 只要还有失败的任务，离职单整体状态就是「部分失败」
- 所有任务都成功或豁免后，离职单状态变为「已完成」

---

### 6. 豁免审批
**第一步：申请豁免**
**接口：** POST /api/exemptions

**用户看到的结果：**
- 第一次提交豁免申请：返回「成功: true」，提示「豁免申请已提交，等待审批」
- 同一权限再申请一次：返回「成功: false」，「重复操作: true」，原因说「该权限已有待审批的豁免申请」

**第二步：审批通过**
**接口：** POST /api/exemptions/:id/approve

**用户看到的结果：**
- 审批通过后：提示「豁免已审批通过，该权限将跳过回收」
- 对应权限的状态变为「已豁免」
- 对应回收任务的状态也变为「已豁免」
- 离职单整体状态会重新计算（豁免也算完成的一种）

- 重复审批已通过的申请：返回「成功: false」，「重复操作: true」，原因说「该申请状态已经已通过，无需重复审批」

---

### 7. 审计报告
**接口：** GET /api/audit-report/:formId

**用户看到的汇总：**
- 顶部显示离职单基本信息（员工姓名、部门、最后工作日、当前状态）
- 「权限清单」部分：总数、已回收多少、已豁免多少、回收失败多少、待回收多少
- 「回收任务」部分：总数、已完成多少、已豁免多少、执行失败多少、待执行多少
- 「豁免申请」部分：总数、待审批多少、已通过多少、已拒绝多少
- 「操作日志」部分：按时间顺序列出所有操作，每条有时间、操作人、动作名称、具体详情（比如「执行回收任务成功：企业邮箱 - 邮箱账号」）

**真实验收现象：**
- 审计报告是给合规、内审的人看的，他们不需要知道什么 UUID、什么 HTTP 状态码
- 他们只需要看到：谁在什么时候做了什么，结果怎么样，有没有漏掉什么
- 汇总数字要能对得上（比如已完成 + 已豁免 + 执行失败 + 待执行 = 总数）

## 三、接口返回风格说明

所有接口返回都尽量用人话，不用机器术语：

✅ 好的返回示例：
```json
{
  "成功": true,
  "提示": "离职单已创建，单号：xxx",
  "数据": { ... }
}
```

❌ 不会出现的返回：
```json
{
  "code": 200,
  "message": "OK",
  "payload": { ... }
}
```

重复操作时，返回里明确有「重复操作: true」和中文原因，非开发的人也能看懂：
```json
{
  "成功": false,
  "重复操作": true,
  "原因": "员工工号「E001」已有未完成的离职流程，工单号：xxx",
  "已有数据": { ... }
}
```
