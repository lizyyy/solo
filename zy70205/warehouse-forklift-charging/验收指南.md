# 仓库叉车充电排队 API - 验收指南

## 一、业务场景概述

本系统面向仓库夜班叉车集中回充场景，核心矛盾是：
- 夜班结束时所有叉车同时返回需要充电
- 充电位数量有限（示例中4个充电位）
- 次日任务优先级不同，需要优先保证高优先级任务
- 电池电量参差不齐，需要智能分配

## 二、快速开始

### 1. 安装依赖
```bash
cd warehouse-forklift-charging
pip install -r requirements.txt
```

### 2. 初始化演示数据
```bash
python init_data.py
```

### 3. 启动服务
```bash
uvicorn app.main:app --reload --port 8000
```

### 4. 访问文档
- Swagger UI: http://localhost:8000/docs
- ReDoc: http://localhost:8000/redoc

### 5. 运行场景测试
```bash
python scenarios.py
```

## 三、API 响应码说明

### 成功码（代表通过）
| 响应码 | 含义 | 说明 |
|--------|------|------|
| OK | 操作成功 | 查询、获取类操作成功 |
| CREATED | 创建成功 | 叉车、任务、充电请求创建成功 |
| UPDATED | 更新成功 | 档案信息更新成功 |
| COMPLETED | 完成成功 | 充电、任务完成成功 |
| CORRECTED | 修正成功 | 人工修正已应用 |

### 错误码（代表需要人工处理）
| 响应码 | 含义 | 处理建议 |
|--------|------|----------|
| VALIDATION_ERROR | 参数校验失败 | 检查请求字段是否完整、格式是否正确 |
| VALIDATION_FAILED | 业务校验失败 | 检查业务规则，如叉车状态、充电位状态 |
| NOT_FOUND | 资源不存在 | 确认叉车编号、充电位编号是否正确 |
| DUPLICATE_REQUEST | 重复提交 | 使用不同的幂等键或等待之前的请求处理完成 |
| INVALID_STATUS | 状态不合法 | 检查当前状态是否允许该操作 |
| INVALID_TRANSITION | 非法状态流转 | 不允许的状态转换，需要重新评估业务流程 |
| INSUFFICIENT_BATTERY | 电量不足 | 需要先充电或使用人工修正调整电量 |
| ALREADY_CHARGING | 已有充电请求 | 取消现有请求或等待完成 |
| ALREADY_CHARGED | 已达到目标电量 | 无需充电，检查目标电量设置 |
| UNAVAILABLE | 资源不可用 | 充电位被占用，需要排队 |

## 四、核心功能验证

### 1. 叉车档案验证

**验证目标**：确认叉车档案能正确创建、查询、更新

**正常处理 - 通过**：
```bash
# 创建叉车
curl -X POST "http://localhost:8000/api/forklifts" \
  -H "Content-Type: application/json" \
  -d '{
    "forklift_code": "TEST-001",
    "name": "测试叉车",
    "battery_capacity": 80.0
  }'

# 预期响应: success=true, code="CREATED"
```

**失败原因**：
```bash
# 缺少必需字段
curl -X POST "http://localhost:8000/api/forklifts" \
  -H "Content-Type: application/json" \
  -d '{
    "forklift_code": "TEST-002"
  }'

# 预期响应: success=false, code="VALIDATION_ERROR"
# 需要人工检查: 缺少 battery_capacity 字段
```

**验证点**：
- GET `/api/forklifts/FL-001` 返回 `forklift.status == "active"` 表示档案生效
- GET `/api/forklifts/FL-001` 返回 battery 信息表示电池关联正确

### 2. 充电位锁定验证

**验证目标**：确认充电位锁定机制可靠

**正常处理 - 通过**：
```bash
# 查看充电位状态
curl "http://localhost:8000/api/stations/CS-001"
# 预期: status="available"

# 提交充电请求
curl -X POST "http://localhost:8000/api/charging/request" \
  -H "Content-Type: application/json" \
  -d '{
    "forklift_code": "FL-001",
    "station_code": "CS-001",
    "target_percent": 90.0
  }'

# 再次查看充电位
curl "http://localhost:8000/api/stations/CS-001"
# 预期: status="occupied", current_forklift_id 已设置
```

**失败原因 - 重复占用**：
```bash
# 尝试用另一个叉车占用同一充电位
curl -X POST "http://localhost:8000/api/charging/request" \
  -H "Content-Type: application/json" \
  -d '{
    "forklift_code": "FL-002",
    "station_code": "CS-001",
    "target_percent": 90.0
  }'

# 预期响应: errors 包含 code="UNAVAILABLE"
# 需要人工处理: 等待充电完成或选择其他充电位
```

### 3. 电量预测验证

**验证目标**：确认电量预测与原始数据一致

**验证步骤**：
```bash
# 步骤1: 获取原始数据
curl "http://localhost:8000/api/forklifts/FL-004"
# 记录: battery_capacity, charging_rate, battery.current_percent

# 步骤2: 发起预测
curl -X POST "http://localhost:8000/api/charging/predict" \
  -H "Content-Type: application/json" \
  -d '{
    "forklift_code": "FL-004",
    "current_percent": 22.0,
    "target_percent": 90.0,
    "station_code": "CS-001"
  }'
```

**判断通过的输出**：
- `validation_result: "PASS"`
- `validation_details.forklift_found: true`
- `validation_details.target_percent_valid: true`
- `validation_details.station_found: true`
- `estimated_charging_hours` 计算公式:
  `(电池容量 * (目标电量 - 当前电量) / 100) / 充电位功率`

**需要人工处理的输出**：
- `validation_result: "NEEDS_REVIEW"`
- 检查 `validation_details` 中哪个字段为 false

## 五、可复现场景说明

### 场景1: 正常处理流程
**通过输出**：
```
[✓ PASS] 验证叉车档案
[✓ PASS] 验证充电位状态
[✓ PASS] 创建充电请求
[✓ PASS] 完成充电
```
**判断标准**：所有步骤返回 `success=true`，充电请求状态从 `charging` 变为 `completed`

---

### 场景2: 缺字段错误
**通过输出（预期失败）**：
```
[✓ PASS] 缺少forklift_code
[✓ PASS] 缺少battery_capacity
[✓ PASS] 缺少任务时间字段
```
**判断标准**：
- 系统返回 `success=false`
- 响应包含 `errors` 数组
- 错误信息明确指出缺失的字段

**需要人工处理**：
- 检查请求体是否完整
- 参考 API 文档补充必需字段

---

### 场景3: 重复提交
**通过输出（预期拦截）**：
```
[✓ PASS] 首次提交
[✓ PASS] 重复提交检测
[✓ PASS] 重复叉车编号
```
**判断标准**：
- 首次提交返回 `success=true`
- 重复提交返回 `code="DUPLICATE_REQUEST"`
- 响应包含 `existing_request_id`

**需要人工处理**：
- 使用新的 `request_idempotency_key`
- 或者使用不带幂等键的请求（会生成新请求）

---

### 场景4: 非法状态流转
**通过输出（预期拦截）**：
```
[✓ PASS] 重复完成已完成请求
[✓ PASS] 非法状态转换拦截
[✓ PASS] 停用叉车充电拦截
```
**判断标准**：
- 返回 `code="INVALID_TRANSITION"` 或 `code="INVALID_STATUS"`
- 错误信息说明不允许的转换

**状态流转规则**：
```
充电请求状态流转:
PENDING → QUEUED / CANCELLED
QUEUED → CHARGING / CANCELLED
CHARGING → COMPLETED / CANCELLED / FAILED
COMPLETED → (不允许转换)
CANCELLED → (不允许转换)
FAILED → QUEUED / PENDING
```

**需要人工处理**：
- 确认业务流程是否正确
- 如果确实需要调整，使用人工修正接口

---

### 场景5: 人工修正流程
**通过输出**：
```
[✓ PASS] 人工修正电量
[✓ PASS] 修正后提交充电请求
[✓ PASS] 查看修正历史
```
**人工修正使用场景**：
1. 电池传感器读数异常
2. 系统状态与实际状态不符
3. 紧急情况下需要绕过正常流程

**修正后重跑验证**：
```bash
# 步骤1: 修正前提交失败
curl -X POST "http://localhost:8000/api/charging/request" \
  -H "Content-Type: application/json" \
  -d '{"forklift_code": "FL-003", "target_percent": 95.0}'
# 可能因电量问题失败

# 步骤2: 人工修正
curl -X POST "http://localhost:8000/api/correction/apply" \
  -H "Content-Type: application/json" \
  -d '{
    "entity_type": "battery",
    "entity_id": 3,
    "field_name": "current_percent",
    "old_value": "45.0",
    "new_value": "30.0",
    "reason": "电池传感器读数异常",
    "operator": "admin"
  }'

# 步骤3: 修正后重跑
curl -X POST "http://localhost:8000/api/charging/request" \
  -H "Content-Type: application/json" \
  -d '{"forklift_code": "FL-003", "target_percent": 95.0}'
# 预期: success=true
```

---

### 场景6: 排队优先级验证
**通过输出**：
```
[✓ PASS] 高优先级请求排队
[✓ PASS] 普通优先级请求排队
[✓ PASS] 优先级排序验证
[✓ PASS] 查看队列状态
```

**优先级计算规则**（分数越高越优先）：

| 条件 | 加分 |
|------|------|
| 电量 < 最低运行电量 | +100 |
| 电量 < 40% | +60 |
| 电量 < 60% | +30 |
| 高优先级任务需要充电 | +50 |
| 高优先级任务2小时内开始 | +30 |
| 中优先级任务需要充电 | +25 |
| 已有活跃充电请求 | -200 |

**判断标准**：
- FL-005（电量15% + 高优先级任务）的 priority_score 应该最高
- 队列按 priority_score 降序排列
- 充电位释放后自动分配给优先级最高的排队请求
