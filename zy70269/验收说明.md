# 公交站牌破损上报 API - 验收说明

## 项目概述

本系统解决以下主线问题：
- 公交站牌破损、线路变更、广告位遮挡由不同队伍上报
- 派修容易重复的问题通过"上报聚类 + 去重合并"机制解决

---

## 启动方式

```bash
# 1. 安装依赖
npm install

# 2. 启动服务（端口 3001）
npm run dev

# 3. 运行验收测试（另开终端）
npm test
```

---

## 核心资源模型

| 资源 | 说明 | 边界定义 |
|------|------|----------|
| **Stop（站牌）** | 物理站牌，包含关联线路 | 每个站牌有唯一 ID，状态只能是 ACTIVE 才能上报 |
| **Route（线路）** | 公交线路，带版本号 | 线路版本用于检测上报数据是否过时 |
| **Report（上报）** | 各队伍提交的问题记录 | 按队伍权限隔离上报类型 |
| **Dispatch（派修单）** | 实际派发给维修队的工单 | 同类问题聚合为一个派修单 |
| **ReportCluster（聚类）** | 同站牌同类型上报的聚合 | 核心去重机制 |

---

## 队伍权限隔离（边界 1：不同队伍上报不同类型）

| 队伍 ID | 名称 | 允许上报类型 | 不允许 |
|---------|------|-------------|--------|
| TEAM-MAINT | 设施维护队 | DAMAGED（站牌破损） | 线路变更、广告遮挡 |
| TEAM-ROUTE | 线路管理队 | ROUTE_CHANGE（线路变更） | 站牌破损、广告遮挡 |
| TEAM-AD | 广告巡查队 | AD_BLOCKED（广告位遮挡） | 站牌破损、线路变更 |

越权上报会返回错误码 `REPORT_TYPE_INVALID`

---

## 线路影响校验（边界 2：原始数据对得上）

上报时指定 `affectedRoutes` 会触发：
1. **关联校验**：线路是否确实属于该站牌
2. **版本校验**：上报的线路版本与系统版本是否一致

校验通过返回 `routeVerification.matchResult = "PASS"`
校验失败返回 `ROUTE_VERSION_MISMATCH` 或 `ROUTE_STOP_ASSOCIATION_INVALID`

---

## 派修去重机制（边界 3：解决重复派修）

去重判定条件（同时满足）：
- 同一站牌（stopId 相同）
- 同一上报类型（reportType 相同）
- 已有派修单状态为 PENDING（待处理）

去重结果：
- 首次上报 → 生成新派修单（`processingResult = NEW_DISPATCH`）
- 重复上报 → 合并到已有派修单（`processingResult = MERGED`, `isDuplicate = true`）

---

## 状态流转

```
上报状态流转：
SUBMITTED → VALIDATED → ROUTE_CHECKED → DISPATCHED → COMPLETED
                         ↑
                    （如有线路校验）

派修单状态：
PENDING → IN_PROGRESS → COMPLETED
            ↓
         MERGED（被合并）
```

## API 接口列表

### 1. 验证站牌档案
**POST /api/stops/verify**

验证站牌档案是否生效，是上报的前置条件。

请求体：
```json
{
  "stopId": "STOP-001"
}
```

通过响应（success=true）：
```json
{
  "success": true,
  "data": {
    "stop": { "id": "STOP-001", "name": "人民广场站", "status": "ACTIVE" },
    "associatedRoutes": [
      { "id": "ROUTE-01", "name": "1路", "version": 3 }
    ],
    "verificationResult": "PASS",
    "message": "站牌档案验证通过"
  }
}
```

### 2. 提交上报
**POST /api/reports**

提交破损/变更/遮挡上报。

请求体：
```json
{
  "teamId": "TEAM-MAINT",
  "stopId": "STOP-001",
  "reportType": "DAMAGED",
  "description": "站牌玻璃破碎",
  "affectedRoutes": [
    { "routeId": "ROUTE-01", "version": 3 }
  ],
  "reporterInfo": { "name": "张三", "phone": "13800138000" }
}
```

字段说明：
- `teamId`: 队伍标识，决定权限
- `reportType`: 上报类型（DAMAGED / ROUTE_CHANGE / AD_BLOCKED）
- `affectedRoutes`: 可选，指定受影响线路用于版本校验

### 3. 查询上报详情
**GET /api/reports/:reportId**

查看上报的完整状态流转历史和关联派修单。

### 4. 重试上报
**POST /api/reports/:reportId/retry**

修正参数后重新提交。

## 验收场景

### 场景 1：正常处理 ✅ 通过判定

**输出特征：**
- HTTP 200 / 201
- `success = true`
- `verificationResult = "PASS"`（站牌验证）
- `processingResult = "NEW_DISPATCH"`（首次上报）
- `dispatch.id` 存在
- `statusHistory` 包含完整流转记录

**判定：PASS → 无需人工干预，系统自动完成**

---

### 场景 2：失败原因 ❌ 需人工处理

**输出特征：**
- HTTP 400
- `success = false`
- `error.code` 为业务错误码
- `actionRequired` 给出具体处理建议

**常见错误码及处理：**

| 错误码 | 含义 | actionRequired 指引 |
|--------|------|-------------------|
| `STOP_NOT_FOUND` | 站牌不存在 | 请核对站牌编号，或先同步站牌档案 |
| `STOP_INACTIVE` | 站牌已停用 | 该站牌已停用，请确认上报对象 |
| `STOP_ARCHIVE_NOT_VERIFIED` | 档案未验证 | 站牌档案未经验证，请先调用验证接口 |
| `ROUTE_VERSION_MISMATCH` | 线路版本不一致 | 同步最新线路数据后重报（返回了系统版本号） |
| `ROUTE_STOP_ASSOCIATION_INVALID` | 线路不归属该站牌 | 请核对线路归属 |
| `REPORT_TYPE_INVALID` | 队伍越权 | 切换正确队伍或上报类型 |
| `TEAM_ID_INVALID` | 队伍未注册 | 请核对队伍 ID |

**判定：NEEDS_MANUAL_INTERVENTION → 根据 actionRequired 操作后重试**

---

### 场景 3：修正后重跑 🔄 重试成功

**流程：**
1. 首次提交失败（例如版本号填错）
2. 从错误响应 `error.details.systemVersion` 获取正确版本
3. 修改参数后重新提交
4. 返回 `success = true`

**判定：PASS_AFTER_RETRY → 修正后通过**

---

## 验收判定速查表

| 检查项 | 通过标准 | 失败标准 |
|--------|---------|---------|
| 站牌档案验证 | `verificationResult === "PASS"` | `success === false` |
| 首次上报成功 | `processingResult === "NEW_DISPATCH"` | 任一业务错误码 |
| 重复上报去重 | `processingResult === "MERGED"` 且 `isDuplicate === true` | 生成多个派修单 |
| 线路数据对得上 | `routeVerification.matchResult === "PASS"` | `ROUTE_VERSION_MISMATCH` |
| 错误可理解 | 有 `actionRequired` 字段 | 无明确指引 |
| 状态可追溯 | `statusHistory` 有完整记录 | 状态跳变或缺失 |

## 题目边界验证

本系统通过以下三个边界拉开题目范围：

1. **公交站牌边界**：
   - 必须先验证站牌档案（`/api/stops/verify`）
   - 非 ACTIVE 状态的站牌不允许上报
   - 解决"档案是否生效"的验证问题

2. **线路影响边界**：
   - 上报时可指定 `affectedRoutes` 进行版本校验
   - 版本不一致直接拦截，确保"和原始数据对得上"
   - 解决"上报数据可靠性"问题

3. **派修去重边界**：
   - 同站牌同类型的 PENDING 派修单会触发合并
   - 重复上报返回 `MERGED` 而非 `NEW_DISPATCH`
   - 从源头上解决"派修容易重复"的主线问题
