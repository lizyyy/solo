# 智能排班建议解释系统

## 一、系统概述

这是一个用于管理和解释智能排班模型灰度批次样本的系统。核心目标是解决**模型版本换了但样本编号没变**这类高频场景的处理流程标准化问题。

### 核心角色
- **标注负责人（周姐）**：负责导入灰度批次、补充标注员留言、人工修改字段
- **运营复核人**：负责复核特殊情况，特别是模型版本变更的记录
- **产品**：查看复盘数据、了解整体情况

## 二、边界规则（写在代码里，也写在这里）

### 规则1：模型版本换了但样本编号没变（MODEL_VERSION_CHANGED_SAME_ID）

**触发条件**：
- 同一批次内，或跨批次之间
- 样本编号（sampleId）完全相同
- 但模型版本（modelVersion）不一致

**自动处理**：
- 自动标记状态：`模型版本变更待复核`
- **不允许自动归为正常**，必须人工复核
- 会关联显示前次使用的模型版本和所属批次

**怎么判？（给运营复核人）**：
1. 先看「解释说明」了解具体情况
2. 再看「标注员/周姐留言」有没有补充背景
3. 如果是**正常模型迭代**（比如模型升级了，故意拿旧样本验证效果）→ 点「复核通过」
4. 如果是**数据错误**（比如样本编号和模型版本配错了）→ 点「驳回」，让标注团队重新处理
5. **拿不准的别瞎判**，在批次详情里留言问周姐

**怎么改？**：
- 复核通过 → 状态变为「复核通过」
- 复核驳回 → 状态变为「复核驳回」
- 标注负责人可以在批次详情页补充留言、人工修改字段

**怎么回滚？**：
- 在批次详情页点「回滚」按钮
- 状态恢复为「模型版本变更待复核」（回到同一份可解释结果，运营复核人还能在待处理列表里看到）
- 所有操作都会留操作日志，回滚前/后状态都有记录，随时可查证据
- 回滚后可以重新复核、重新驳回

---

### 规则2：同一批次内重复样本编号（DUPLICATE_SAMPLE_IN_BATCH）

**触发条件**：
- 同一个灰度批次内
- 出现两条或以上相同的样本编号

**自动处理**：
- 自动标记状态：`异常`
- 需要人工复核处理

---

### 规则3：正常样本（NORMAL_SAMPLE）

**触发条件**：
- 未命中任何异常规则

**自动处理**：
- 自动标记状态：`正常`
- 无需复核

---

## 三、标准操作流程（三步走）

### 第一步：灰度批次第一次导入（标注负责人周姐操作）

1. 进入「灰度批次列表」页
2. 点击「导入灰度批次」按钮
3. 填写：批次名称、模型版本、样本数量（或上传文件）
4. 点击「确认导入」
5. 系统会自动检测规则，标记异常记录

### 第二步：标注负责人周姐补看标注员留言

1. 点击刚导入的批次，进入详情页
2. 浏览样本列表，重点看标了「模型版本变更」或「异常」的记录
3. 对需要补充说明的记录，点「补留言」按钮
4. 把背景信息写上（比如：这是模型v2.1的迭代验证，用的v1.0的旧样本）
5. 留言会同步显示给运营复核人

### 第三步：产品复盘页更新（运营复核人操作）

1. 进入「产品复盘页」
2. 顶部统计卡片可以看到整体情况
3. 重点看「模型版本换了但样本编号没变 - 待复核列表」
4. 每条记录都有：前次版本、本次版本、解释说明、标注留言、下一步动作提示
5. 核对无误后，点「复核通过」或「驳回」
6. 所有操作会同步更新到批次详情页和导出明细里

## 四、数据一致性保证

**导出明细、页面展示、接口返回，读的都是同一份数据：**

- 页面展示 → 直接读 samples.json
- API 接口 → 直接读 samples.json
- 导出 Excel → 直接从 samples.json 生成

**所以不会出现：**
- ❌ 页面显示异常，导出里消失了
- ❌ 接口返回的状态和页面对不上
- ❌ 同一个记录在不同地方显示不一样

---

## 五、证据留存

每条样本都保留以下信息，运营追问时能回到证据：

| 字段 | 说明 |
|------|------|
| originalRowNumber | 原始行号（导入文件里的第几行） |
| originalData | 原始导入数据（完整保留，不改） |
| manualChanges | 人工改动记录（改了什么、谁改的、什么时候改的） |
| matchedRules | 命中了哪些边界规则（完整记录） |
| status | 当前处理状态 |
| explanation | 自动生成的解释说明 |
| annotatorComment | 标注员/周姐补充的留言 |
| operationLogs | 完整的操作日志时间线 |

## 六、快速开始

### 安装依赖

```bash
# 安装根目录依赖
npm install

# 安装后端和前端依赖
cd backend && npm install
cd ../frontend && npm install
```

### 启动开发环境

```bash
# 在根目录执行，同时启动前后端
npm run dev
```

- 前端地址：http://localhost:3000
- 后端地址：http://localhost:3002

### 一键运行验证脚本

```bash
# 后端启动后，运行完整链路验证
python3 backend/scripts/verify-full-flow.py
```

验证内容包括：
- 产品复盘页 7 条待处理是否渲染
- 来源批次、前次版本、周姐留言、下一步动作是否完整
- 批次列表/详情/复盘页 数据是否一致
- 复核通过 → 从待复核列表移除
- 回滚 → 回到待复核列表（同一份可解释结果）
- 操作历史日志是否完整
- 导出明细是否包含完整字段 + 操作日志 Sheet
- 驳回 + 回滚 也能回到待复核

### 初始化样例数据（可选）

系统启动后，可以通过以下步骤体验完整流程：

1. **导入第一个批次**（v1.0模型）：
   - 批次名称：20240601_灰度批次_v1.0
   - 模型版本：v1.0
   - 样本数量：10

2. **导入第二个批次**（v2.0模型，故意用部分相同样本编号）：
   - 批次名称：20240607_灰度批次_v2.0
   - 模型版本：v2.0
   - 样本数量：10
   - 👉 这时候系统会自动检测到 SAMPLE-0001 到 SAMPLE-0010 这些样本编号的模型版本变了
   - 👉 自动标记为「模型版本变更待复核」

3. **周姐补留言**：
   - 进入第二个批次详情页
   - 找一条标记为「模型版本变更」的记录
   - 点「补留言」，写上背景

4. **运营复核**：
   - 进入「产品复盘页」
   - 看待复核列表，核对信息
   - 点「复核通过」或「驳回」

## 八、注意事项

1. **别只看汇总数**：汇总卡片只是概览，有疑问一定要点进详情看原始行号和操作日志
2. **模型版本变更别急着归正常**：这是高频场景，不是边角料，一定要复核
3. **口头约定不管用**：所有规则都写在 `constants.js` 和这份 README 里，以代码和文档为准
4. **操作留痕**：所有人工操作都会记日志，谁、什么时候、做了什么、改之前是什么样，都能查
