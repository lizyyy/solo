# 慢行绿道断点修补系统

面向市政巡检、居民代表的业务管理平台，用于管理绿道断点修复、施工临时改道、公交刷卡时段数据联动的全流程。

## 核心设计原则

1. **规则透明**：所有边界规则同时写在代码和本 README 中，不靠口头约定
2. **数据不重复**：重复导入同一批公交刷卡时段时，数量不会翻倍
3. **历史可追溯**：即使只改了一条备注，也能看出改前改后的差别
4. **错误说人话**：错误提示直接说明问题和解决建议，不吐内部字段名
5. **先复核再确认**：施工临时改道别急着归正常，留给居民代表开会复核

## 三步核心工作流

### 第一步：公交刷卡时段第一次导入

- 巡检员上传 CSV 格式的公交刷卡时段数据
- 系统自动检测重复数据（同一断点 + 同一时段 + 同一日期）
- 重复数据自动跳过，不计入统计，数量不会翻倍
- 新断点自动创建，状态为"待巡检"

### 第二步：市政巡检员补看红线图备注

- 巡检员查看断点详情，补充/修改红线图备注
- 如发现施工临时改道未同步到地图，点击"标记为施工临时改道"
- **系统自动将状态流转为"待复核"，不会直接归为正常**
- 备注的每次修改都会保存历史快照，可对比查看

### 第三步：点位清单更新

- 居民代表在工作台看到所有"待复核"的施工改道项
- 点击进入详情页，可查看关联的公交刷卡时段和红线图备注
- 确认后点击"居民代表复核确认"，点位清单正式更新
- 状态流转为"已确认"或继续跟进

## 边界规则（同时写在代码中）

所有规则均在 `api/services/` 和 `api/db/init.ts` 的 seed 数据中有对应实现。

---

### 规则 001：施工临时改道未同步地图

**触发条件**：巡检员标记 `has_construction_detour = true`，且断点状态不是 `pending_review`

**判定逻辑**：
- 自动将状态流转为 `pending_review`（待复核）
- **不归为正常**，必须留给居民代表复核
- 在历史记录中注明是边界规则引擎触发的状态流转

**修改方式**：
1. 设置 `status = 'pending_review'`
2. 记录操作人 = "边界规则引擎-自动流转"
3. 生成历史快照，保存状态变更前后的值
4. 在工作台高亮显示待复核项

**回滚方式**：
1. 在历史记录页面找到对应的状态变更记录
2. 点击"回滚"按钮
3. 系统从历史快照恢复原状态
4. 记录回滚操作本身为一条新的历史记录

---

### 规则 002：重复导入公交刷卡时段

**触发条件**：数据库唯一约束 `UNIQUE(breakpoint_id, time_slot, source_date)` 冲突

**判定逻辑**：
- 识别为重复数据，直接跳过不插入
- 不计入 `imported_count`，只累计 `duplicate_count`
- 导入完成后在报告中明确显示跳过了多少条

**修改方式**：
1. 不执行 INSERT 操作
2. 批次的 `duplicate_count` + 1
3. 在导入预览页面用黄色背景标记重复行
4. 导入完成后通知用户"已自动跳过 N 条重复数据"

**回滚方式**：
1. 删除导入批次关联的所有 `bus_card_times` 记录
2. 对于因本次导入新创建的断点，可选择删除或保留
3. 恢复断点到导入前的状态
4. 所有回滚操作留痕

---

### 规则 003：仅修改备注的历史追踪

**触发条件**：调用 `PATCH /breakpoints/:id` 且仅包含 `redline_note` 字段变更

**判定逻辑**：
- 记录为 `update` 类型的变更
- 必须同时保存 `oldValue`（修改前）和 `newValue`（修改后）
- 保存完整快照，不只是差异

**修改方式**：
1. 更新 `breakpoints.redline_note` 字段
2. 生成一条 `history_record`：
   - `field_name = 'redline_note'`
   - `old_value = 原备注内容（或 null）`
   - `new_value = 新备注内容`
   - `snapshot = { before: {...}, after: {...} }`
3. 在详情页的时间线中显示改前/改后对比

**回滚方式**：
1. 从对应的 `history_record` 中取出 `old_value`
2. 更新断点的 `redline_note` 为 `old_value`
3. 生成一条新的历史记录，注明是回滚操作
4. 回滚操作本身也可再次回滚

## 错误提示规范

所有错误均使用 `FriendlyError` 格式，包含：
- `message`：直接说人话，说明问题是什么
- `suggestion`：告诉用户该怎么办
- `details`：可选，技术细节（默认收起）

**示例**：
```json
{
  "code": "DETOUR_MUST_REVIEW",
  "message": "有施工临时改道的断点必须经过居民代表复核",
  "suggestion": "请先标记为\"待复核\"，不要直接归为正常，留给居民代表开会确认"
}
```

禁止只返回内部字段名，如：`"field 'has_construction_detour' is invalid"`

## 可视化展示约定

选择图表或 3D 展示时，必须服务于复核流程：

1. **点击可溯源**：点击图表中的断点，必须能跳转到详情页
2. **不只有漂亮画面**：详情页中必须能看到原始的公交刷卡时段和红线图备注
3. **待复核优先**：可视化页面顶部优先展示需要居民代表复核的施工改道项
4. **快捷操作**：在图表 tooltip 中提供"查看详情"的直接入口

## 项目结构

```
├── api/                    # 后端 Express
│   ├── db/                 # 数据库初始化和连接
│   ├── routes/             # API 路由
│   ├── services/           # 业务逻辑（含边界规则实现）
│   └── app.ts              # 应用入口
├── src/                    # 前端 React
│   ├── components/         # UI 组件
│   ├── pages/              # 页面
│   ├── store/              # Zustand 状态管理
│   ├── lib/                # 工具函数、API 客户端
│   └── App.tsx             # 路由配置
├── shared/                 # 前后端共享类型
└── data/                   # SQLite 数据库文件
```

## 技术栈

- **数据库**：SQLite (better-sqlite3)
- **图表**：recharts
