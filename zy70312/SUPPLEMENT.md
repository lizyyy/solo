# API 错误预算看板 - 补充说明文档

## 一、系统主要边界

### 1.1 功能边界

**覆盖范围：**
- 服务级和接口级的错误预算计算和监控
- 按时间窗口（默认7天或30天）滚动计算预算消耗
- 燃烧速度检测和分级告警
- 短时尖峰与持续燃烧的区分处理
- 例外审批流程（申请、审批、过期）
- 发布冻结管理（自动触发、手动操作、解除）
- 指标缺口检测和待确认列表
- 风险列表导出（CSV格式）

**不覆盖范围：**
- 不负责实际的指标采集（只负责接收和存储）
- 不执行实际的发布阻塞（只提供决策建议）
- 不处理用户权限管理（假设所有操作都经过授权）
- 不提供告警通知（仅在界面展示状态）

### 1.2 数据边界

**指标数据：**
- 时间粒度：5分钟一个数据点
- 时间窗口：支持7天、30天等可配置周期
- 数据维度：服务级聚合或接口级细分
- 必需字段：总请求数、错误请求数
- 可选字段：P50延迟、P99延迟

**预算规则：**
- SLO范围：99.0% ~ 99.99%
- 错误预算：SLO的补集（如99.9% SLO对应0.1%错误预算）
- 燃烧速度阈值1：默认2x（警告）
- 燃烧速度阈值2：默认10x（严重）
- 尖峰检测窗口：默认15分钟
- 持续燃烧判定窗口：默认60分钟

### 1.3 决策边界

**四种发布决策：**

| 决策 | 触发条件 | 建议动作 |
|------|---------|---------|
| 继续发布 | 预算剩余 > 30%，燃烧速度正常，无尖峰 | 正常发布流程 |
| 观察 | 预算剩余 20-30%，或燃烧速度警告，或检测到尖峰 | 发布后密切观察30分钟 |
| 需例外审批 | 预算剩余 < 10%，或持续燃烧，或严重燃烧速度 | 申请例外审批后方可发布 |
| 冻结发布 | 预算耗尽，或持续严重燃烧，或燃烧速度极快 | 禁止发布，排查根因 |

**决策优先级（从高到低）：**
1. 手动冻结 → 冻结发布
2. 预算耗尽 → 冻结发布
3. 持续严重燃烧 → 冻结发布
4. 极快燃烧速度 → 冻结发布
5. 持续燃烧 / 严重燃烧速度 → 需例外审批
6. 预算剩余 < 10% → 需例外审批
7. 预算剩余 < 30% / 警告燃烧速度 / 尖峰 → 观察
8. 其他 → 继续发布

### 1.4 例外审批边界

**审批流程：**
1. 申请人创建例外申请（含发布编号、原因、有效期）
2. 审批人通过或拒绝
3. 审批通过后在有效期内豁免冻结限制
4. 过期自动失效

**有效期限制：**
- 最小：1小时
- 最大：72小时
- 默认：4小时

**注意：** 例外审批只是豁免冻结限制，不改变预算消耗计算。

## 二、一个失败路径

### 2.1 场景描述

**服务：** payment-service（支付服务，SLO: 99.9%，预算: 0.1%）

**时间线：**

1. **Day 1-5（正常阶段）**
   - 错误率稳定在 0.01-0.02%
   - 预算消耗缓慢，剩余约 90%
   - 决策：继续发布
   - 状态：健康

2. **Day 5 14:00（发布变更）**
   - 发布新版本 v2.3.0
   - 包含支付网关集成重构

3. **Day 5 14:30（尖峰出现）**
   - 错误率突然升至 15-25%
   - 持续约 2 小时
   - 系统检测到：短时尖峰
   - 决策：观察
   - 状态：警告
   - 团队假设：只是短暂的流量波动

4. **Day 5 16:30（持续燃烧）**
   - 错误率虽有所下降，但仍维持在 8-12%
   - 持续超过 1 小时
   - 系统检测到：持续燃烧 + 燃烧速度 15x（严重）
   - 决策：冻结发布
   - 状态：严重 → 冻结
   - **团队没有注意到状态变化，继续准备下一个发布**

5. **Day 5 18:00（预算耗尽）**
   - 7天错误预算完全耗尽
   - 自动创建冻结记录
   - 决策：冻结发布
   - 状态：已冻结

6. **Day 5 19:00（尝试发布）**
   - 团队尝试发布 hotfix v2.3.1
   - 看板显示：冻结发布
   - 需要申请例外审批

7. **Day 5 19:30（例外审批）**
   - 申请紧急例外审批，理由：hotfix修复支付问题
   - 审批通过，有效期 2 小时

8. **Day 5 20:00（发布失败）**
   - 由于根因未找到，hotfix 未能正确修复
   - 错误率升至 30%+
   - 预算已经为负（无法再消耗）

9. **Day 5 22:00（审批过期）**
   - 例外审批过期
   - 再次进入冻结状态

10. **Day 6 02:00（根因定位）**
    - 终于发现：支付网关签名算法不兼容
    - 回滚到 v2.2.0

11. **Day 6 04:00（恢复）**
    - 错误率恢复正常
    - 但 7 天窗口内的预算已经耗尽
    - 需要等待窗口滚动恢复

### 2.2 失败原因分析

**系统层面的边界：**
1. 系统只能检测和提示，不能强制阻止发布
2. 例外审批机制可以绕过冻结，但不解决根本问题
3. 预算耗尽后，即使恢复正常，也需要等待窗口滚动

**团队层面的失误：**
1. 没有在"观察"状态时提高警惕
2. 没有及时发现"持续燃烧"的严重程度
3. 在根因未明的情况下申请例外审批发布
4. 没有设置自动告警，依赖人工查看看板

### 2.3 系统如何记录这个路径

```

- expires_at: Day 5 21:30
```

## 三、一次重复执行路径

### 3.1 场景：每周发布会的复查流程

**背景：** 团队每周五下午 16:00 召开发布会，需要复查所有服务的错误预算状态。

### 3.2 执行步骤（照着做）

#### Step 1: 打开看板概览页

**操作：**
- 访问 `http://localhost:5173/`
- 点击导航栏的「服务概览」

**检查项：**
- [ ] 顶部统计卡片：总服务数、健康、警告、严重、已冻结、指标缺失
- [ ] 确认没有「已冻结」的服务（或有但已确认）
- [ ] 确认「指标缺失」数量为 0（或已列入待确认）
- [ ] 查看每个服务卡片的「发布决策」标签

**预期结果：**
- 大多数服务显示「继续发布」或「观察」
- 没有「冻结发布」的服务
- 「需例外审批」的服务应有对应的审批记录

#### Step 2: 查看风险列表并导出

**操作：**
- 点击导航栏的「风险列表」
- 点击「导出 CSV」按钮

**检查项：**
- [ ] 风险列表按严重程度排序（冻结 > 指标缺失 > 严重 > 警告 > 健康）
- [ ] 检查每个服务的「发布决策」列
- [ ] 检查「原因」列，了解风险来源
- [ ] 检查「建议」列，确认后续动作
- [ ] 确认导出的 CSV 文件可用于发布会存档

**导出文件包含：**
- 服务名称、接口、状态、发布决策
- 剩余预算、燃烧速度
- 原因列表（分号分隔）
- 建议列表（分号分隔）

#### Step 3: 检查指标缺口

**操作：**
- 点击导航栏的「指标缺口」

**检查项：**
- [ ] 如果显示「所有指标正常」，跳过此步
- [ ] 如果有缺口：
  - [ ] 确认缺口时长（是否超过 2 小时）
  - [ ] 检查最后可见时间
  - [ ] 记录需要人工确认的服务
  - [ ] 这些服务的发布需要例外审批

**重要：** 指标缺口不能被当成健康状态！

#### Step 4: 逐个复查有风险的服务

**操作：**
- 回到「服务概览」
- 点击每个状态非「健康」的服务卡片

**检查项（每个服务）：**

1. **查看状态和决策**
   - [ ] 状态标签（健康/警告/严重/冻结/指标缺失）
   - [ ] 发布决策标签

2. **查看错误预算**
   - [ ] 剩余预算百分比
   - [ ] 燃烧速度及等级
   - [ ] 燃烧速度是否超过阈值

3. **查看原因分析**
   - [ ] 阅读所有原因条目
   - [ ] 理解为什么是这个状态

4. **查看趋势图表**
   - [ ] 错误率趋势（是否在上升？）
   - [ ] 预算剩余趋势（消耗速度如何？）
   - [ ] 燃烧速度趋势（是否在恶化？）

5. **查看操作建议**
   - [ ] 确认建议是否合理
   - [ ] 确认团队是否已执行

6. **检查冻结记录（如果有）**
   - [ ] 冻结原因
   - [ ] 冻结时间
   - [ ] 是否需要解除

#### Step 5: 检查例外审批

**操作：**
- 点击导航栏的「例外审批」

**检查项：**
- [ ] 待审批：确认是否需要处理
- [ ] 已通过：确认在有效期内，对应服务是否确实需要
- [ ] 已过期：这些审批已失效，对应服务恢复原始状态
- [ ] 已拒绝：了解拒绝原因

**特别注意：**
- 例外审批的有效期结束后自动失效
- 需要在发布前确认审批是否仍有效

#### Step 6: 形成发布会结论

**汇总：**

| 服务 | 状态 | 决策 | 动作 |
|------|------|------|------|
| payment-service | 警告 | 观察 | 可以发布，发布后观察 30 分钟 |
| search-service | 严重 | 需例外审批 | 已有审批记录（RELEASE-20260512-001），确认有效期 |
| report-service | 冻结 | 冻结发布 | 禁止发布，需先排查根因 |
| ... | ... | ... | ... |

**会议决策模板：**

1. **可以直接发布的服务：** [列表]
2. **需要观察后发布的服务：** [列表 + 观察要点]
3. **需要例外审批的服务：** [列表 + 审批状态]
4. **禁止发布的服务：** [列表 + 原因 + 后续计划]
5. **指标缺失待确认的服务：** [列表 + 责任人]

### 3.3 重复执行的关键检查点

每次发布会都必须确认：

1. **「冻结发布」的服务** → 必须有充分理由才能例外
2. **「需例外审批」的服务** → 必须有有效的审批记录
3. **「指标缺失」的服务** → 必须人工确认后才能发布
4. **「观察」的服务** → 必须有人负责发布后的监控
5. **例外审批的有效期** → 发布时间必须在有效期内

### 3.4 常见复查结果

**正常场景：**
- 所有服务健康或观察
- 无冻结、无指标缺失
- 可以正常进行发布会

**有风险场景：**
- 个别服务警告或严重
- 已申请例外审批
- 发布会需要讨论这些服务的风险

**异常场景：**
- 有服务被冻结
- 有指标缺失
- 需要先解决问题再开会，或推迟部分发布

## 五、API 接口清单

### 5.1 看板查询

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/overview | 获取所有服务概览 |
| GET | /api/services/:id | 获取服务详情（含趋势） |
| GET | /api/services | 获取所有服务列表 |
| GET | /api/risk-list | 获取发布会风险列表 |
| GET | /api/export/risk-list | 导出风险列表 CSV |
| GET | /api/metrics-gaps | 获取指标缺口列表 |

### 5.2 指标写入

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | /api/metrics | 批量写入指标数据 |

**请求体示例：**
```json
[
  {
    "serviceId": "uuid",
    "endpointId": "uuid或null",
    "timestamp": 1715500800000,
    "totalRequests": 1000,
    "errorRequests": 5,
    "p50LatencyMs": 50,
    "p99LatencyMs": 200,
    "source": "api"
  }
]
```

| 方法 | 路径 | 说明 |

| POST | /api/exceptions/:id/approve | 通过审批 |
| POST | /api/exceptions/:id/reject | 拒绝审批 |

### 5.4 发布冻结
