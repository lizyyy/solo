# 采购付款排程 - 核心业务规则文档

## 1. 系统概述

本系统用于管理采购付款计划的自动排程，核心目标是解决以下业务痛点：
- 付款计划需要按账期、发票和资金计划排队
- 插单操作容易导致排程混乱
- 状态变更缺乏可追溯性
- 异常情况无法及时发现和处理

## 2. 核心业务流程

### 2.1 主流程

```
创建付款计划(草稿) 
    ↓
关联发票并完成认证
    ↓
提交排程(待排程)
    ↓
自动排程计算(已排程)
    ↓
执行付款(部分付款/已付款)
```

### 2.2 异常分流

```
提交排程校验失败 → 转入人工复核
排程时资金不足 → 延后付款日期 + 生成延后通知
插单申请 → 走审批流程(紧急优先级例外)
```

## 3. 状态机说明

### 3.1 付款计划状态

| 状态 | 说明 | 可转换到 | 触发条件 |
|------|------|----------|----------|
| draft (草稿) | 刚创建，未提交 | pending_schedule, cancelled | 提交排程 / 取消 |
| pending_schedule (待排程) | 已提交，等待排程 | scheduled, manual_review | 自动排程 / 校验失败 |
| scheduled (已排程) | 已排定付款日期 | partially_paid, delayed, manual_review | 执行付款 / 资金变更 / 插单影响 |
| partially_paid (部分付款) | 已支付部分款项 | fully_paid | 继续付款 |
| fully_paid (已付款) | 已全额支付 | - | 终止状态 |
| delayed (已延后) | 付款日期已延后 | scheduled, manual_review | 重新排程 / 异常处理 |
| manual_review (人工复核) | 需要人工处理 | scheduled, cancelled, pending_schedule | 人工处理后 |
| cancelled (已取消) | 已取消 | - | 终止状态 |

### 3.2 发票状态

| 状态 | 说明 | 可转换到 | 触发条件 |
|------|------|----------|----------|
| pending_received (待收票) | 已创建，未收到 | received | 录入收到日期 |
| received (已收票) | 已收到发票 | verified | 完成认证 |
| verified (已认证) | 已完成发票认证 | matched | 匹配付款计划 |
| matched (已匹配) | 已匹配到付款计划 | partially_used, fully_used | 付款执行 |
| partially_used (部分使用) | 部分金额已使用 | fully_used | 继续使用 |
| fully_used (已用完) | 金额已全部使用 | - | 终止状态 |
| invalid (已作废) | 已作废 | - | 终止状态 |

## 4. 处理成功场景

### 4.1 付款计划创建成功

**条件：**
- 必填字段完整（采购订单、供应商、账期、金额等）
- 账期天数 ≥ 0
- 计划金额 > 0

**结果：**
- 付款计划状态：draft (草稿)
- 期望付款日期自动计算（如未指定）
- 下一步操作：关联发票

**接口返回示例：**
```json
{
  "success": true,
  "code": "PLAN_000",
  "message": "付款计划创建成功，请关联发票后提交排程",
  "data": {
    "plan_id": "PP-20260510-ABC123",
    "status": "draft"
  },
  "next_action": "请关联发票后提交排程",
  "needs_manual_review": false
}
```

### 4.2 提交排程成功

**条件（全部满足）：**
1. 付款计划状态为 draft
2. 有关联的发票（至少1张）
3. 发票总金额 ≥ 计划付款金额
4. 所有发票已完成认证（status = verified）

**结果：**
- 付款计划状态：pending_schedule (待排程)
- 加入待排程队列，按优先级排序
- 下一步操作：等待自动排程或手动触发

**规则追踪示例：**
```
RULE: PLAN_SUBMIT_001 - 检查付款计划是否存在 ✓
RULE: PLAN_SUBMIT_002 - 检查付款计划状态是否为草稿 ✓
RULE: PLAN_SUBMIT_003 - 检查发票金额是否覆盖计划金额 ✓ (计划: 10000元, 发票: 10500元)
RULE: PLAN_SUBMIT_004 - 检查发票是否已认证 ✓ (3张发票均已认证)
RULE: PLAN_SUBMIT_005 - 提交排程成功 ✓
```

### 4.3 自动排程成功

**条件（全部满足）：**
1. 付款计划在待排程队列中
2. 关联发票校验通过
3. 资金日历中有可用资金

**结果：**
- 付款计划状态：scheduled (已排程)
- 确定最终付款日期
- 生成排程记录
- 预留对应资金

**排程算法：**
1. 按优先级排序：URGENT > HIGH > NORMAL
2. 计算期望付款日期：发票日期 + 账期天数（周末顺延）
3. 从期望日期开始查找可用资金
4. 找到足够资金后锁定该日期

### 4.4 发票匹配成功

**条件（全部满足）：**
1. 发票状态为 verified 或 matched
2. 发票供应商与付款计划供应商一致
3. 发票采购订单与付款计划采购订单一致（跨订单需人工复核）
4. 发票未匹配到其他付款计划

**结果：**
- 发票状态：matched (已匹配)
- 发票与付款计划建立关联

## 5. 需要人工复核的场景

以下场景系统无法自动处理，会将付款计划转入 `manual_review` 状态，需要人工介入。

### 5.1 发票相关

| 场景 | 触发条件 | 复核建议 |
|------|----------|----------|
| 发票金额不足 | 关联发票总金额 < 计划付款金额 | 补充发票或调整计划金额 |
| 发票未认证 | 存在未完成认证的发票 | 先完成发票认证 |
| 无关联发票 | 提交排程时没有关联任何发票 | 先创建并匹配发票 |
| 跨订单匹配 | 发票采购订单与计划采购订单不一致 | 确认是否允许跨订单使用 |
| 发票号重复 | 新创建的发票号已存在 | 检查是否重复录入 |

### 5.2 资金相关

| 场景 | 触发条件 | 复核建议 |
|------|----------|----------|
| 资金不足 | 90天内未找到足够可用资金 | 补充资金计划或延后付款 |
| 资金已锁定 | 目标日期资金状态为 locked | 选择其他日期或解锁资金 |
| 无资金配置 | 期望付款日期未配置资金日历 | 先配置该日期的资金额度 |

### 5.3 状态相关

| 场景 | 触发条件 | 复核建议 |
|------|----------|----------|
| 状态异常 | 非草稿状态提交排程 | 检查计划当前状态，确认操作意图 |
| 已匹配其他计划 | 发票已匹配到其他付款计划 | 确认是否需要转移匹配关系 |
| 计划已取消 | 对已取消计划进行操作 | 确认是否需要恢复计划 |

### 5.4 插单相关

| 场景 | 触发条件 | 复核建议 |
|------|----------|----------|
| 目标位置无效 | 目标位置 >= 当前位置 | 插单只能向前，确认目标位置 |
| 影响范围大 | 插单将影响超过10个计划 | 评估影响，考虑其他方案 |
| 审批被驳回 | 插单申请审批不通过 | 调整插单理由或放弃插单 |

## 6. 规则可追溯机制

### 6.1 规则追踪格式

每条业务规则执行时都会生成追踪记录，包含：

```json
{
  "rule": "PLAN_SUBMIT_003",
  "description": "检查发票金额是否覆盖计划金额",
  "input": {
    "plan_amount": 10000.00,
    "invoice_amount": 9500.00,
    "invoice_count": 2
  },
  "output": "发票金额不足，缺口500.00元",
  "passed": false
}
```

### 6.2 规则编号体系

| 前缀 | 规则类型 | 示例 |
|------|----------|------|
| PLAN | 付款计划相关 | PLAN_CREATE_001, PLAN_SUBMIT_003 |
| INV | 发票相关 | INV_CREATE_001, INV_MATCH_002 |
| FUND | 资金相关 | FUND_CHECK_001, FUND_SEARCH_003 |
| SCHEDULE | 排程相关 | SCHEDULE_BATCH_001, PLAN_SCHEDULE_002 |
| CREDIT | 账期计算 | CREDIT_CALC_001, CREDIT_CALC_003 |
| APPR | 审批相关 | APPR_INS_001, APPR_INS_004 |
| NOTI | 通知相关 | NOTI_DELAY_001, NOTI_DELAY_003 |
| INSERT | 插单相关 | INSERTION_001, INSERTION_EXEC_001 |

### 6.3 查询规则轨迹

使用接口 `/api/payment-plans/{plan_id}/rule-traces` 可以查询付款计划的所有规则执行轨迹，包括：
- 排程记录列表
- 每次排程的原始日期和调整后日期
- 调整原因和调整类型
- 操作人和操作时间

## 7. 后台任务处理

### 7.1 自动排程任务 (SchedulerTask)

**执行频率：** 建议每日凌晨 2:00 执行

**任务流程：**
1. 获取所有待排程的付款计划
2. 按优先级排序（URGENT > HIGH > NORMAL）
3. 逐个执行排程计算
4. 生成排程记录
5. 对需要延后的创建延后通知

**失败处理：**

| 失败类型 | 表现 | 重试策略 |
|----------|------|----------|
| 完全失败 | 任务状态 = failed，所有计划仍在待排程队列 | 可立即重试，不影响数据 |
| 部分失败 | 任务状态 = partial_success，部分计划转入人工复核 | 已成功的不会重复处理，只处理剩余计划 |
| 单个计划失败 | 该计划转入 manual_review，其他继续 | 修复问题后可单独触发该计划 |

**再次执行表现：**
- 已成功排程的计划（status = scheduled）不会重复处理
- 待排程队列中的计划会重新计算
- 人工复核状态的计划需要人工处理后才能重新排程

### 7.2 延后通知任务 (NotificationTask)

**执行频率：** 建议每小时执行一次

**任务流程：**
1. 获取所有 pending 状态的延后通知
2. 获取所有 failed 状态的延后通知
3. 逐个发送通知
4. 更新通知状态

**失败处理：**

| 失败类型 | 表现 | 重试策略 |
|----------|------|----------|
| 单个通知失败 | 通知状态 = failed，记录错误信息 | 下次执行时自动重试 |
| 部分失败 | 任务状态 = partial_success | 失败的通知标记为 failed，下次重试 |
| 完全失败 | 任务状态 = failed | 全部通知保持原状态，下次重新处理 |

**通知状态流转：**
```
pending → sent → acknowledged
         → failed (可重试)
```

### 7.3 报表生成任务 (ReportTask)

**执行频率：** 建议每日凌晨 6:00 执行

**报表内容：**
- 已排程付款金额和笔数
- 插单记录
- 延后记录
- 人工复核记录
- 资金使用情况
- 逾期付款预警

**失败处理：**
- 报表生成失败不影响业务流程
- 可随时手动重新生成
- 报表基于当前数据库状态，可重复生成

## 8. 插单审批机制

### 8.1 插单流程

```
申请插单
    ↓
检查优先级
    ├─ URGENT → 直接插队（无需审批）
    └─ 其他 → 创建审批 → 审批通过/驳回
                    ↓
              执行插单操作
                    ↓
              记录插单轨迹
                    ↓
              生成影响分析
```

### 8.2 审批规则

| 条件 | 是否需要审批 | 说明 |
|------|-------------|------|
| 优先级 = URGENT | 否 | 紧急付款可直接插队 |
| 优先级 = HIGH | 是 | 需审批人确认 |
| 优先级 = NORMAL | 是 | 需审批人确认 |
| 目标位置 = 1 | 是 | 插队到最前需谨慎评估 |
| 影响计划数 > 10 | 是 | 大面积影响需审批 |

### 8.3 插单影响

插单执行后会：
1. 将付款计划标记为 is_insertion = true
2. 对受影响的计划生成调整记录（adjustment_type = 'insertion'）
3. 可能需要重新计算受影响计划的付款日期
4. 建议重新执行一次完整排程

## 9. 资金日历规则

### 9.1 资金查找顺序

排程时按以下顺序查找可用资金：

1. **期望付款日期**：从发票日期 + 账期天数计算
2. **向后顺延**：如当日资金不足，顺延到下一个工作日
3. **跳过周末**：周末不安排付款
4. **最大范围**：最多查找 90 天

### 9.2 资金状态

| 状态 | 说明 | 是否可用 |
|------|------|----------|
| available | 可用，未被使用 | 是 |
| partially_used | 部分已使用，仍有余额 | 是 |
| fully_used | 已全部预留 | 否 |
| locked | 已锁定，不可用 | 否 |
| cancelled | 已取消 | 否 |

### 9.3 资金预留机制

排程成功后：
- 对应日期的资金日历条目增加 reserved_fund
- 可用余额 = total_fund - reserved_fund
- 可用余额为 0 时，状态变为 fully_used

## 10. 异常恢复指南

### 10.1 常见问题处理

**问题：大量付款计划转入人工复核**

处理步骤：
1. 调用 `/api/reviews/manual` 查看待复核列表
2. 检查每个计划的 remark 字段，了解具体原因
3. 针对原因进行处理：
   - 发票问题：补充发票或完成认证
   - 资金问题：配置资金日历
   - 状态问题：确认状态流转
4. 处理完成后，计划状态会自动恢复，或需手动触发重新排程

**问题：排程任务执行失败**

处理步骤：
1. 查看任务返回的 errors 字段
2. 检查是否为临时问题（如数据库连接、网络问题）
3. 可调用 `can_retry()` 判断是否可重试
4. 手动重新执行排程任务

**问题：延后通知发送失败**

处理步骤：
1. 调用 `/api/notifications/pending` 查看待发送列表
2. 查看失败通知的错误信息
3. 检查通知渠道配置（邮件服务器、短信网关等）
4. 调用 `/api/notifications/{id}/send` 重试发送

### 10.2 数据一致性检查

建议定期检查以下一致性：

1. **发票匹配一致性**：
   - 发票的 matched_payment_plan_id 应存在于付款计划中
   - 付款计划的 invoice_ids 应包含对应的发票

2. **资金预留一致性**：
   - 已排程计划的总金额 ≤ 对应日期的 reserved_fund
   - reserved_fund 不应超过 total_fund

3. **状态流转合理性**：
   - 已付款计划不应出现在待排程队列
   - 已认证发票不应回到待收票状态

## 11. 接口返回规范

所有接口返回统一格式，便于非开发人员理解：

```json
{
  "success": true/false,
  "code": "业务结果码",
  "message": "业务化描述，非开发人员可直接理解",
  "data": { "具体业务数据" },
  "needs_manual_review": true/false,
  "review_reason": "需要人工复核的原因",
  "next_action": "下一步操作建议",
  "rule_traces": [
    { "规则执行轨迹，可用于复查" }
  ],
  "timestamp": "处理时间"
}
```

### 结果码规范

| 码值范围 | 含义 | 示例 |
|----------|------|------|
| XXX_000 | 成功 | PLAN_000, SCHEDULE_000 |
| XXX_999 | 失败 | PLAN_999, MATCH_999 |

### 业务化消息示例

**不推荐（技术化语言）：**
- "HTTP 400 Bad Request"
- "Constraint violation error"
- "NullPointerException"

**推荐（业务化语言）：**
- "发票金额不足，计划金额10000元，关联发票仅9500元，请补充发票"
- "该日期未配置资金日历，请先配置5月15日的资金额度"
- "插单申请需审批，将影响5个付款计划的排程时间"
