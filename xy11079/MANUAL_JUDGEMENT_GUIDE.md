# 蛋糕预订台取货核验 - 人工判定说明

## 一、概述
本文档说明蛋糕预订台取货核验系统中，进入人工处理流程的判定标准，明确哪些字段会影响订单状态，哪些仅作为备注留档。

## 二、影响订单状态的字段（核心判定字段）

### 2.1 代取人身份信息
| 字段名 | 说明 | 状态影响 | 判定标准 |
|--------|------|----------|----------|
| `proxyPicker` | 代取人姓名 | ✅ 影响状态 | 必须与授权书上的姓名一致 |
| `proxyIdCard` | 代取人身份证号 | ✅ 影响状态 | 必须符合18位身份证格式，且与授权书一致 |
| `proxyPhone` | 代取人联系电话 | ✅ 影响状态 | 必须与系统预留电话一致 |

**自动触发人工审核的情况**：
- 身份证号格式验证失败 →  `PROXY_IDCARD_INVALID`
- 身份证号与系统记录不匹配 → `MANUAL_REVIEW_REQUIRED`

### 2.2 订单支付信息
| 字段名 | 说明 | 状态影响 | 判定标准 |
|--------|------|----------|----------|
| `balancePaid` | 实付尾款金额 | ✅ 影响状态 | 必须 ≥ 订单尾款金额 |
| `paymentMethod` | 支付方式 | ⚠️ 间接影响 | 记录支付方式，影响财务对账 |

**自动触发失败**：
- 实付金额 < 尾款 → `BALANCE_NOT_PAID`，状态置为 `failed`

### 2.3 核验核心字段
| 字段名 | 说明 | 状态影响 | 判定标准 |
|--------|------|----------|----------|
| `verificationCode` | 取货验证码 | ✅ 影响状态 | 必须与订单验证码完全一致 |
| `verificationType` | 核验类型 | ✅ 影响状态 | customer/proxy/manual |

**自动触发失败**：
- 验证码错误 → `VERIFICATION_CODE_INVALID`

## 三、仅作为备注留档的字段（不影响状态）

### 3.1 操作记录字段
| 字段名 | 说明 | 留档位置 |
|--------|------|----------|
| `operator` | 操作人姓名 | 修改历史记录 |
| `operatorId` | 操作人工号 | 修改历史记录 |
| `remarks` | 备注信息 | 修改历史记录 |

### 3.2 人工审核备注字段
| 字段名 | 说明 | 留档位置 |
|--------|------|----------|
| `manual_remarks` | 人工审核意见 | 历史记录表，field = manual_remarks |

**说明**：
- 所有人工审核的备注信息都会完整记录在修改历史中，可通过 `/api/orders/{id}/history 接口查询
- 备注信息仅用于追溯，不直接改变订单核心状态流转逻辑

## 四、人工审核操作指南

### 4.1 审核场景
当系统自动核验出现以下错误码时，进入人工审核：
- `PROXY_IDCARD_INVALID` - 代取人身份证验证失败
- `MANUAL_REVIEW_REQUIRED` - 需要人工进一步核实

### 4.2 审核操作接口
**接口地址：`POST /api/verifications/{orderId}/resubmit`

**请求参数**：
```json
{
  "operator": "审核员姓名",
  "remarks": "审核意见（必填，详细说明）",
  "approve": true/false
}
```

**审核结果**：
- `approve: true` → 订单状态变为 `completed`
- `approve: false` → 订单状态恢复为 `pending`

### 4.3 审核留痕机制
1. **每次人工审核操作都会：
   - 在历史记录表新增一条 `field = manual_remarks` 的记录
   - 记录审核人、审核时间、审核意见
   - 订单状态变更也会单独记录一条历史记录

## 五、订单状态流转图

```
pending → 系统核验 → 成功 → completed
         ↓
      失败
         ↓
    failed（金额不足）
    manual_review（身份验证失败）→ 人工审核 → 通过 → completed
                                 ↓
                               不通过 → pending
```

## 六、日志一致性检查

系统提供日志一致性检查接口：`GET /api/verifications/log-consistency/{orderId}`

检查规则：
- 成功的核验记录数 = 状态变为 completed 的历史记录数
- 两者不相等时标记为日志不一致

## 七、撤回后再次提交

### 7.1 撤回操作
接口：`POST /api/verifications/{orderId}/withdraw`

仅当订单状态为 `completed` 时可撤回
撤回后状态变为 `pending`
撤回操作完整记录在历史中

### 7.2 再次提交
撤回后的订单可以重新发起核验
所有重新核验的操作都会记录新的核验记录和历史记录

## 八、字段更新历史查询

所有字段的变更都会记录历史，包括：
- 状态变更（status）
- 代取人信息变更
- 人工审核备注
- 订单撤回记录

查询接口：`GET /api/orders/{id}/history`
