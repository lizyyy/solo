# 招聘背调进度 API 验收规则

## 一、状态可见性

### 1.1 背调任务状态

用户应该能够看到以下任务状态：

| 状态 | 中文描述 | 可见场景 |
|------|----------|----------|
| `draft` | 草稿 | 任务刚创建，尚未提交材料需求 |
| `pending_materials` | 等待材料 | 已提交材料需求，等待候选人提交 |
| `materials_submitted` | 材料已提交 | 候选人已提交所有材料 |
| `sent_to_third_party` | 已发送第三方 | 材料已审核并发送给背调机构 |
| `third_party_received` | 第三方已回执 | 收到背调机构的初步回执 |
| `pending_review` | 待审核 | 背调完成，等待最终决策 |
| `completed` | 已完成 | 已做出录用/拒绝决策 |
| `conflict` | 存在冲突 | 发现材料或背调结果有冲突 |
| `cancelled` | 已取消 | 任务被主动取消 |
| `timeout` | 超时 | 第三方机构未在规定时间内返回结果 |

### 1.2 候选人状态

候选人状态与任务状态联动：

| 状态 | 中文描述 | 关联任务状态 |
|------|----------|--------------|
| `pending` | 待处理 | draft |
| `in_progress` | 进行中 | pending_materials, materials_submitted, sent_to_third_party, third_party_received, pending_review, conflict, timeout |
| `approved` | 已通过 | completed (decision=approved) |
| `rejected` | 已拒绝 | completed (decision=rejected) |
| `cancelled` | 已取消 | cancelled |

## 二、记录完整性

### 2.1 材料版本记录

每次材料提交都会创建新版本，用户应能看到：

- **版本号**：递增的整数版本号
- **材料类型**：身份证、学历证明、工作证明、推荐信等
- **文件名和URL**：实际文件的存储位置
- **提交时间**：精确到秒的提交时间戳
- **提交者**：上传材料的用户ID
- **备注**：提交时的附加说明
- **是否最新**：当前是否为该类型材料的最新版本

**关键规则**：
- 同一类型材料可以多次提交，每次创建新版本
- 只有最新版本的 `is_latest` 标记为 TRUE
- 历史版本始终保留，用于审计和复查

### 2.2 第三方回执记录

每次第三方回调都会记录：

- **提供商名称**：背调机构名称
- **参考ID**：第三方系统的关联ID
- **回执类型**：初步确认、进度更新、最终报告等
- **状态**：第三方返回的状态信息
- **原始数据**：第三方返回的完整JSON数据
- **摘要**：人工可读的结果摘要
- **接收时间**：系统接收回调的时间

### 2.3 风险标签记录

每个风险标签应包含：

- **标签名称**：如"学历造假"、"工作经历不符"等
- **风险等级**：low（低）、medium（中）、high（高）、critical（严重）
- **描述**：风险的详细说明
- **来源**：third_party（第三方）或 manual（人工添加）
- **创建者**：添加标签的用户（人工添加时）
- **是否解决**：布尔值标记
- **解决时间**：标记为解决的时间
- **解决者**：解决风险的用户ID
- **解决说明**：如何解决该风险

### 2.4 审计日志记录

**必须记录的操作**：

| 操作类型 | 触发条件 | 记录内容 |
|----------|----------|----------|
| `TASK_CREATED` | 创建新任务 | 候选人信息、任务描述 |
| `STATUS_CHANGED` | 任务状态变更 | 旧状态、新状态、变更原因 |
| `SENT_TO_THIRD_PARTY` | 发送给第三方 | 提供商名称、超时时间、重试次数 |
| `DECISION_MADE` | 做出最终决策 | 决策结果（通过/拒绝）、决策原因 |
| `TASK_CANCELLED` | 取消任务 | 取消原因 |
| `RISK_TAG_ADDED` | 添加风险标签 | 标签详情 |
| `RISK_TAG_RESOLVED` | 解决风险标签 | 解决说明 |
| `TIMEOUT_HANDLING_FAILED` | 超时处理失败 | 错误信息 |

**每条日志包含**：
- 时间戳（精确到毫秒）
- 操作执行者（用户ID或system）
- 执行者类型（user/system）
- 关联的任务ID和候选人ID
- 操作前后的状态
- 详细的操作数据（JSON格式）
- 客户端IP地址（API调用时）

## 三、数据汇总能力

### 3.1 任务详情汇总

单个任务详情接口 (`GET /api/tasks/:taskId`) 应返回完整上下文：

```json
{
  "id": "task-uuid",
  "status": "pending_review",
  "candidate_name": "张三",
  "candidate_email": "zhangsan@example.com",
  "candidate_status": "in_progress",
  "materials": [
    {
      "material_type": "education",
      "version": 2,
      "is_latest": true,
      "file_name": "学历证明_v2.pdf",
      "submitted_at": "2026-05-09T10:30:00Z"
    }
  ],
  "third_party_receipts": [
    {
      "provider_name": "XXX背调公司",
      "status": "completed",
      "summary": "学历验证通过，工作经历部分需确认",
      "received_at": "2026-05-10T08:00:00Z"

    {
      "tag_name": "工作经历不符",

      "new_status": "pending_review",
```

### 3.2 按状态筛选任务

通过 `GET /api/tasks/status?status=pending_review` 可以获取特定状态的所有任务，便于：
- 查看待处理的任务队列
- 统计各状态的任务数量
- 批量处理相同状态的任务

### 3.3 时间线视图

审计日志按时间倒序排列，用户可以看到完整的任务时间线：
1. 任务创建
2. 材料需求提交
3. 材料提交（可能多次）
4. 发送第三方
5. 第三方回执
6. 风险标签添加
7. 决策或取消

## 四、异常场景处理

### 4.1 冲突处理

**触发条件**：
- 第三方背调发现材料与实际情况不符
- 不同材料之间存在矛盾信息
- 人工审核发现问题

**用户应看到**：
1. 任务状态变为 `conflict`
2. 自动添加对应的风险标签
3. 审计日志记录冲突详情
4. 候选人状态保持 `in_progress`

**解决路径**：
- 路径A：重新提交材料 → `materials_submitted` → 重新发送第三方
- 路径B：直接重新发送第三方（如第三方数据有误）
- 路径C：取消任务

### 4.2 撤销处理

**触发条件**：
- 候选人主动放弃
- 公司决定不继续招聘
- 发现候选人已接受其他offer

**用户应看到**：
1. 任务状态变为 `cancelled`（终态，不可逆转）
2. 候选人状态变为 `cancelled`
3. 记录取消原因和取消者
4. 审计日志完整记录

**关键规则**：
- 已完成（`completed`）的任务不能取消
- 已取消的任务不能重新激活
- 取消操作需要提供原因

### 4.3 超时处理

**触发条件**：
- 第三方背调机构未在配置的超时时间内（默认72小时）返回结果
- 后台定时任务每5分钟检查一次超时任务

**用户应看到**：
1. 任务状态变为 `timeout`
2. 记录超时发生的时间
3. `retry_count` 字段显示已重试次数

**处理规则**：
- 默认最大重试次数：3次
- 每次重试重新设置超时时间
- 超过最大重试次数后，只能选择取消或人工干预
- 重试时任务状态回到 `sent_to_third_party`

**后台任务失败表现**：
- 如果定时任务执行失败，错误会记录到审计日志
- 失败不影响其他任务的处理
- 下次定时任务（5分钟后）会再次尝试
- 持续失败需要人工检查数据库连接和系统状态

### 4.4 状态流转校验

**关键保护**：
- 所有状态变更必须经过状态机校验
- 无效的状态转换会返回明确的错误信息
- 例如：不能从 `completed` 状态回到 `pending_review`

**用户体验**：
- 前端应根据当前状态禁用无效操作
- API 层仍会二次校验，防止绕过前端
- 错误信息应说明为什么操作不可行

## 五、决策闭环

### 5.1 决策前置条件

只有满足以下条件才能做出决策：
1. 任务状态为 `pending_review`
2. 所有关键风险标签已解决或已评估
3. 至少有一份第三方最终回执

### 5.2 决策内容

决策必须包含：
- **决策结果**：`approved`（通过）或 `rejected`（拒绝）
- **决策原因**：必填的文字说明
- **决策者**：自动记录操作人ID
- **决策时间**：自动记录时间戳

### 5.3 决策后状态

- 任务状态变为 `completed`（终态）
- 候选人状态同步更新为 `approved` 或 `rejected`
- 所有关联数据锁定，不可修改
- 审计日志记录完整决策信息

## 六、审计与复查

### 6.1 不可修改性

以下数据一旦创建不可修改：
- 材料版本（只能新增版本，不能修改历史）
- 第三方回执（完整保留原始数据）
- 审计日志（追加写入，不可删除或修改）
- 风险标签的创建记录

### 6.2 复查支持

系统应支持：
1. **完整时间线**：通过审计日志查看所有操作
2. **版本对比**：查看材料的历史版本变化
3. **风险追踪**：风险标签从创建到解决的完整过程
4. **决策依据**：查看做出最终决策时的所有上下文

### 6.3 数据完整性

- 所有写入操作使用数据库事务
- 关键操作同时更新多个表时保证原子性
- 失败时自动回滚，不会产生半完成状态

## 七、API 接口清单

### 核心接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/tasks` | 创建背调任务 |
| GET | `/api/tasks/:taskId` | 获取任务详情（含所有关联数据） |
| GET | `/api/tasks/status` | 按状态筛选任务 |
| POST | `/api/tasks/:taskId/material-requirements` | 提交材料需求 |
| POST | `/api/tasks/:taskId/materials` | 提交候选人材料 |
| POST | `/api/tasks/:taskId/send-to-third-party` | 发送给第三方背调 |
| POST | `/api/tasks/:taskId/callback` | 第三方回调接口 |
| POST | `/api/tasks/:taskId/decision` | 做出最终决策 |
| POST | `/api/tasks/:taskId/cancel` | 取消任务 |
| POST | `/api/tasks/:taskId/risk-tags` | 添加风险标签 |
| POST | `/api/tasks/risk-tags/:tagId/resolve` | 解决风险标签 |

### 健康检查

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/health` | 服务健康状态检查 |

## 八、配置参数

| 参数 | 环境变量 | 默认值 | 说明 |
|------|----------|--------|------|
| 超时时间 | `BACKGROUND_CHECK_TIMEOUT_HOURS` | 72 | 第三方响应超时时间（小时） |
| 最大重试 | `MAX_RETRY_TIMES` | 3 | 超时后最大重试次数 |
| 服务端口 | `PORT` | 3000 | API服务端口 |
| 数据库主机 | `DB_HOST` | localhost | PostgreSQL主机 |
| 数据库端口 | `DB_PORT` | 5432 | PostgreSQL端口 |
| 数据库名 | `DB_NAME` | background_check | 数据库名称 |
