# 实时指标迟到修正服务 - 使用说明

## 一、系统概述

### 1.1 解决的问题

实时指标系统常见的矛盾：
- **榜单**：实时榜单根据当时数据生成，迟到事件到达后，旧榜单已被消费
- **告警**：基于不完整数据触发的告警，可能是误报
- **日报**：日报数据与修正后的实时数据不一致

### 1.2 核心设计

```
事件时间(event_time) → 迟到窗口检测 → 指标修正 → 告警撤销/榜单回放/修正报告
```

**核心规则：**
1. 以 `event_time`（事件发生时间）而非 `ingest_time`（接收时间）作为入口
2. `ingest_time - event_time > 迟到窗口` → 判定为迟到事件
3. 迟到事件自动触发修正流程
4. 人工修正后锁定（`is_manual_overridden=true`），后续计算不再覆盖
5. 所有查询默认返回最新版本（`is_latest=true`），保证一致性

### 1.3 数据模型

| 表名 | 说明 | 关键字段 |
|------|------|----------|
| `events` | 事件记录 | `event_time`, `is_late`, `status` |
| `metric_snapshots` | 指标快照（多版本） | `version`, `is_latest`, `is_manual_overridden` |
| `latency_windows` | 迟到窗口配置 | `metric_name`, `window_seconds` |
| `alerts` | 告警记录 | `status`, `revoked_time` |
| `rankings` | 榜单记录（多版本） | `version`, `is_latest`, `is_replayed` |
| `correction_reports` | 修正报告 | `source`, `affected_alerts`, `affected_rankings` |

## 三、核心能力详解

### 3.1 事件上报

**API：** `POST /api/events`

**请求参数：**
```json
{
  "event_id": "evt_001",
  "event_time": "2024-01-15T10:30:00Z",
  "metric_name": "sales_amount",
  "metric_value": 50000,
  "entity_id": "merchant_A",
  "dimensions": {"channel": "mobile"}
}
```

**关键设计：**
- `event_id` 用于幂等性，重复上报返回 `DUPLICATE` 状态
- `event_time` 是事件发生时间，用于计算迟到
- 系统自动计算 `latency_seconds = ingest_time - event_time`

**响应示例：**
```json
{
  "event_id": "evt_001",
  "status": "processed",
  "is_late": false,
  "message": "正常事件处理完成",
  "snapshot": {
    "value": 50000,
    "version": 1,
    "source": "real_time"
  }
}
```

### 3.2 迟到窗口配置

**API：**
- `GET /api/latency-windows` - 查询配置
- `POST /api/latency-windows` - 创建配置
- `PUT /api/latency-windows/{metric_name}` - 更新配置

**默认配置：**
| 指标 | 窗口 | 说明 |
|------|------|------|
| sales_amount | 3600秒（1小时） | 销售额 |
| order_count | 1800秒（30分钟） | 订单数 |
| conversion_rate | 7200秒（2小时） | 转化率 |

**判定逻辑：**
```python
is_late = (ingest_time - event_time).total_seconds() > window_seconds
```

### 3.3 指标快照（多版本）

**API：** `GET /api/metrics/snapshots`

**查询参数：**
- `is_latest_only=true`（默认）：只返回最新版本
- `is_latest_only=false`：返回所有历史版本

**关键保证：**
1. **后续统计**：使用 `is_latest=true` 的快照
2. **历史查询**：默认也返回 `is_latest=true`，保持一致
3. **需要对比时**：显式设置 `is_latest_only=false`

**快照版本示例：**
| version | value | source | is_latest | is_manual_overridden |
|---------|-------|--------|-----------|----------------------|
| 1 | 50000 | real_time | false | false |
| 2 | 130000 | late_event_correction | false | false |
| 3 | 200000 | manual | true | true |

### 3.4 人工修正

**API：** `POST /api/metrics/manual-correction`

**请求参数：**
```json
{
  "metric_name": "sales_amount",
  "entity_id": "merchant_A",
  "bucket_time": "2024-01-15T10:00:00Z",
  "new_value": 200000,
  "operator": "finance_admin",
  "reason": "财务对账发现漏记"
}
```

**发生了什么：**
1. 创建新版本快照（`version+1`）
2. 设置 `is_manual_overridden=true`
3. 后续迟到事件到达时，跳过自动计算
4. 检查并撤销不再满足条件的告警
5. 回放更新相关榜单
6. 生成修正报告供复查

### 3.5 告警管理

**API：**
- `GET /api/alerts` - 查询告警列表
- `GET /api/alerts/{alert_id}` - 查看详情
- `POST /api/alerts/{alert_id}/revoke` - 手动撤销

**告警状态：**
- `active`：活跃告警
- `revoked`：已撤销（自动或手动）
- `corrected`：修正后更新

**自动撤销逻辑：**
当指标值修正后不再满足告警规则时，系统自动：
1. 设置 `status = revoked`
2. 记录 `revoked_time`
3. 记录 `revoke_reason`

### 3.6 榜单回放

**API：**
- `GET /api/rankings` - 查询榜单
- `GET /api/rankings/compare/...` - 对比版本变化
- `POST /api/rankings/replay` - 手动回放

**自动回放场景：**
1. 迟到事件修正
2. 人工修正

**回放逻辑：**
1. 基于最新的指标快照重新计算排名
2. 旧版本 `is_latest=false`（归档）
3. 新版本 `is_latest=true, is_replayed=true`

**版本对比示例：**
```json
{
  "versions": [1, 2],
  "changes": [
    {
      "entity_id": "merchant_A",
      "old_rank": 2,
      "new_rank": 1,
      "rank_change": 1,
      "old_value": 150000,
      "new_value": 230000
    }
  ]
}
```

### 3.7 修正报告（复查审计）

**API：**
- `GET /api/correction-reports` - 查询报告列表
- `GET /api/correction-reports/{report_id}` - 查看详情
- `GET /api/correction-reports/by-entity/{entity_id}` - 实体修正历史

**报告内容：**
```json
{
  "report_id": "report_abc123",
  "correction_time": "2024-01-15T12:00:00Z",
  "metric_name": "sales_amount",
  "entity_id": "merchant_A",
  "original_value": 50000,
  "new_value": 130000,
  "source": "late_event",
  "affected_alerts": [1, 2],
  "affected_rankings": [3, 4, 5],
  "reason": "迟到事件修正，延迟 5400 秒"
}
```

**报告来源：**
- `late_event`：迟到事件自动触发
- `manual`：人工手动修正

## 四、问题排查指南

### 4.1 看到数据矛盾？

**第一步：检查是否有迟到事件**
```bash
curl "http://localhost:8000/api/events?is_late=true&limit=10"
```

**第二步：查看修正报告**
```bash
curl "http://localhost:8000/api/correction-reports?source=late_event"
```

**第三步：对比指标快照版本**
```bash
curl "http://localhost:8000/api/metrics/snapshots/{metric}/{entity}/{bucket_time}?is_latest_only=false"
```

### 4.2 告警是误报？

**第一步：查看告警详情**
```bash
curl "http://localhost:8000/api/alerts/{alert_id}"
```

**第二步：检查指标当前值**
```bash
curl "http://localhost:8000/api/metrics/latest/{metric}/{entity}"
```

**第三步：手动撤销（兜底）**
```bash
curl -X POST "http://localhost:8000/api/alerts/{alert_id}/revoke" \
  -H "Content-Type: application/json" \
  -d '{"reason": "人工确认是误报"}'
```

### 4.3 榜单排名不对？

**第一步：查看榜单当前版本**
```bash
curl "http://localhost:8000/api/rankings?ranking_type=daily&metric_name=sales_amount&ranking_date=2024-01-15"
```

**第二步：对比历史版本**
```bash
curl "http://localhost:8000/api/rankings/compare/daily/sales_amount/2024-01-15"
```

**第三步：手动回放（兜底）**
```bash
curl -X POST "http://localhost:8000/api/rankings/replay" \
  -H "Content-Type: application/json" \
  -d '{"ranking_type":"daily","metric_name":"sales_amount","ranking_date":"2024-01-15T00:00:00Z"}'
```

### 4.4 人工修正后还在变？

检查快照的 `is_manual_overridden` 字段：
```bash
curl "http://localhost:8000/api/metrics/latest/{metric}/{entity}?bucket_time=..."
```

如果是 `true`，后续事件不会覆盖。如果是 `false`，可能修正没有成功。

## 五、样例场景重现

### 场景1：正常处理

```bash
curl -X POST "http://localhost:8000/api/events" \
  -H "Content-Type: application/json" \
  -d '{
    "event_id": "test_normal_001",
    "event_time": "'"$(date -u -v-30M +%Y-%m-%dT%H:%M:%SZ)"'",
    "metric_name": "sales_amount",
    "metric_value": 50000,
    "entity_id": "merchant_A"
  }'
```

**预期：**
- `is_late: false`
- `status: processed`
- 创建版本 1 的快照

### 场景2：异常拦截

```bash
curl -X POST "http://localhost:8000/api/events" \
  -H "Content-Type: application/json" \
  -d '{
    "event_id": "test_abnormal_001",
    "event_time": "'"$(date -u -v-15M +%Y-%m-%dT%H:%M:%SZ)"'",
    "metric_name": "sales_amount",
    "metric_value": -1000,
    "entity_id": "merchant_A"
  }'
```

**预期：**
- `status: aborted`
- 消息包含"异常拦截：指标值为负数"

### 场景3：重复操作

```bash
# 第一次
curl -X POST "http://localhost:8000/api/events" \
  -H "Content-Type: application/json" \
  -d '{
    "event_id": "test_dup_001",
    "event_time": "'"$(date -u -v-45M +%Y-%m-%dT%H:%M:%SZ)"'",
    "metric_name": "sales_amount",
    "metric_value": 15000,
    "entity_id": "merchant_B"
  }'

# 第二次（相同event_id）
curl -X POST "http://localhost:8000/api/events" \
  -H "Content-Type: application/json" \
  -d '{
    "event_id": "test_dup_001",
    "event_time": "'"$(date -u -v-45M +%Y-%m-%dT%H:%M:%SZ)"'",
    "metric_name": "sales_amount",
    "metric_value": 15000,
    "entity_id": "merchant_B"
  }'
```

**预期：**
- 第二次返回 `status: duplicate`

### 场景4：迟到事件

```bash
curl -X POST "http://localhost:8000/api/events" \
  -H "Content-Type: application/json" \
  -d '{
    "event_id": "test_late_001",
    "event_time": "'"$(date -u -v-2H -v-30M +%Y-%m-%dT%H:%M:%SZ)"'",
    "metric_name": "sales_amount",
    "metric_value": 80000,
    "entity_id": "merchant_A"
  }'
```

**预期：**
- `is_late: true`
- 快照版本增加
- 生成修正报告

### 场景5：人工修正

```bash
BUCKET_TIME=$(date -u -v-1H +%Y-%m-%dT%H:00:00Z)

curl -X POST "http://localhost:8000/api/metrics/manual-correction" \
  -H "Content-Type: application/json" \
  -d '{
    "metric_name": "sales_amount",
    "entity_id": "merchant_A",
    "bucket_time": "'"${BUCKET_TIME}"'",
    "new_value": 200000,
    "operator": "admin_test",
    "reason": "测试人工修正"
  }'
```

**预期：**
- `is_manual_overridden: true`
- 生成来源为 `manual` 的修正报告

## 七、一致性保证机制

### 7.1 人工修正后的一致性

```
人工修正 → is_manual_overridden=true → 后续事件跳过自动计算
                                      → 查询始终返回人工修正值
```

### 7.2 历史查询一致性

```
所有查询默认 is_latest_only=true
  → 后续统计用最新值
  → 历史查询也用最新值
  → 不会出现"新数据用修正值，旧查询用原始值"的矛盾
```

### 7.3 多版本保留

需要对比时使用 `is_latest_only=false`：
- 审计追溯
- 问题排查
- 版本对比
