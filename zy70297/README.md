# 🔥 商户燃气安检整改台

餐饮商户燃气安全检查整改管理系统。围绕**软管、报警器、阀门**三类问题，实现安检发现问题、自动创建整改任务、复查预约、停气标记、监管报表的完整业务闭环。

---

## 📋 项目亮点（辨识度）

### 1. 核心业务规则（不同问题类型整改周期不同）

| 问题类型 | 严重程度 | 整改期限 | 说明 |
|---------|---------|---------|------|
| 🔴 **软管** (hose) | 危急 | **3天** | 老化、龟裂、超2米、私接三同等 |
| 🟠 **报警器** (alarm) | 重要 | **5天** | 未安装、过期失效、安装位置错误等 |
| 🔵 **阀门** (valve) | 一般 | **7天** | 锈蚀、泄漏、紧急切断阀失效等 |

### 2. 停气标记机制

- **自动停气**：连续 **2次** 复查不通过，系统自动执行停气
- **手动停气**：管理员可根据实际情况随时执行停气
- **恢复供气**：商户整改完成后可恢复供气，同时自动预约复查

### 3. 前后端同一套业务状态

后端定义 `RectificationStatus` 状态机，前后端严格共享：

```
created(待整改) 
  → scheduled_review(待复查) 
    → review_failed(复查不通过) → 可再次预约复查
    → completed(已完成)
    → gas_cut_off(已停气) → restore后回到scheduled_review
```

### 4. 状态可视化

- **当前卡点**：每个任务实时显示卡点（如"整改已逾期"、"复查已预约"、"已停气"）
- **处理建议**：根据状态和逾期天数智能生成建议（紧急/高/中/低优先级）
- **历史变化**：完整的状态变更时间线，记录操作员、时间、原因

## 🚀 启动命令

### 1. 安装依赖

```bash
npm install
```

### 2. 启动开发环境（前后端同时启动）

```bash
npm run dev
```

- 前端地址：http://localhost:5173
- 后端地址：http://localhost:3001

### 3. 单独启动后端

```bash
cd backend && npm run dev
```

### 4. 重置样本数据（后端启动时自动加载，也可手动执行）

```bash
cd backend && npm run seed
```

### 5. 运行测试

```bash
npm run test
```

## 🎬 主流程演示

### 场景：从安检到整改完成的完整闭环

1. **进入监管报表页**（首页）
   - 查看整体统计：4家商户、2家整改中、1家已停气、4个逾期任务
   - 风险预警清单按优先级排序，紧急任务置顶

2. **查看商户档案**
   - 点击"商户档案"导航
   - 筛选"已停气"状态，看到"香辣小龙虾"
   - 点击进入详情，查看安检记录和整改任务

3. **新增安检（演示整改任务自动创建）**
   - 进入"快捷面馆"详情页
   - 点击"新增安检"按钮
   - 填写：安检员=测试员、问题类型=软管、描述=测试软管问题
   - 提交后系统**自动创建整改任务**，整改期限3天

4. **复查预约与完成**
   - 进入"粤式茶餐厅"的阀门整改任务详情
   - 点击"预约复查"，填写日期和复查员
   - 点击"完成复查"，选择"不通过"
   - **注意**：系统提示"第2次复查不通过将自动触发停气"

5. **观察停气标记**
   - 查看"香辣小龙虾"任务详情
   - 状态变更历史显示：2次复查不通过 → 自动停气
   - 页面有明显的红色停气警示

## ⚠️ 异常操作演示

### 异常1：非待复查状态不能完成复查

**操作**：在`created`状态的任务上尝试调用"完成复查"接口

**结果**：
- 前端："完成复查"按钮**不显示**（仅`scheduled_review`状态显示）
- 后端：API返回 `404`，错误信息"整改任务不存在或状态不允许完成复查"

**验证**：查看单元测试 `非scheduled_review状态不能完成复查`

---

### 异常2：非停气状态不能恢复供气

**操作**：在`created`状态的任务上尝试"恢复供气"

**结果**：
- 前端："恢复供气"按钮**不显示**（仅`gas_cut_off`状态显示）
- 后端：API返回 `404`，错误信息"整改任务不存在或当前状态不允许恢复供气"

**验证**：查看单元测试 `非停气状态不能恢复供气`

---

### 异常3：连续2次复查不通过自动停气

**操作**：
1. 创建整改任务 → 预约复查 → 复查不通过（第1次）
2. 再次预约复查 → 复查不通过（第2次）

**结果**：
- 第2次不通过时，系统**自动将状态改为`gas_cut_off`**
- API响应包含 `gasCutOffTriggered: true`
- 商户状态同步更新为`gas_cut_off`

**验证**：
- 单元测试 `连续2次复查不通过应执行停气`
- API响应 `/api/reports` 中 `gasCutOffMerchants: 1`（香辣小龙虾）

## 🔌 核心API接口

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/merchants | 商户列表 |
| GET | /api/merchants/:id | 商户详情（含安检记录+整改任务） |
| POST | /api/inspections | 提交安检记录（自动创建整改任务） |
| GET | /api/rectification-tasks | 整改任务列表 |
| GET | /api/rectification-tasks/:id | 任务详情（含历史变更） |
| POST | /api/rectification-tasks/:id/schedule-review | 预约复查 |
| POST | /api/rectification-tasks/:id/complete-review | 完成复查（可能触发自动停气） |
| POST | /api/rectification-tasks/:id/cut-off-gas | 手动停气 |
| POST | /api/rectification-tasks/:id/restore-gas | 恢复供气 |
| GET | /api/reports | 监管报表（含业务规则） |
| GET | /api/health | 健康检查 |

## 📝 技术栈

### 后端
- **框架**：Express + TypeScript
- **数据存储**：内存存储（方便原型演示，可随时替换为数据库）
- **测试**：Vitest

### 前端
- **框架**：React 18 + TypeScript
- **构建**：Vite
- **路由**：React Router
- **样式**：纯CSS（无UI框架依赖，轻量）

### 特色
- 使用 npm workspaces 管理前后端
- 前后端共享相同的类型定义（可提取为公共包）
- 纯内存数据，启动即有样本数据，零配置运行
