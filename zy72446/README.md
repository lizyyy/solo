# 巡演酒店房型联动系统

追踪合同截图 → 曲目别名 → 房型联动的完整证据链。解决"同一首歌有现场名和版权名"时，回头找证据断链的问题。

## 快速开始

```bash
npm install
npm start
# 打开 http://localhost:3000
```

## 核心设计原则

> **结论要能追到证据，而不是只看一个汇总数。**

## 三步标准工作流

每一条合同截图记录，必须走完以下三步，缺一不可：

| 步骤 | 角色 | 操作 | 系统行为 |
|------|------|------|----------|
| 1 | 巡演统筹阿梅 | 导入合同页截图 | 保留原始行号、来源文件、文件哈希 |
| 2 | 巡演统筹阿梅 | 核对曲目别名表 | 自动匹配别名，检测名称冲突 |
| 3 | 巡演统筹阿梅 | 更新店长周报 | 汇总数据，带状态标记导出 |

## 边界规则（写在代码里，不是口头约定）

### 规则1：同一首歌有现场名和版权名 → 不准自动归"正常"

**触发条件**：
- 歌曲名同时匹配到 `alias_type = 'live_name'` 和 `alias_type = 'copyright_name'` 的两条别名记录
- 或匹配到多个不同的规范名（canonical_name）

**系统行为**：
- 联动状态强制设为 `pending_review`（待复核）
- 写入 `conflict_detail` 字段，记录具体匹配到了哪些别名
- 店长周报里这行会单独标记，音乐老师不复核就不能给店长

**复核操作**：
- 音乐老师二选一：`confirm_normal`（确认正常）或 `mark_conflict`（标记冲突）
- 复核意见和操作人永久记录在操作历史里

### 规则2：重复导入同一批合同 → 数量不准翻倍

**去重逻辑**（三层保护）：
1. 计算整批文件的 MD5 哈希（`file_hash`）
2. 同一批次内按 `原始行号 + 文件哈希` 做唯一约束
3. `INSERT OR IGNORE` 重复数据直接跳过，不报错

**结果**：
- 同一批文件导 100 次也只会有 1 份数据
- 导入接口返回 `imported_rows` 和 `duplicate_rows` 两个数

### 规则3：任何修改必须留痕（改前改后都看得到）

**所有写入操作都走 `recordHistory()`**：
- 合同截图的创建、备注修改
- 房型联动的创建、状态变更
- 工作流步骤的推进
- 曲别别名的添加

**历史记录包含**：
- `entity_type` / `entity_id`：改的哪条数据
- `field_name`：改的哪个字段
- `old_value` / `new_value`：改前改后的值
- `operator`：谁改的
- `created_at`：什么时候改的
- `operation_note`：改的时候写了啥备注

### 规则4：曲目别名表是唯一真值来源

**优先级**：曲目别名表 > 合同页截图

**别名匹配逻辑**：
1. 先精确匹配 `alias_name`（别名）
2. 再匹配 `canonical_name`（规范名本身）
3. 都没匹配到 → 状态 `no_alias`，等阿梅补录别名

**添加别名的副作用**：
- 新增一条别名后，自动触发所有相关歌曲的联动重算
- 之前 `no_alias` 的可能变成 `normal` 或 `pending_review`

### 规则5：回滚靠历史，不靠删数据

**不支持物理删除**：
- 所有表都没有 DELETE 接口
- 别名表用 `is_active` 软删除
- 改错了就再改一次，操作历史里能看到完整轨迹

**怎么回滚**：
1. 去操作历史里看改之前的值是啥
2. 手动改回去，系统自动记录这次"回滚操作"

## 数据模型

### contract_screenshots（合同页截图原始数据）

| 字段 | 说明 | 为什么要有 |
|------|------|------------|
| `original_row_number` | 合同页上的原始行号 | 音乐老师追问时，能直接翻到合同第几行 |
| `import_batch_id` | 导入批次号 | 追溯这堆数据是哪次导入的 |
| `file_hash` | 文件内容哈希 | 去重用，防止重复导入 |
| `source_file` | 原始文件名 | 知道数据来自哪个截图文件 |
| `status` | 合同状态 | imported / confirmed |

### song_aliases（曲目别名表）

| 字段 | 说明 | 可选值 |
|------|------|--------|
| `canonical_name` | 规范歌名（版权名） | - |
| `alias_name` | 别名 | - |
| `alias_type` | 别名类型 | `live_name` 现场名 / `copyright_name` 版权名 / `other` 其他 |
| `source` | 来源 | 曲目别名表V3 / 版权合同 / ... |
| `is_active` | 是否有效 | 1 有效 / 0 软删除 |

### room_linkages（房型联动结果）

| 状态 | 说明 | 谁来处理 |
|------|------|----------|
| `pending` | 刚导入，还没匹配 | 系统自动处理 |
| `no_alias` | 曲目别名表里找不到 | 阿梅补录别名 |
| `pending_review` | 检测到名称冲突 | 音乐老师复核 |
| `normal` | 联动正常 | - |
| `name_conflict` | 音乐老师确认有冲突 | - |

### operation_history（操作历史）

所有变更的审计日志，**永不可删**。

## API 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/import/csv` | 导入CSV格式的合同截图 |
| POST | `/api/import/json` | 导入JSON格式的合同截图 |
| GET | `/api/contracts` | 合同截图列表 |

| GET | `/api/weekly-report` | 店长周报数据 |

## 交接体验说明

**音乐老师打开结果时，不用问阿梅，就能知道卡在哪**：

1. **房型联动页面** - 一眼看到哪些是 `pending_review`
2. **点"查看证据"** - 弹出详情页，顶部三个工作流步骤：
   - 绿色 = 已完成
   - 灰色 = 还没做
3. **冲突详情** - 黄色高亮框，写清楚匹配到了啥冲突
4. **操作历史** - 下面列着谁什么时候改了啥，改前改后都有

**典型场景：七里香的现场名 vs 版权名**

1. 阿梅导入合同，行号3写的是"七里香 (Live)"，行号7写的是"七里香"
2. 阿梅去曲目别名表加了两条：
   - 七里香 → 七里香 (Live) → 现场名
   - 七里香 → 七里香 → 版权名
3. 系统自动检测到：同一首歌同时有现场名和版权名
4. 联动状态变成 `pending_review`，不会偷偷归 normal
5. 音乐老师打开系统，看到黄色标记，点进去看匹配详情
6. 音乐老师复核，选"确认正常"或"标记冲突"，写意见
7. 操作历史永久记录这次复核，以后谁问都能翻出来

## 常见问题

**Q: 阿梅只改了一条备注，历史里能看出来吗？**
A: 能。`updateContractRemarks()` 会记录 old_value 和 new_value，diff 一目了然。

**Q: 同一批合同导了两遍，房间数会翻倍吗？**
A: 不会。文件哈希 + 原始行号做唯一约束，重复的直接 IGNORE。

**Q: 音乐老师复核完，阿梅能看到复核意见吗？**
A: 能。操作历史里有，联动记录的 review_note 字段也存了。

**Q: 歌名冲突了，系统会自动选一个吗？**
A: **绝对不会**。必须等音乐老师人工复核，系统不替人做决定。
