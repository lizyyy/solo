# 数据血缘变更 API - 自然语言验收点

## 一、主流程验收

### 1.1 表字段版本管理

**验收点 1：创建表时自动生成初始版本**
- 操作：调用 POST /tables 创建新表，包含字段定义
- 预期：
  - 表元数据创建成功，current_version = 1
  - 自动生成一条 version = 1 的 TableFieldVersion 记录
  - 版本包含完整的字段定义和 hash_value
  - 操作历史记录中出现 CREATE 类型记录，entity_type = TableMetadata

**验收点 2：新增字段生成新版本**
- 操作：
  1. 创建表 A，包含字段 id, name
  2. 创建字段变更请求：新增字段 age (integer)
  3. 提交审核 → 批准 → 应用
- 预期：
  - 生成 version = 2 的新版本
  - 新版本包含 3 个字段 (id, name, age)
  - 旧版本 is_active = false
  - 表的 current_version 变为 2
  - 两个版本的 hash_value 不同

**验收点 3：版本对比准确识别差异**
- 操作：
  1. 创建表，初始版本有 2 个字段
  2. 修改 1 个字段类型，新增 1 个字段，删除 1 个字段
  3. 对比版本 1 和版本 2
- 预期：
  - POST /tables/compare-versions 返回：
    - added_fields 包含新增字段
    - removed_fields 包含删除字段
    - modified_fields 包含修改字段，附带 old 和 new
    - unchanged_fields 包含未修改字段

### 1.2 血缘图与影响分析

**验收点 4：下游影响链路分析正确**
- 操作：
  1. 创建表 A、B、C
  2. 建立血缘关系：A → B → C (通过 job1 和 job2)
  3. 查询 GET /lineage/downstream/{A的id}
- 预期：
  - 返回的下游表包含 B 和 C
  - B 的 path_length = 1，C 的 path_length = 2
  - relevant_jobs 包含对应的 job_id

**验收点 5：关键变更标记为高风险**
- 操作：
  1. 创建表，建立下游依赖（多个下游表）
  2. 创建变更请求：删除一个关键字段
  3. 提交审核触发影响分析
- 预期：
  - 影响分析中 is_critical = true
  - risk_level = 'high'
  - summary 明确说明高风险原因

**验收点 6：指标口径影响识别**
- 操作：
  1. 创建表 A，字段 amount
  2. 创建指标 M1，定义为 SUM(amount)，来源表为 A
  3. 创建变更请求修改表 A 的 amount 字段类型
  4. 提交审核触发分析
- 预期：
  - 影响分析的 impacted_metrics 包含 M1
  - M1 的 calculation_logic 和 owner 信息正确

### 1.3 订阅告警

**验收点 7：订阅者在变更批准后收到告警**
- 操作：
  1. 创建表 T
  2. 用户 A 订阅表 T
  3. 创建变更请求 → 提交 → 批准
- 预期：
  - Alert 表中出现一条记录
  - subscriber_id = 用户 A
  - status = PENDING（待发送）
  - alert_type = 'change_approved'
  - title 和 message 包含变更字段名和请求 ID

**验收点 8：同一表多个订阅者都收到告警**
- 操作：
  1. 用户 A、B、C 都订阅表 T
  2. 批准一个变更请求
- 预期：生成 3 条 Alert 记录，分别对应 3 个订阅者

### 1.4 回滚机制

**验收点 9：回滚恢复到前一版本**
- 操作：
  1. 初始版本 1：字段 [id, name]
  2. 应用变更到版本 2：新增字段 age
  3. 执行回滚
- 预期：
  - 变更请求状态变为 ROLLED_BACK
  - 表的 current_version 恢复为 1
  - 版本 1 的 is_active = true
  - 版本 2 的 is_active = false
  - 操作历史中出现 ROLLBACK 记录

**验收点 10：回滚需要填写原因**
- 操作：调用回滚接口但未提供 reason
- 预期：返回错误，必须填写回滚原因

**验收点 11：不能回滚未应用的变更**
- 操作：创建变更请求但不应用，直接调用回滚
- 预期：返回错误，提示只有 APPLIED 状态的变更才能回滚

**验收点 12：不能回滚已回滚的变更**
- 操作：
  1. 应用变更
  2. 回滚成功
  3. 再次调用回滚同一请求
- 预期：返回错误，状态检查失败

## 二、异常场景验收

### 2.1 状态机校验

**验收点 13：DRAFT → PENDING_REVIEW 是唯一合法路径（提交审核）**
- 操作：
  - 已提交的请求（PENDING_REVIEW）再次提交
  - 已批准的请求（APPROVED）尝试提交
- 预期：都返回错误，只有 DRAFT 才能提交

**验收点 14：必须先审核才能应用**
- 操作：DRAFT 状态的变更直接调用 apply
- 预期：错误，必须先 approved

**验收点 15：状态不可逆**
- 操作：
  - 提交审核后，不能撤回为 DRAFT
  - 批准后，不能撤回为 PENDING_REVIEW
  - 应用后，不能撤回为 APPROVED
- 预期：所有状态回退操作都失败

### 2.2 字段操作合法性

**验收点 16：不能删除不存在的字段**
- 操作：创建删除字段请求，但字段名不存在
- 预期：错误，字段不存在

**验收点 17：不能新增已存在的字段**
- 操作：创建新增字段请求，但字段名已存在
- 预期：错误，字段已存在

**验收点 18：不能修改不存在的字段**
- 操作：修改不存在的字段
- 预期：错误，字段不存在

**验收点 19：重命名必须提供新名称**
- 操作：创建 rename 请求但 new_value 中没有 new_name
- 预期：错误，重命名操作需要提供 new_name

### 2.3 重复操作防护

**验收点 20：不能创建重复的表**
- 操作：使用相同的 database.schema.table 创建两次
- 预期：第二次失败，表已存在

**验收点 21：重复订阅自动激活（不报错）**
- 操作：同一 subscriber_id 对同一表订阅两次
- 预期：第二次订阅不报错，而是更新 is_active = true 以及其他属性

### 2.4 边界情况

**验收点 22：空血缘图不报错**
- 操作：表没有任何下游依赖，提交变更请求
- 预期：影响分析正常执行，impacted_tables = []

**验收点 23：复杂血缘图（多路径）正确识别**
- 操作：
  - A → B → D
  - A → C → D
  - 分析 A 的下游
- 预期：D 被识别，path_length 取最小值

## 三、数据一致性验收

### 3.1 版本一致性

**验收点 24：同一批数据重跑结果稳定（hash 一致性）**
- 操作：
  1. 相同字段定义创建两个独立的表实例
  2. 分别调用 generate_hash 计算
- 预期：两个 hash 完全相同

**验收点 25：字段顺序不影响版本识别**
- 操作：
  1. 版本 1：字段顺序 [id, name, amount]
  2. 版本 2：字段顺序 [id, amount, name]，内容完全相同
- 预期：
  - 如果 hash 基于有序字段列表（按 position 或按插入顺序），则 hash 不同
  - 如果是字段级别的变更，compare_versions 应识别为 unchanged

**验收点 26：版本号递增且不重复**
- 操作：连续应用多次变更
- 预期：版本号 1 → 2 → 3 → ... 单调递增，无跳跃无重复

### 3.2 历史记录完整性

**验收点 27：所有关键操作都有历史记录**
- 操作：
  - 创建表
  - 创建变更请求
  - 提交审核
  - 批准
  - 应用
  - 回滚
- 预期：每个步骤在 OperationHistory 表中都有对应记录，包含：
  - operation_type
  - entity_type 和 entity_id
  - old_state 和 new_state（状态变更类操作）
  - operation_by 和 operation_at

**验收点 28：回滚的历史可追溯**
- 操作：
  1. 应用变更
  2. 回滚，填写原因 "发现问题"
- 预期：
  - 变更请求的 rollback_reason = "发现问题"
  - rollback_by 和 rollback_at 有值
  - 操作历史中 ROLLBACK 记录的 comment 包含原因

### 3.3 并发与一致性

**验收点 29：同一时刻只有一个激活版本**
- 操作：查询同一表的所有版本
- 预期：任何时刻，is_active = true 的版本数量 = 1

**验收点 30：应用变更原子性**
- 操作：模拟应用变更过程（涉及多表更新）
  - 旧版本 is_active = false
  - 创建新版本
  - 更新表的 current_version
  - 更新变更请求状态
- 预期：要么全部成功，要么全部失败（事务保证）

### 3.4 关键字段变更判定

**验收点 31：删除字段是关键变更**
- 操作：任何 REMOVE 类型变更
- 预期：is_critical = true

**验收点 32：重命名字段是关键变更**
- 操作：任何 RENAME 类型变更
- 预期：is_critical = true

**验收点 33：类型不兼容变更为关键**
- 操作：修改字段类型 string → integer
- 预期：is_critical = true

**验收点 34：兼容类型变更不是关键**
- 操作：integer → bigint，float → double
- 预期：is_critical = false

**验收点 35：可空变非空是关键**
- 操作：nullable: true → false
- 预期：is_critical = true

**验收点 36：新增字段不是关键**
- 操作：ADD 类型变更
- 预期：is_critical = false

### 3.5 风险等级计算

**验收点 37：关键变更高风险**
- 操作：is_critical = true 的变更
- 预期：risk_level = 'high'

**验收点 38：影响范围大是高风险**
- 操作：影响 > 20 个下游实体（表 + 任务 + 指标）
- 预期：risk_level = 'high'

**验收点 39：中等影响是中风险**
- 操作：影响 6-20 个下游实体
- 预期：risk_level = 'medium'

**验收点 40：小影响是低风险**
- 操作：影响 <= 5 个下游实体，且非关键变更
- 预期：risk_level = 'low'

## 四、普通使用者操作指南

### 4.1 我想修改一个表字段，应该怎么做？

**标准流程：**
1. **确认表信息**
   - 调用 GET /tables 查找你的表
   - 记录 table_id

2. **查看当前版本**
   - 调用 GET /tables/{table_id}/versions
   - 查看最新版本的字段定义

3. **创建变更请求**
   - 调用 POST /change-requests
   - 选择变更类型：add / remove / modify / rename
   - 填写 field_name 和必要的 new_value
   - 必须填写 reason（原因）

4. **提交审核**
   - 调用 POST /change-requests/{id}/submit
   - 系统会自动进行影响分析

5. **查看影响分析**
   - 调用 GET /change-requests/{id}/impact-analysis
   - 检查哪些下游表、任务、指标会受影响
   - 查看风险等级

6. **审批变更**
   - 审批人调用 POST /change-requests/{id}/approve
   - 订阅者会收到告警

7. **应用变更**
   - 调用 POST /change-requests/{id}/apply
   - 系统生成新版本，旧版本失效

8. **出错了？回滚**
   - 调用 POST /change-requests/{id}/rollback
   - 必须填写回滚原因
   - 系统恢复到前一版本

### 4.2 我想知道某个字段变更会影响什么？

**操作步骤：**
1. 创建变更请求（状态 DRAFT）
2. 提交审核（调用 submit）
3. 立即查看 impact-analysis

**重点关注：**
- `impacted_tables`：哪些下游表会受影响
- `impacted_jobs`：哪些 ETL 任务可能失败
- `impacted_metrics`：哪些指标口径需要核对
- `risk_level`：风险等级（high/medium/low）

### 4.3 我想订阅某个表的变更通知？

**操作步骤：**
1. 查找表的 table_id
2. 调用 POST /subscriptions
3. 填写：
   - table_id
   - subscriber_id（你的用户 ID）
   - subscriber_email（可选）
   - notification_channel（默认 email）

**后续：**
- 当表的任何变更被 APPROVE 时，你会收到告警
- 调用 GET /alerts?subscriber_id={你的ID} 查看所有告警

### 4.4 我想对比两个版本有什么区别？

**操作步骤：**
1. 调用 POST /tables/compare-versions
2. 填写：
   - table_id
   - version1（如 1）
   - version2（如 3）

**返回结果说明：**
- `added_fields`：新增的字段
- `removed_fields`：删除的字段
- `modified_fields`：修改的字段，包含 old 和 new
- `unchanged_fields`：未修改的字段

### 4.5 我想查看历史操作记录？

**操作步骤：**
1. 调用 GET /operation-history
2. 可选过滤条件：
   - entity_type：如 "FieldChangeRequest"
   - entity_id：如变更请求的 ID
   - batch_id：批次 ID（如果是批量操作）

**可追踪的操作类型：**
- CREATE：创建
- SUBMIT：提交审核
- APPROVE：批准
- APPLY：应用
- ROLLBACK：回滚
