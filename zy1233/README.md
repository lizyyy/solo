# 🐍 Python GIL 机制演练台

一个交互式的 Python 全局解释器锁（GIL）行为模拟平台，让你能够可视化地理解 GIL 如何影响多线程程序的执行。

## ✨ 功能特性

### 核心模拟场景
- **CPU 密集型工作负载**: 模拟纯 Python 字节码执行，观察经典 GIL 行为
- **I/O 阻塞场景**: 模拟线程进行 I/O 操作时主动释放 GIL
- **C 扩展 GIL 释放**: 模拟 C 扩展在执行长时间运算时主动释放 GIL
- **锁竞争场景**: 模拟多线程竞争同一把锁的 convoy effect

### 可配置参数
- **线程数**: 1-32 个线程
- **切换间隔**: 控制 GIL 抢占阈值
- **总指令数**: 模拟执行的字节码数量
- **随机种子**: 支持可复现的实验

### 数据可视化
- **时间线视图**: 直观展示 GIL 获取/释放、抢占、I/O 等待等事件
- **统计卡片**: 显示总指令数、吞吐率、GIL 事件统计
- **线程进度条**: 对比各线程的指令执行量和等待时间
- **风险分析**: 智能分析配置可能带来的性能问题

### 数据持久化与交换
- **SQLite 存储**: 所有实验自动保存到本地数据库
- **JSON 导出**: 导出完整实验数据用于分析
- **Markdown 导出**: 生成结构化的实验报告
- **JSONL 导入**: 导入外部的 `gil-events.jsonl` 文件进行分析

## 📖 使用指南

### 配置实验

1. **工作负载类型**: 选择要模拟的场景（可多选）
   - CPU 密集型: 模拟纯 Python 计算
   - I/O 阻塞: 模拟网络/文件 I/O
   - C 扩展释放 GIL: 模拟 numpy/pandas 等库的行为
   - 锁竞争: 模拟多线程争用共享资源

2. **调整参数**:
   - 线程数: 建议 2-8 个线程观察 GIL 行为
   - 切换间隔: 默认 0.005 秒，增大可减少上下文切换
   - 总指令数: 更多指令 = 更详细的统计

3. **随机种子**: 输入相同种子可复现完全相同的实验结果

### 解读结果

#### 统计卡片
- **总指令数**: 执行的字节码总数
- **总耗时**: 实际运行时间
- **吞吐率**: 每秒执行的指令数
- **GIL 获取次数**: 线程成功获取 GIL 的次数
- **抢占次数**: 因时间片用完被强制切换的次数
- **I/O 等待**: 线程因 I/O 阻塞的次数
- **锁等待**: 线程因等待锁而阻塞的次数

#### 线程统计
- **指令执行**: 显示每个线程执行了多少指令
  - 如果各线程分配不均，可能是 GIL 调度或 I/O 阻塞导致
- **等待时间**: 显示每个线程等待 GIL 的时间
  - 高等待时间 = 严重的 GIL 竞争

#### 时间线视图
点击时间线中的事件块可查看详细信息：
- 🟢 **绿色**: GIL 获取
- 🔴 **红色**: GIL 释放
- 🟠 **橙色**: 抢占（时间片用完）
- 🟣 **紫色**: I/O 等待
- 🔵 **蓝色**: 普通指令执行

#### 风险分析
根据你的配置，系统会自动提示潜在问题：
- 高线程数可能导致过度上下文切换
- CPU 密集型 + 多线程 = 无并行加速（反而更慢）
- 锁竞争 + 多线程 = convoy effect

## 🔬 GIL 行为解释

### 什么是 GIL？

GIL (Global Interpreter Lock) 是 CPython 中的一个互斥锁，确保同一时刻只有一个线程执行 Python 字节码。这简化了 CPython 的实现，但也限制了多线程程序的并行能力。

### GIL 何时释放？

1. **时间片抢占**: 每执行一定数量的字节码（默认 ~100 条），当前线程会被检查是否需要让出 GIL
2. **I/O 阻塞**: 当线程进行 I/O 操作（网络请求、文件读写）时，会主动释放 GIL
3. **C 扩展释放**: 某些 C 扩展（如 numpy）在执行长时间计算时会主动释放 GIL

### 常见场景分析

| 场景 | GIL 行为 | 实际效果 |
|------|----------|----------|
| 单线程 CPU 密集 | GIL 一直被持有 | 正常执行 |
| 多线程 CPU 密集 | 频繁抢占切换 | 比单线程更慢（切换开销） |
| 多线程 I/O 密集 | I/O 时释放 GIL | 接近并行（其他线程可执行） |
| 使用 C 扩展 | 计算时释放 GIL | 真正的并行计算 |

## 🎯 推荐实验

### 实验 1: 理解 GIL 对 CPU 密集型的影响

**配置**:
- CPU 密集型: ✅
- 线程数: 4
- 总指令数: 10000

**观察**:
- 对比单线程和多线程的吞吐率
- 注意多线程反而更慢（切换开销）
- 查看时间线中的抢占事件

**结论**: CPU 密集型任务不应使用多线程，应使用 multiprocessing 或 C 扩展。

### 实验 2: I/O 密集型的优势

**配置**:
- CPU 密集型: ✅
- I/O 阻塞: ✅
- 线程数: 8
- 总指令数: 5000

**观察**:
- 线程在 I/O 等待时释放 GIL
- 其他线程可以在等待期间执行
- 时间线中会看到大量紫色（I/O 等待）和绿色（GIL 获取）交替

**结论**: I/O 密集型任务受益于多线程，因为 GIL 在等待时被释放。

### 实验 3: 锁竞争的 convoy effect

**配置**:
- CPU 密集型: ✅
- 锁竞争: ✅
- 线程数: 8
- 总指令数: 10000

**观察**:
- 高锁等待计数
- 线程等待时间显著增加
- 这就是 "convoy effect" - 等待锁的线程也占据 GIL 等待队列位置

**结论**: 减少锁竞争，使用更细粒度的锁或无锁数据结构。

### 实验 4: 使用相同种子复现结果

**配置**:
- 任意配置
- 种子: 42

**观察**:
- 运行两次相同配置（相同种子）
- 结果应该完全一致

**结论**: 种子确保了实验的可复现性，方便调试和对比。

## 📝 事件类型

模拟器记录以下事件类型：

| 事件类型 | 描述 |
|----------|------|
| `gil_acquire` | 线程成功获取 GIL |
| `gil_release` | 线程释放 GIL |
| `preemption` | 线程因时间片用完被抢占 |
| `io_wait` | 线程开始 I/O 等待 |
| `io_wake` | 线程从 I/O 等待中唤醒 |
| `lock_acquire` | 线程成功获取锁 |
| `lock_wait` | 线程开始等待锁 |
| `instruction` | 执行单条字节码 |
| `gil_release_c_extension` | C 扩展主动释放 GIL |
