# 考试缓考审批 API 验收规则

## 一、整体验收思路

普通使用者按以下步骤走，就能知道系统做对了没有：

1. **先看状态对不对**：一条申请从"草稿"到"待审核"再到"已通过"或"已拒绝"，中间不能跳步，也不能倒着走（除了撤回这种特殊场景）。
2. **再查记录全不全**：谁提交的、谁审核的、为什么通过/拒绝、什么时候改的成绩，这些都要有痕迹可查。
3. **最后算汇总准不准**：汇总报表上的数字，要能和你一条条数出来的对得上。

如果某一步对不上，就按"下一步该查哪里"的提示去查日志或相关数据。

---

## 二、核心动作验收

### 1. 缓考申请

**应该看到的状态：**
- 学生刚填完还没提交：状态是「草稿 (draft)」。
- 学生点了提交：状态变成「待审核 (pending_review)」。
- 教务同意了：状态变成「已通过 (approved)」。
- 教务不同意：状态变成「已拒绝 (rejected)」。

**应该留下的记录：**
- 学生提交那一刻，会有一条「submit」类型的审计日志。
- 教务审核那一刻，会有一条「approve」或「reject」类型的审计日志，上面记着审核人 ID 和审核意见（如果有写）。

**验收现象：**
- 把同一个申请从草稿提交两次，第二次会报错，说"只有草稿状态的申请可以提交"。
- 把已经通过的申请再提交一次，也会报错。

**下一步该查哪里：**
- 如果状态不对 → 查 `/applications/{id}` 的返回，确认当前状态字段。
- 如果看不到审核意见 → 查 `/audit/logs?resource_type=DeferralApplication&resource_id={id}`，看那条 approve 日志里的 `review_comment`。

---

### 2. 资格校验

**应该看到的结果：**
- 校验接口返回一个 `eligible` 字段，`true` 表示可以申请，`false` 表示不行。
- 不行的话，`reasons` 数组里会告诉你为什么（比如"已存在有效缓考申请"、"成绩已锁定"等）。
- 虽然可以申请但需要注意的，`warnings` 数组里会提醒（比如"这是补考，不能再缓考"、"该学生本学期已申请过 3 次"）。

**验收现象：**
- 同一学生对同一考试，如果已经有一条"待审核"或"已通过"的申请，再校验会返回 `eligible: false`。
- 如果考试状态不是"已排期 (scheduled)"，也会返回 `eligible: false`。
- 如果成绩已经"锁定"或"已发布"，也会返回 `eligible: false`。

**下一步该查哪里：**
- 想看该学生还有哪些申请 → 查 `/applications?student_id={id}`。
- 想看该学生这门课的成绩 → 查 `/scores?student_id={id}&exam_id={exam_id}`。

---

### 3. 考场重排（补考分配）

**应该看到的状态：**
- 刚通过审核还没分配考场：申请状态是「已通过 (approved)」。
- 分配完补考考场后：申请状态变成「已排期 (rescheduled)」，并且 `assigned_makeup_exam_id` 字段有了一个值。
- 原考试里这位学生的成绩：状态变成「缺考 (absent)」（因为他要去考补考了）。
- 考试表中会多一条 `is_makeup: true` 的记录，`related_original_exam_id` 指向原考试。

**应该留下的记录：**
- 每分配一个申请，会有一条「reschedule」类型的审计日志，记录从哪个状态变到哪个状态、分配到了哪个考场。
- 创建补考考场时，会有一条「makeup_create」类型的审计日志，记着日期、教室、参与人数。

**验收现象（幂等性验证）：**
- 把同一批申请（application_ids 一样）、同一时间地点再跑一次：
  - **不会**创建新的补考考场（因为已存在同样日期、时间、原考试的补考）。
  - 但**会**重新把这些申请分配到那个已存在的考场（状态从 approved 变成 rescheduled，或者已经是 rescheduled 就不动）。
- 用不同的 `batch_key` 跑同一批：
  - 每一批的 `batch_key` 不一样，方便追溯是哪次重跑的结果。
- 如果这批申请里混了不同课程的 → 直接报错，说"所有申请必须属于同一门课程"。

**下一步该查哪里：**
- 想看生成了哪个补考 → 查 `/applications/{id}` 返回的 `assigned_makeup_exam_id`。
- 想看这次重跑改了哪些 → 查 `/audit/logs?resource_type=DeferralApplication`，按 `created_at` 倒序，看同一时间段的一批「reschedule」日志。
- 想看原考试的成绩是不是变成缺考了 → 查 `/scores?exam_id={original_exam_id}&student_id={student_id}`，确认 `score_status` 是 `absent`。

## 三、边界场景验收

### 1. 成绩锁定

**应该看到的状态：**
- 刚导入成绩：`score_status` 是「待处理 (pending)」或仍为「空 (empty)」。
- 点了锁定后：`score_status` 变成「已锁定 (locked)」，`locked_at` 记录了锁定时间，`locked_by` 记录了操作人。
- 考试本身的 `status` 也会变成「已锁定 (locked)」。

**应该留下的记录：**
- 每条被锁定的成绩，会有一条「score_lock」类型的审计日志。
- 如果之后有人解锁（只有锁定和待处理能解，已发布的不能直接解），会有一条「score_unlock」日志，上面必须写清楚解锁原因。

**验收现象：**
- 锁定后再导入同一考试的成绩 → 报错，说"考试已锁定"。
- 锁定后改单条成绩 → 看业务逻辑：这里设计的是必须先走解锁流程，直接更新会因为状态是 locked 而被跳过或报错。
- 用同一个 `batch_key` 再导入一次 → 直接报错，说"批次号已使用"（防止重复导入同一批数据）。

**下一步该查哪里：**
- 看哪些成绩被锁了 → 查 `/scores?exam_id={id}&score_status=locked`。
- 看谁锁的 → 查 `/audit/logs?resource_type=Score&resource_id={score_id}`，找「score_lock」那条日志。

---

### 2. 补录（成绩更正）

**应该看到的状态：**
- 已发布的成绩要改 → 不能直接改原记录，而是走「成绩更正 (rescore)」流程。
- 原记录的 `score_status` 会变成「已重评 (retaked)」（表示这条是历史，不算数了）。
- 会**新生成一条**成绩记录，`is_rescore: true`，`original_score_id` 指向原记录。

**应该留下的记录：**
- 会有一条「rescore」类型的审计日志，记着旧分数、新分数、操作人、更正原因。

**验收现象：**
- 查某个学生某门课的成绩 → 能看到两条：一条旧的（retaked）和一条新的（pending 或后续状态）。
- 新记录的 `created_at` 明显晚于原记录。

**下一步该查哪里：**
- 想看更正历史 → 查 `/scores?student_id={id}&exam_id={exam_id}`，按 `created_at` 排序，看 `is_rescore` 字段。
- 想看为什么更正 → 查审计日志里的「rescore」那条，看 `comment` 字段。

---

### 3. 撤回

**应该看到的状态：**
- 学生或教务撤回一条申请后：状态变成「已取消 (cancelled)」。
- 但已经"已拒绝"、"已取消"、"已完成"的申请 → 不能再撤回（会报错）。

**应该留下的记录：**
- 会有一条「cancel」类型的审计日志，记着撤回原因（如果填了）。

**验收现象：**
- 撤回一条"草稿"状态的申请 → 成功，变成 cancelled。
- 撤回一条"已拒绝"的申请 → 报错，说"当前状态无法撤回"。

**下一步该查哪里：**
- 看谁撤回的、为什么 → 查审计日志里的「cancel」那条，看 `new_value` 里的 `reason`。

## 四、教务报表验收

### 汇总报表 (`/reports/summary`)

**应该看到的数字：**
- `total_applications`：系统里所有申请的总数。
- `pending_review`：状态是 pending_review 的申请数。
- `approved`：状态是 approved 的申请数（注意：一旦分配了补考考场，状态会变成 rescheduled，所以 approved 统计的是"通过但还没排考场"的）。
- `rejected`：状态是 rejected 的申请数。
- `cancelled`：状态是 cancelled 的申请数。
- `makeup_exams_created`：`is_makeup = true` 的考试总数。
- `students_with_makeup`：状态是 rescheduled 的申请中，不同学生去重后的数量。
- `scores_locked`：`score_status = locked` 的成绩总数。
- `scores_published`：`score_status = published` 的成绩总数。

**验收现象：**
- 你手动数一遍 `status=pending_review` 的申请有几条，应该和 `pending_review` 字段相等。
- 你手动数一遍 `is_makeup=true` 的考试有几条，应该和 `makeup_exams_created` 相等。

**下一步该查哪里：**
- 数字对不上 → 先查 `/applications?status=pending_review` 这种列表接口，数数是不是真的那么多；再看审计日志，是不是有人最近改了状态但报表统计口径不同（本系统报表是实时数数据库的，理论上一致）。

### 日报报表 (`/reports/daily`)

**应该看到的数字：**
- `new_applications`：这一天 `created_at` 落在当天的申请数。
- `reviewed_applications`：这一天发生的「approve」+「reject」审计日志条数。
- `approved_today`：这一天发生的「approve」审计日志条数。
- `rejected_today`：这一天发生的「reject」审计日志条数。
- `makeup_exams_scheduled`：这一天 `created_at` 落在当天的补考考试数（`is_makeup=true`）。

**验收现象：**
- 今天审核通过 3 条、拒绝 1 条 → `reviewed_applications` 应该是 4，`approved_today=3`，`rejected_today=1`。

**下一步该查哪里：**
- 数对不上 → 查 `/audit/logs`，按时间段过滤 action=approve/reject，数数是不是一致。

## 五、跨系统边界与常见坑的验收

### 状态不会乱跳

**验收思路：** 试着做以下操作，看系统会不会拦：

1. 草稿 → 直接拒绝 → **会报错**（只能先提交成 pending_review 才能审核）。
2. 已通过 → 再提交一次 → **会报错**（不是 draft 状态）。
3. 已拒绝 → 撤回 → **会报错**（rejected 状态不能取消）。
4. 已发布的成绩 → 直接解锁 → **会报错**（要走 rescore 更正流程）。

**现象：** 以上操作都返回 400 错误，错误信息里写清楚了原因。

---

### 同一批数据重跑结果稳定

**验收思路：**

场景 A：分配补考
- 第一次跑：用 `batch_key="BATCH_001"` 分配一批申请。
- 记下生成的 `makeup_exam_id` 和每条申请的 `assigned_makeup_exam_id`。
- 第二次跑：用同样的申请列表、同样的时间地点、`batch_key="BATCH_002"` 再跑一次。

**应该看到：**
- 第二次不会新建补考考场（因为同样的原考试+日期+时间已经有一个了）。
- 但每条申请的 `batch_key` 会更新成 "BATCH_002"（方便你知道哪一条是这次重跑处理的）。
- 审计日志里会多出一批新的「reschedule」日志，时间是第二次跑的时间。

场景 B：导入成绩
- 第一次用 `batch_key="SCORE_001"` 导入。
- 第二次用同样的 `batch_key="SCORE_001"` 再导入 → **直接报错**（批次号重复，防止误重跑）。
- 第二次用 `batch_key="SCORE_002"` 导入 → 成功（但要注意：如果考试没锁定，会覆盖；如果考试已锁定，会报错）。

**下一步该查哪里：**
- 想看是哪批跑的 → 查 `batch_key` 字段（申请表和成绩表都有）。
- 想看这次重跑改了哪些 → 查同一时间段的审计日志。

## 六、普通使用者验收走查清单

按这个清单走一遍，基本就验收完了：

### 走查 1：完整的缓考流程
1. 建一个学生、一门课程、一场考试。
2. 调用资格校验 → `eligible: true`。
3. 创建申请（draft）→ 提交（pending_review）→ 审核通过（approved）。
4. 查这条申请的审计日志 → 应该有 submit 和 approve 两条。
5. 把这条申请和另一门课的申请放一起分配补考 → 报错（课程不同）。
6. 只放同一门课的申请去分配 → 成功，状态变成 rescheduled。
7. 查原考试该学生的成绩 → 应该是 absent。
8. 查补考考试 → `is_makeup: true`，`related_original_exam_id` 正确。

### 走查 2：成绩锁定
1. 导入一批成绩（batch_key 随便写一个）。
2. 查成绩状态 → pending。
3. 锁定这门考试的成绩。
4. 查成绩状态 → locked。
5. 再用同样的 batch_key 导入一次 → 报错（批次重复）。
6. 用新的 batch_key 再导入 → 报错（考试已锁定）。

### 走查 3：成绩更正
1. 假设某条成绩已发布（实际操作中可以先导入再手动把状态改成 published 来测，或者走完发布流程）。
2. 调 rescore 接口更正分数。
3. 查成绩列表 → 应该有两条：旧的 retaked，新的 rescore=true。
4. 查审计日志 → 有一条 rescore，写了原因。

### 走查 4：撤回
1. 创建一条申请，提交成 pending_review。
2. 撤回它 → 状态变成 cancelled。
3. 再撤回一次 → 报错（已取消）。

### 走查 5：汇总日报
1. 在同一天做以上操作。
2. 查 `/reports/summary` → 数字和你实际操作的数量对得上。
3. 查 `/reports/daily` → 今天的新建、审核、通过、拒绝、补考创建数量对得上。

## 七、如果某步不对，下一步该查哪里

通用排查路径：

1. **状态不对？** → 先查资源详情接口（`/applications/{id}`、`/scores/{id}`），确认 `status` 字段到底是什么。
2. **为什么会变成这个状态？** → 查 `/audit/logs?resource_type=xxx&resource_id={id}`，按时间倒序看，每一次改动都有日志，写着旧值和新值。
3. **是哪批数据跑出来的？** → 看 `batch_key` 字段（申请和成绩上都有），同一个 batch_key 的属于同一批操作。
4. **数字不对？** → 用列表接口（`/applications?status=xxx`、`/audit/logs?action=xxx`）自己数一遍，和报表比。

## 八、系统文件结构

```
zy70063/
├── requirements.txt          # 依赖清单
├── main.py                   # 应用入口
├── app/
│   ├── __init__.py
│   ├── database.py           # 数据库连接
│   ├── models.py             # 数据模型（学生、课程、考试、申请、成绩、审计日志）
│   ├── schemas.py            # 请求/响应结构定义
│   ├── services.py           # 核心业务逻辑（6 个 Service）
│   └── routers/
│       ├── __init__.py
│       ├── applications.py   # 缓考申请接口
│       ├── eligibility.py    # 资格校验接口
│       ├── reschedule.py     # 考场重排接口
│       ├── scores.py         # 成绩管理接口
│       ├── audit.py          # 审计日志接口
│       └── reports.py        # 教务报表接口
└── 验收规则.md               # 就是本文档
```

```bash
pip install -r requirements.txt
uvicorn main:app --reload
```
