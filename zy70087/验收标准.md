# 社区养老探访API服务 - 自然语言验收标准

## 一、核心业务流程验收（主链路覆盖）

### 1.1 探访计划创建与幂等性验收
**操作步骤：**
1. 使用相同的 `idempotency_key` 连续两次调用 `POST /plans/` 创建探访计划
2. 第二次调用时，系统应返回已存在的计划，且 `created` 字段为 `false`

**验收点：**
- ✅ 第一次调用返回 `created: true`，计划成功创建
- ✅ 第二次调用返回 `created: false`，计划ID与第一次相同
- ✅ 两次调用返回的计划详情完全一致
- ✅ 数据库中只存在1条该计划记录

**下一步排查：**
- 如果第二次调用也创建了新计划 → 检查 `idempotency_key` 是否正确传递，查看 `get_visit_plan_by_idempotency_key` 方法
- 如果返回的计划详情不一致 → 检查计划创建时的字段映射

### 1.2 签到定位流程验收
**操作步骤：**
1. 调用 `POST /visits/check-in` 进行签到
2. 调用 `GET /plans/{plan_id}` 检查计划状态
3. 调用 `POST /visits/{record_id}/check-out` 进行签退
4. 再次检查计划状态

**验收点：**
- ✅ 签到后计划状态变为 `in_progress`
- ✅ 签到记录包含经纬度和时间戳
- ✅ 签退后计划状态变为 `completed`
- ✅ 探访记录完整记录了签到和签退时间

**下一步排查：**
- 签到后计划状态未更新 → 检查 `check_in` 方法中的计划状态更新逻辑
- 签退后状态异常 → 检查 `check_out` 方法中的状态流转

### 1.3 异常上报与家属通知流程验收
**操作步骤：**
1. 调用 `POST /exceptions/` 上报一个异常
2. 检查计划状态（如果关联了计划）
3. 调用 `GET /exceptions/{exception_id}/notifications` 查看通知记录
4. 调用 `POST /exceptions/{exception_id}/resolve` 解决异常
5. 再次检查计划状态和异常状态

**验收点：**
- ✅ 异常上报后计划状态变为 `exception`
- ✅ 自动创建了一条家属通知记录
- ✅ 通知内容包含异常类型、级别和描述摘要
- ✅ 解决异常后，异常状态变为 `resolved`
- ✅ 关联的计划状态恢复为 `completed`（如果之前是exception状态）

**下一步排查：**
- 没有生成通知 → 检查 `create_exception` 端点中的通知创建逻辑
- 解决后计划状态未恢复 → 检查 `resolve_exception_report` 方法

## 二、异常场景验收

### 2.1 重复任务合并验收
**操作步骤：**
1. 为同一老人、同一日期、同一探访类型创建两个探访计划
2. 调用 `GET /plans/` 查看计划列表，系统应提示重复警告
3. 调用 `POST /plans/merge` 合并这两个计划
4. 查看被合并计划的状态
5. 查看主计划的合并历史

**验收点：**
- ✅ 创建第二个计划时返回 `duplicate_warning: true`
- ✅ 合并后，被合并计划的状态变为 `merged`
- ✅ `TaskMergeHistory` 表有合并记录
- ✅ 操作历史记录了合并操作

**下一步排查：**
- 没有检测到重复 → 检查 `find_duplicate_tasks` 方法的查询条件
- 合并后状态不正确 → 检查 `merge_duplicate_tasks` 方法

### 2.2 历史记录补录与撤回验收
**操作步骤：**
1. 调用 `POST /visits/backdate` 补录一条历史探访记录（`is_backdated: true`）
2. 查看探访记录，确认有 `is_backdated` 标记和原因
3. 调用 `GET /plans/{plan_id}/history` 查看操作历史
4. 调用 `POST /visits/{record_id}/withdraw` 撤回该记录
5. 再次查看探访记录和操作历史

**验收点：**
- ✅ 补录记录有明确的 `is_backdated: true` 标记
- ✅ 操作历史中记录了补录操作（operation_type: backdate）
- ✅ 撤回后，探访记录从列表中消失
- ✅ 操作历史中记录了撤回操作，包含撤回原因
- ✅ 原计划状态变为 `withdrawn`

**下一步排查：**
- 补录后没有历史记录 → 检查 `create_backdated_visit` 中的 `record_operation_history` 调用
- 撤回后计划状态未更新 → 检查 `withdraw_visit_record` 方法

### 2.3 数据一致性与幂等性验证
**操作步骤：**
1. 准备一批探访计划数据（包含10个计划）
2. 连续运行两次相同的创建脚本
3. 统计数据库中的计划总数
4. 检查每个计划的操作历史

**验收点：**
- ✅ 两次运行后，数据库中仍然只有10个计划（幂等性）
- ✅ 每个计划的 `task_idempotency_key` 唯一
- ✅ 每个计划的操作历史清晰可追溯
- ✅ 相同数据重跑结果完全一致

**下一步排查：**
- 计划数量增加 → 检查 `idempotency_key` 生成策略和去重逻辑
- 历史记录缺失 → 检查所有增删改操作是否都调用了 `record_operation_history`

## 三、报表与数据一致性验收

### 3.1 日报数据准确性验收
**操作步骤：**
1. 完成1个探访计划（签到+签退）
2. 上报1个异常并解决
3. 上报1个异常不解决
4. 调用 `GET /reports/daily` 获取今日日报
5. 对比实际数据与报表统计

**验收点：**
- ✅ `total_plans` 等于当天创建的计划数
- ✅ `completed_visits` 等于已签退的计划数
- ✅ `total_exceptions` 等于上报的异常总数（2个）
- ✅ `resolved_exceptions` 等于已解决的异常数（1个）
- ✅ `pending_exceptions` 等于未解决的异常数（1个）
- ✅ `family_notifications_sent` 等于异常上报触发的通知数（2个）

**下一步排查：**
- 统计数据不符 → 检查 `get_daily_report` 中的查询逻辑
- 异常统计错误 → 检查异常状态的枚举值和查询条件

### 3.2 导出报表业务价值验收
**操作步骤：**
1. 调用 `GET /reports/export/daily` 导出日报
2. 查看导出的JSON内容

**验收点：**
- ✅ 报表类型标注为 `daily_business_review`（非调试日志）
- ✅ 包含 `visit_completion_rate`（探访完成率）关键指标
- ✅ 包含 `review_checklist`（待跟进事项清单）：
  - `pending_visits_to_follow_up`：待完成探访数
  - `pending_exceptions_to_resolve`：待解决异常数
  - `missed_visits_to_investigate`：需调查的遗漏探访数
- ✅ 包含 `detailed_plans`：每个计划的详细状态
- ✅ 包含 `pending_exceptions_detail`：待处理异常的详细信息

**下一步排查：**
- 缺少关键指标 → 检查 `export_daily_report` 端点的返回结构
- 数据不是业务导向 → 调整导出逻辑，聚焦业务复核需求

### 3.3 老人探访汇总验收
**操作步骤：**
1. 为某位老人创建多个探访计划
2. 完成部分计划，上报部分异常
3. 调用 `GET /reports/elderly/{elderly_id}` 获取汇总
4. 核对各项统计

**验收点：**
- ✅ `total_plans` 准确统计该老人的计划数
- ✅ `completed_visits` 准确统计已完成的探访数
- ✅ `last_visit_date` 显示最近一次探访日期
- ✅ `unresolved_exceptions` 统计该老人未解决的异常数

**下一步排查：**
- 日期范围查询错误 → 检查 `get_elderly_visit_summary` 中的时间条件

## 四、追踪与排查指引

### 4.1 如何追踪一个计划的完整生命周期？
1. **查看计划详情** → `GET /plans/{plan_id}`
2. **查看操作历史** → `GET /plans/{plan_id}/history`
   - 可以看到：创建、更新、签到、签退、异常、补录、撤回、合并等所有操作
   - 每条记录包含：操作人、操作时间、操作详情、变更前后数据
3. **查看探访记录** → `GET /visits/?plan_id={plan_id}`
4. **查看异常记录** → `GET /exceptions/?elderly_id={elderly_id}`
5. **查看通知记录** → `GET /exceptions/{exception_id}/notifications`

### 4.2 数据不一致时如何排查？
1. **检查幂等性键** → 确认 `idempotency_key` 是否正确传递
2. **检查操作历史** → 查看 `OperationHistory` 表，确认所有变更都有记录
3. **检查状态流转** → 确认计划状态是否符合：pending → in_progress → completed/exception
4. **检查关联关系** → 确认探访记录、异常记录是否正确关联到计划

### 4.3 关键数据字段说明
- `task_idempotency_key`：幂等性键，用于防止重复创建计划
- `is_backdated`：标记是否为补录记录
- `operation_type`：操作类型（create/update/check_in/check_out/backdate/withdraw/merge/resolve）
- `original_data/new_data`：操作前后的数据快照，用于追溯变更
