# 企业班车站点热度调整台 - 使用说明

## 📋 项目概述

本系统专门针对企业班车运营中的核心痛点：**站点报名与实际乘车差异大，临时撤点影响员工通勤**。系统提供从数据采集、热度分析、撤点试算到公告发布的完整业务闭环。

## 🏗️ 技术架构

- **后端**: Express + SQLite3 + Node.js (端口: 3001)
- **前端**: React 18 + Ant Design 5 + Axios (端口: 3000)
- **数据**: 内置SQLite数据库，无需额外配置

## 📖 完整操作流程

### 第一步：查看热度分析（发现问题）

1. 登录系统，点击左侧菜单 **「热度分析」**
2. 查看站点热度排行榜（热度越低越需要关注）
3. 注意观察**差异率**列，红色表示超过50%
4. 点击「分析」按钮查看详细趋势

> **关键点**: 系统自动计算热度指数 = 100 - 差异率×100
> - 高热度(≥70): 运营良好
> - 中热度(40-70): 需要关注
> - 低热度(<40): 建议撤点评估

### 第二步：发起撤点申请（试算）

1. 点击 **「调整任务」** → **「发起撤点申请」**
2. 选择要调整的站点（如：霍营地铁站B口）
3. 填写任务标题和原因
4. 点击 **「试算并创建」**

> **系统自动计算**:
> - 统计该站点的报名人数
> - 统计最近30天的实际乘车人数
> - 计算差异率 = (报名-实乘)/报名
> - 计算热度指数
> - **触发拦截规则检查**

### 第三步：查看拦截结果

创建任务后，系统会展示：

**🔴 拦截信息（如果有）:**
- 报名人数 ≥ 10人 → 需要部门主管复核
- 差异率 ≥ 70% 且报名 ≥ 5人 → 需要运营确认
- 实乘为0但有报名 → 需检查刷卡设备

**📊 系统建议:**
根据热度自动生成处理建议

### 第四步：员工影响分析

1. 在调整任务列表中，点击 **「详情」**
2. 查看右侧「员工影响分析」卡片
3. 显示：
   - 预计受影响员工数
   - 部门分布（方便通知对应部门行政）
   - 备选方案建议
4. 下拉查看**受影响员工详情**（姓名、部门、电话、邮箱）

> **业务价值**: 撤点前必须了解影响范围，避免临时撤点造成员工通勤混乱

### 第五步：复核审批

任务状态说明：

| 状态 | 颜色 | 说明 |
|------|------|------|
| pending | 蓝色 | 待处理（可直接审批） |
| pending_review | 橙色 | **待复核**（触发拦截规则） |
| approved | 绿色 | 已通过 |
| rejected | 红色 | 已拒绝 |
| escalated | 紫色 | 已上报上级 |

**复核操作：**
- **通过审批**: 执行站点调整（站点状态变为withdrawn）
- **上报上级**: 标记需要更高层级审批
- **拒绝申请**: 终止任务

### 第六步：发布调整公告

1. 点击 **「调整公告」** → **「新建公告」**
2. 填写：
   - 标题（如：关于霍营地铁站B口班车调整的通知）
   - 类型（线路调整/站点撤销/运营通知）
   - 生效日期
   - 影响线路和站点
   - 公告内容（系统提供模板）
3. 点击 **「预览」** 确认格式
4. 点击 **「发布」**

## 🔒 拦截规则详解

系统内置3级拦截机制，确保撤点决策慎重：

### 一级拦截（强制复核）
```
条件: 报名人数 ≥ 10人
结果: 自动进入「待复核」状态
理由: 影响人数较多，需部门主管确认
```

### 二级拦截（运营确认）
```
条件: 差异率 ≥ 70% 且 报名人数 ≥ 5人
结果: 进入「待复核」状态
理由: 数据差异异常，需核实数据准确性
```

### 三级拦截（技术检查）
```
条件: 实际乘车 = 0 但 报名人数 ≥ 3
结果: 进入「待复核」状态
理由: 可能是刷卡设备故障，而非站点无人使用
```

### 无拦截（直接通过）
```
条件: 不满足以上任何拦截条件
结果: 状态为「待处理」，可直接审批
```

## 📈 核心业务逻辑

### 热度计算公式

```javascript
差异率 = (报名人数 - 实际乘车人数) / 报名人数
热度指数 = 100 - 差异率 × 100

热度等级:
  - 高热度: 指数 ≥ 70（运营良好）
  - 中热度: 40 ≤ 指数 < 70（需要关注）
  - 低热度: 指数 < 40（建议撤点评估）
```

### 实际乘车统计逻辑

- 统计最近30天（自动排除周末）
- 按员工ID去重（同一人多次刷卡只算1次）
- 与报名记录对比

## ❓ 常见问题

**Q: 数据初始化后如何重置？**
A: 删除 `backend/data/shuttle.db` 文件，重新运行 `npm run seed`

**Q: 如何修改拦截规则阈值？**
A: 编辑 `backend/src/services/heatCalculation.js` 中的 `checkInterceptionRules` 函数

**Q: 实际乘车数据如何接入真实刷卡系统？**
A: 可调用 `/api/swipe` POST接口批量导入真实刷卡数据

**Q: 系统支持多线路吗？**
A: 支持，在「站点管理」中可配置站点所属线路，热度分析支持按线路筛选

## 🎓 业务价值总结

本系统解决的核心问题：

1. **报名实乘差异量化**: 用数据说话，避免主观判断
2. **拦截机制防误操作**: 10人以上撤点必须复核
3. **员工影响可视化**: 撤点前明确知道影响谁、影响多少
4. **全流程可追溯**: 从发现问题 → 试算 → 复核 → 公告，完整闭环

真正实现：**数据驱动决策，流程保障合规**
