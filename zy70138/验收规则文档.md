
# AB实验分桶回溯API - 验收规则文档

## 一、业务背景

在AB实验过程中，当实验规则（分桶策略、分组配置、流量比例等）发生变更时，常常出现以下问题：

1. **历史用户分桶解释不清**：同一用户在不同版本中被分配到不同分组，无法解释具体原因
2. **指标归因混乱**：用户行为指标无法准确归因到正确的实验版本和分组
3. **数据前后矛盾**：规则变更前后的数据对比缺乏版本标记，导致结论不可信

本项目通过**分桶哈希 + 版本冻结**机制解决这些问题。

---

## 二、核心概念说明

### 2.1 实验配置（入口）
实验配置是所有操作的起点，包含：
- **实验ID**：全局唯一标识
- **版本管理**：支持多版本并存，新版本不覆盖历史版本
- **版本冻结**：一旦版本冻结，分桶规则不可修改

### 2.2 分桶哈希（主推进规则1）
采用 **SHA256 + 取模** 的确定性分桶策略：
- 输入：`experiment_id + user_id`
- 输出：`bucket_number (0-99)`
- 特点：同一输入永远得到相同输出

### 2.3 版本冻结（主推进规则2）
版本一旦冻结：
- 分桶策略、分组配置、流量比例均不可修改
- 用户分配记录被固化，后续查询始终返回历史值
- 指标数据将被归因到冻结时的版本

### 2.4 指标归因与回溯（兜底/复查）
当规则变更后，历史指标可通过：
- **显式分配记录**：优先使用已存储的分配记录
- **时间范围匹配**：根据指标事件时间匹配当时生效的版本
- **哈希回填**：使用版本冻结时的规则重新计算分桶

## 三、API 功能清单

### 3.1 实验配置管理

| API | 功能 | 关键状态 |
|-----|------|----------|
| `POST /api/v1/experiments` | 创建实验 | draft → running |
| `GET /api/v1/experiments` | 查询实验列表 | 按更新时间排序 |
| `GET /api/v1/experiments/{id}` | 查询实验详情 | 包含所有版本 |
| `POST /api/v1/experiments/{id}/versions` | 创建新版本 | 自动检测与上一版本的冲突 |

### 3.2 版本冻结管理

| API | 功能 | 关键规则 |
|-----|------|----------|
| `POST /api/v1/versions/{n}/freeze` | 冻结版本 | 需通过冻结校验：<br>1. 流量分配总和100%<br>2. 存在对照组<br>3. 设置生效时间 |
| `POST /api/v1/versions/{n}/unfreeze` | 撤销冻结 | 限制条件：<br>1. 冻结后24小时内<br>2. 已分配用户 < 100<br>3. 会清除该版本所有分配记录 |

### 3.3 分桶与查询

| API | 功能 | 记录内容 |
|-----|------|----------|
| `POST /api/v1/experiments/{id}/assign` | 单用户分桶 | 写入 `UserAssignment` 表，记录：<br>user_id, treatment, bucket, assigned_at, source |
| `POST /api/v1/experiments/{id}/assign/batch` | 批量分桶 | 区分「新分配」与「已存在」 |
| `POST /api/v1/experiments/{id}/backfill` | 回溯分桶 | 不写库，仅返回计算结果，用于历史数据复查 |

### 3.4 指标归因

| API | 功能 | 归因优先级 |
|-----|------|------------|
| `POST /api/v1/experiments/{id}/metrics` | 记录指标 | 1. 显式分配记录<br>2. 生效时间范围匹配<br>3. 哈希回填 |
| `GET /api/v1/metrics/{name}/aggregate` | 指标聚合 | 按版本+分组统计 |

### 3.5 冲突与差异

| API | 功能 | 检测内容 |
|-----|------|----------|
| `GET /api/v1/diff/{v1}/{v2}` | 版本差异 | 1. 分桶策略变更<br>2. 分组范围变更<br>3. 用户分组迁移 |
| `GET /api/v1/experiments/{id}/conflicts` | 冲突列表 | 记录所有检测到的冲突 |
| `POST /api/v1/conflicts/{id}/resolve` | 解决冲突 | 记录解决决策 |

### 3.6 数据导出

| 导出类型 | 内容 | 用途 |
|----------|------|------|
| `assignments` | 用户分配明细 | 业务复核谁分到了哪个组 |
| `metrics` | 指标归因明细 | 业务复核指标如何被归因 |
| `versions` | 版本配置历史 | 业务复核规则是如何变更的 |

## 四、验收规则：用户应看到的内容

### 4.1 实验与版本状态

**创建实验后**，用户应看到：
- 实验状态：`draft`（草稿）
- 版本数：0
- 最新更新时间

**创建版本后**，用户应看到：
- 版本号：从1开始递增
- 配置内容：分组名称、分桶范围、流量占比、对照组标记
- 冲突提示（如有）：与上一版本的差异项，按严重程度分级
- 操作日志：记录创建操作的时间、操作者

**冻结版本后**，用户应看到：
- 版本状态：`frozen`（已冻结）
- 冻结时间、冻结人
- 已存在的用户分配数量
- 实验状态自动变为：`running`（运行中）
- 操作日志：记录冻结操作及结果

**撤销冻结后**，用户应看到：
- 版本状态：恢复为未冻结
- 清除的分配记录数量
- 冲突记录：标记为「撤销冻结」，记录原因
- 操作日志：记录撤销操作及原因

### 4.2 用户分桶记录

**单用户分桶时**，用户应看到：
- 分配的分组名称
- 分桶号（0-99）
- 对应的版本号
- 分配时间
- 是否为「新分配」

**批量分桶时**，用户应看到：
- 总用户数
- 新分配数量
- 每个用户的结果（成功/失败/已存在）

**用户历史查询时**，用户应看到：
- 该用户在每个版本中的分组
- 分配来源（实时/批量/回溯）
- 分配时间
- 按版本号排序的历史轨迹

### 4.3 指标归因记录

**记录指标时**，用户应看到：
- 归因到的版本号
- 归因到的分组名称
- 归因方法：
  - `explicit_assignment`（使用存储的分配记录）
  - `backfill_hash`（使用冻结规则回填）
- 事件时间与归因时间

**指标聚合时**，用户应看到：
- 每个分组的统计：计数、总和、均值、最小、最大
- 按版本号区分（可指定版本）
- 支持按时间范围过滤

### 4.4 冲突与差异报告

**版本差异时**，用户应看到：
- 配置变更项：
  - 分桶策略变更（高风险）
  - 分桶数量变更（高风险）
  - 分组范围变更（高风险）
  - 对照组标记变更（极高风险）
  - 新增/删除分组（中风险）
- 用户迁移情况：
  - 两版本的总用户数
  - 共同用户数
  - 分组变更的用户数
  - 前50个变更用户的样例

**冲突列表时**，用户应看到：
- 冲突类型：`version_upgrade` / `unfreeze_rollback`
- 检测时间、解决时间
- 受影响用户数、受影响指标数
- 状态：`open` / `resolved`

### 4.5 操作日志与重试

**操作日志列表**，用户应看到：
- 操作类型：`create_experiment`, `freeze_version`, `unfreeze_version` 等
- 状态：`pending`, `success`, `failed`
- 重试次数
- 下次重试时间（如有）
- 操作者、时间

**重试失败操作时**，用户应看到：
- 当前重试次数
- 最大重试次数限制（默认3次）
- 下次重试的时间间隔（指数退避：1s, 2s, 4s）

## 五、异常场景验收

### 5.1 冲突场景

| 场景 | 预期行为 | 用户应看到 |
|------|----------|------------|
| 新建版本改变分桶策略 | 自动记录冲突 | 冲突提示：严重程度=高，描述=所有用户将重新分桶 |
| 新建版本改变对照组标记 | 自动记录冲突 | 冲突提示：严重程度=极高，描述=分组X的对照组标记变更 |
| 新建版本删除已有分组 | 自动记录冲突 | 冲突提示：严重程度=高，描述=删除现有分组X |
| 新建版本改变分桶范围 | 自动记录冲突 | 冲突提示：旧范围→新范围，受影响用户数 |

### 5.2 撤销场景

| 场景 | 预期行为 | 用户应看到 |
|------|----------|------------|
| 冻结后立即撤销 | 允许撤销 | 清除该版本的所有分配记录，记录原因 |
| 冻结超过24小时后撤销 | 拒绝撤销 | 错误提示：冻结超过24小时且已分配N个用户 |
| 已分配>100用户后撤销 | 拒绝撤销 | 错误提示：同上 |
| 撤销后重新冻结 | 允许 | 重新开始冻结流程，之前的分配记录已清除 |

### 5.3 超时重试场景

| 场景 | 预期行为 | 用户应看到 |
|------|----------|------------|
| 操作首次失败 | 标记为 failed，可重试 | 日志显示 retry_count=0，可点击重试 |
| 第1次重试 | 间隔1秒后执行 | 日志显示 retry_count=1，next_retry_at |
| 第2次重试 | 间隔2秒后执行 | 日志显示 retry_count=2 |
| 第3次重试 | 间隔4秒后执行 | 日志显示 retry_count=3 |
| 超过最大重试次数 | 不再允许重试 | 错误提示：已达到最大重试次数(3) |

### 5.4 归因失败场景

| 场景 | 预期行为 | 用户应看到 |
|------|----------|------------|
| 指标时间早于所有版本生效时间 | 无法归因 | 错误：无法找到匹配的版本，建议检查生效时间 |
| 指标时间在两版本之间的空档期 | 无法归因 | 同上 |
| 版本未冻结 | 不参与归因 | 只使用已冻结的版本进行匹配 |
| 用户未落入任何分组 | 返回错误 | 提示用户的分桶号，说明该号未被任何分组覆盖 |

## 七、数据一致性保证

### 7.1 版本冻结保证
- 已冻结版本的分桶策略、分组配置不可修改
- 用户分配记录与版本关联，版本不变则分配不变
- 新建版本不影响历史版本的数据

### 7.2 哈希确定性保证
- `SHA256(experiment_id + ":" + user_id) % 100`
- 同一输入永远返回相同输出
- 便于离线验证和回溯计算

### 7.3 归因可追溯性
- 每条指标记录都标记了归因使用的版本号
- 可追溯到使用的是显式分配还是哈希回填
- 操作日志完整记录所有变更操作

## 八、快速验证流程

### 8.1 正常流程验证

**步骤1：创建实验和版本**
```
POST /api/v1/experiments
{
  "id": "button_color_test",
  "name": "按钮颜色实验",
  "created_by": "product_manager"
}
```

**步骤2：创建版本并配置分组**
```
POST /api/v1/experiments/button_color_test/versions
{
  "treatments": [
    {"name": "control", "bucket_start": 0, "bucket_end": 49, "traffic_percent": 50, "is_control": true},
    {"name": "blue_button", "bucket_start": 50, "bucket_end": 99, "traffic_percent": 50}
  ],
  "effective_start": "2024-01-01T00:00:00Z",
  "created_by": "product_manager"
}
```

**步骤3：冻结版本**
```
POST /api/v1/experiments/button_color_test/versions/1/freeze
{
  "operator": "product_manager"
}
```

**步骤4：用户分桶**
```
POST /api/v1/experiments/button_color_test/assign
{
  "user_id": "user_001",
  "operator": "system"
}
```
验证：返回 treatment_name、bucket_number、version_number

**步骤5：记录指标**
```
POST /api/v1/experiments/button_color_test/metrics
{
  "user_id": "user_001",
  "metric_name": "click",
  "metric_value": 1,
  "event_time": "2024-01-15T10:00:00Z"
}
```
验证：返回 attribution_method = "explicit_assignment"

**步骤6：指标聚合**
```
GET /api/v1/experiments/button_color_test/metrics/click/aggregate
```
验证：按 control 和 blue_button 分组统计

### 8.2 冲突场景验证

**步骤1：创建新版本（故意修改对照组）**
```
POST /api/v1/experiments/button_color_test/versions
{
  "treatments": [
    {"name": "control", "bucket_start": 0, "bucket_end": 33, "traffic_percent": 34},
    {"name": "blue_button", "bucket_start": 34, "bucket_end": 66, "traffic_percent": 33, "is_control": true},
    {"name": "green_button", "bucket_start": 67, "bucket_end": 99, "traffic_percent": 33}
  ],
  "created_by": "product_manager"
}
```
验证：自动记录 VersionConflict，包含：
- control_changed 类型冲突
- treatment_added（新增 green_button）
- bucket_range_changed（所有分组范围改变）

**步骤2：查看冲突列表**
```
GET /api/v1/experiments/button_color_test/conflicts
```
验证：返回冲突记录，status = "open"

### 8.3 撤销场景验证

**步骤1：冻结新版本后立即撤销**
```
POST /api/v1/experiments/button_color_test/versions/2/freeze
POST /api/v1/experiments/button_color_test/versions/2/unfreeze
{
  "operator": "product_manager",
  "reason": "规则配置错误，需要重新调整"
}
```
验证：
- 版本恢复未冻结状态
- 分配记录被清除
- 记录 unfreeze_rollback 类型的冲突

**步骤2：超过24小时后尝试撤销**
（模拟24小时后，或修改系统时间）
验证：返回 400 错误，说明无法撤销的原因

### 8.4 回溯验证

**步骤1：使用旧版本的规则回溯**
```
POST /api/v1/experiments/button_color_test/backfill
{
  "user_id": "user_001",
  "event_time": "2024-01-10T10:00:00Z"
}
```
验证：返回 version 1 的分组（因为事件时间在版本2之前）

**步骤2：查询用户历史**
```
GET /api/v1/experiments/button_color_test/users/user_001/history
```
验证：显示用户在各版本中的分组情况

## 九、关键规则清单（不可省略）

以下是必须保证的核心规则，任何情况下都不能简化或省略：

1. ✅ **版本号递增**：新版本号 = 最大版本号 + 1
2. ✅ **版本冻结不可修改**：is_frozen=True 时，配置不可变更
3. ✅ **SHA256 分桶**：必须使用 SHA256 + 取模，不能使用随机
4. ✅ **用户分配唯一**：同一版本同一用户只能有一条分配记录
5. ✅ **冻结校验**：流量100%、有对照组、有生效时间
6. ✅ **撤销限制**：24小时内 + <100用户
7. ✅ **归因优先级**：显式记录 > 时间匹配 > 哈希回填
8. ✅ **操作日志**：所有关键操作必须记录
9. ✅ **冲突检测**：创建新版本时自动检测并记录
10. ✅ **指数退避重试**：1s → 2s → 4s，最多3次

## 十、注意事项

### 10.1 关于「只跑通顺利路径」
本项目不仅实现了正常流程（创建→配置→冻结→分桶→归因），还完整实现了：
- 冲突检测与记录
- 冻结撤销（带限制条件）
- 失败操作重试（指数退避）
- 历史数据回溯
- 多版本指标归因

### 10.2 关于「关键规则不偷懒」
所有核心规则都在代码中有明确实现：
- 分桶哈希：`services.py` 中的 `BucketingService.compute_bucket()`
- 版本冻结校验：`services.py` 中的 `VersionFreezeService.validate_freeze_ready()`
- 冲突检测：`services.py` 中的 `ConflictDetectionService.check_version_conflict()`
- 归因逻辑：`services.py` 中的 `AttributionService.attribute_metric()`
- 重试策略：`services.py` 中的 `RetryPolicy`

### 10.3 关于「导出文件」
导出的CSV文件不是调试日志，而是：
- 完整的业务字段
- 可直接用于数据分析
- 包含版本信息，便于追溯
- 按实验维度组织，便于归档
