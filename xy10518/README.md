# 质检抽样复判 CLI

生产质检抽样复判/让步放行历史追踪工具。解决工厂质检员抽检后需要复判或让步放行时，月底追责只剩几张截图的问题。

## 功能特性

- 📋 **完整历史追踪**: 保留初检、复检、让步放行和批次处置的完整历史
- 🔍 **状态可视化**: 每一步都能看到状态变化、历史记录和失败原因
- 📝 **人工修正审计**: 人工修正必须留下前后差异和操作者记录
- ⚡ **幂等操作**: 重复执行或重复回调保持幂等
- 🧪 **内置样例**: 覆盖一次通过、复检通过、让步放行和整批返工四种场景
- 📊 **报表汇总**: 展示每个决定的依据、审批人、批次状态和质量风险

## 核心规则

1. **重复抽样单**: 同一抽样单号重复导入时幂等处理，返回已存在提示
2. **严重缺陷直接让步**: 检测到 CRITICAL 级别缺陷时，自动进入让步放行审批流程
3. **复检样本数不足**: 复检样本数必须至少等于初检样本数，建议为初检的2倍
4. **审批后修改**: 已有让步放行审批记录时，修改会给出警告并记录差异
5. **幂等处理**: 所有状态变更操作都支持重复调用，不会产生副作用

## 本地启动

### 环境要求

- Node.js >= 14
- npm 或 yarn

### 安装依赖

```bash
npm install
```

### 运行方式

**方式一: 使用 ts-node 直接运行（开发模式）**

```bash
npm run dev -- <command> [options]
```

**方式二: 编译后运行**

```bash
npm run build
node dist/cli.js <command> [options]
```

> 以下所有示例均使用 `npm run dev --` 方式，编译后可替换为 `node dist/cli.js`

## 主要演示路径

### 路径一: 一次通过

1. 创建批次
```bash
npm run dev -- create TEST001 -p TEST -n "测试产品" -q 100 -d 2026-05-12 -l "A线-1号"
```

2. 记录初检（无缺陷）
```bash
npm run dev -- inspect TEST001 -s TEST001-S001 -c 50 --defects NONE -i "质检员A"
```

3. 查看状态变化
```bash
npm run dev -- detail TEST001
```

观察: 状态从 `CREATED` → `PASSED`

### 路径二: 复检通过

1. 创建批次
```bash
npm run dev -- create TEST002 -p TEST -n "测试产品B" -q 500 -d 2026-05-12 -l "A线-2号"
```

2. 记录初检（有缺陷，触发复检）
```bash
npm run dev -- inspect TEST002 -s TEST002-S001 -c 30 --defects "MINOR:2,轻微划痕" -i "质检员A"
```

观察: 状态变为 `PENDING_REINSPECTION`（待复检）

3. 记录复检
```bash
npm run dev -- reinspect TEST002 -s TEST002-S002 -c 60 --defects NONE -i "质检员B"
```

观察: 状态变为 `PASSED`

4. 查看完整历史
```bash
npm run dev -- detail TEST002
```

### 路径三: 让步放行

1. 创建批次
```bash
npm run dev -- create TEST003 -p TEST -n "测试产品C" -q 200 -d 2026-05-12 -l "B线-1号"
```

2. 记录初检（严重缺陷，直接进入让步放行）
```bash
npm run dev -- inspect TEST003 -s TEST003-S001 -c 20 --defects "CRITICAL:1,焊点虚焊; MINOR:2,丝印偏移" -i "质检员A"
```

观察: 状态变为 `PENDING_CONCESSION`（待让步放行）

3. 申请让步放行
```bash
npm run dev -- concession TEST003 --reason "客户紧急订单" --justification "经评估不影响核心功能" --risk MEDIUM --requester "李主管"
```

4. 批准让步放行
```bash
npm run dev -- approve TEST003 --approver "赵质量经理" --notes "同意放行，后续需整改"
```

观察: 状态变为 `CONCESSION_APPROVED`

5. 关闭批次
```bash
npm run dev -- close TEST003 --by "赵质量经理"
```

### 路径四: 整批返工

1. 创建批次
```bash
npm run dev -- create TEST004 -p TEST -n "测试产品D" -q 3000 -d 2026-05-12 -l "C线-1号"
```

2. 记录初检
```bash
npm run dev -- inspect TEST004 -s TEST004-S001 -c 100 --defects "MAJOR:5,尺寸超差" -i "质检员B"
```

3. 记录复检（仍不合格）
```bash
npm run dev -- reinspect TEST004 -s TEST004-S002 -c 200 --defects "MAJOR:8,尺寸超差; MINOR:3,表面毛刺" -i "质检员A"
```

4. 批准返工
```bash
npm run dev -- approve TEST004 --type rework --approver "赵质量经理" --reason "批量性尺寸超差，需返工"
```

观察: 状态变为 `REWORK`

## 失败路径演示

### 场景: 复检样本数不足

1. 创建批次
```bash
npm run dev -- create FAIL001 -p TEST -n "失败测试" -q 1000 -d 2026-05-12 -l "A线-1号"
```

2. 记录初检（触发复检）
```bash
npm run dev -- inspect FAIL001 -s FAIL001-S001 -c 50 --defects "MAJOR:1" -i "质检员A"
```

3. 尝试用不足的样本数复检（应该失败）
```bash
npm run dev -- reinspect FAIL001 -s FAIL001-S002 -c 10 --defects NONE -i "质检员B"
```

**预期输出:**
```
  ✖ 操作失败
  复检样本数校验失败

  错误详情:
    - 复检样本数不足: 需至少 50 件, 实际 10 件
```

### 场景: 状态机校验失败 - 重复初检

1. 接上面的 FAIL001，尝试再次记录初检
```bash
npm run dev -- inspect FAIL001 -s FAIL001-S003 -c 50 --defects NONE -i "质检员A"
```

**预期输出:**
```
  ✖ 操作失败
  批次状态 PENDING_REINSPECTION 不允许执行初检

  错误详情:
    - 状态校验失败: 当前状态 PENDING_REINSPECTION, 允许执行初检的状态: CREATED
```

### 场景: 审批后再次修改（警告提示）

1. 使用已有的让步放行批次 B202605120003
2. 进行人工修正
```bash
npm run dev -- correct B202605120003 --by "系统管理员" --field "quantity" --old 200 --new 250 --reason "实际入库数量修正"
```

**预期输出:**
```
  ✓ 操作成功
  人工修正已记录

  警告信息:
    - 该批次已有让步放行审批记录, 修改需要由质量经理审批并记录修改差异
```

查看历史记录:
```bash
npm run dev -- detail B202605120003
```

在历史轨迹中可以看到:
```
  #5 人工修正
    操作者: 系统管理员
    状态变更: [已关闭] → [已关闭]
    原因: 实际入库数量修正
    变更差异:
      - quantity: 200 → 250
```

## 完整命令参考

| 命令 | 描述 |
|------|------|
| `init` | 初始化数据仓库 (--force 强制重置) |
| `seed` | 导入内置样例数据 |
| `create <batch>` | 创建新批次 |
| `inspect <batch>` | 记录初检结果 |
| `reinspect <batch>` | 记录复检结果 |
| `concession <batch>` | 申请让步放行 |
| `approve <batch>` | 审批让步放行或返工 |
| `close <batch>` | 关闭批次 |
| `check` | 查看所有批次列表 |
| `detail <batch>` | 查看批次详情 |
| `report` | 生成质量汇总报告 |
| `correct <batch>` | 人工修正（记录差异） |

## 缺陷等级说明

| 等级 | 权重 | 描述 | 处理方式 |
|------|------|------|----------|
| CRITICAL | 100 | 严重缺陷 | 直接进入让步放行审批 |
| MAJOR | 10 | 主要缺陷 | 可复检或让步放行 |
| MINOR | 1 | 次要缺陷 | 一般不影响结果 |
| NONE | 0 | 无缺陷 | 直接通过 |

## 状态流转图

```
CREATED → INITIAL_INSPECTION
    ↓
    ├─ PASS → PASSED → CLOSED
    ├─ FAIL (无严重缺陷) → PENDING_REINSPECTION → REINSPECTION
    │                          ↓
    │                          ├─ PASS → PASSED → CLOSED
    │                          └─ FAIL → PENDING_CONCESSION 或 REWORK
    └─ FAIL (有严重缺陷) → PENDING_CONCESSION
                              ↓
                              ├─ APPROVE → CONCESSION_APPROVED → CLOSED
                              ├─ REJECT → REJECTED → CLOSED
                              └─ REWORK → REWORK → CLOSED (或重新复检)
```

## 数据存储

数据保存在当前目录的 `data/qc-data.json` 文件中，格式为 JSON，包含:

- **batches**: 所有批次信息，包括检验记录、让步放行记录、历史轨迹
- **samplingSheets**: 所有抽样单记录（用于幂等校验）

可直接打开该文件查看原始数据结构。

## 业务闭环验证

通过 `detail` 命令查看任意批次时，应能回答以下问题:

1. **谁做了什么?** → 历史轨迹中的操作者和操作类型
2. **什么时候做的?** → 每条记录都有时间戳
3. **为什么这么决定?** → 操作原因、审批意见
4. **依据是什么?** → 检验数据、缺陷详情
5. **最终结果是什么?** → 批次最终状态
6. **有谁审批?** → 让步放行/返工的审批人

即使不看源码，也能通过 CLI 输出清晰判断业务是否真的闭环。
