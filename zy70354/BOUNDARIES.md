# 分库分表路由 API - 边界说明

## 一、主要边界（Main Boundaries）

### 1. 配置边界
- **租户配置必须存在**：所有路由操作都需要有效的租户配置（tenantId 必须在 tenantConfigs 中存在）
- **分片配置必须可解析**：根据分片规则计算出的分片 ID 必须能在 shardConfigs 中找到对应的配置
- **月度映射必须完整**：对于使用月度分片规则的租户，每个月份必须在 monthlyShardMappings 中有对应的映射

### 2. 路由键边界
- **必填字段**：tenantId 是必须的路由键，缺失将导致路由失败
- **时间戳字段**：对于使用 ShardRuleType.MONTHLY 规则的租户，createdAt（时间戳）是必须的
- **订单ID字段**：虽然不是强制字段，但缺少 orderId 会影响查询效率和精确路由

### 3. 迁移状态边界
- **迁移中状态**：当 MigrationStatus 为 IN_PROGRESS 时，会根据策略触发双写（DUAL_WRITE）和双读（DUAL_READ）
- **双写策略**：必须同时配置 currentShardId 和 oldShardId 才能执行双写
- **策略优先级**：迁移中策略（DUAL_WRITE/DUAL_READ）优先级高于常规分片规则

### 4. 查询范围边界
- **最大跨月范围**：默认配置为 3 个月（maxCrossMonthRange: 3），超过 36 个月会直接拒绝
- **日期格式**：必须是有效的 ISO 8601 格式，fromDate 必须早于 toDate
- **时间范围校验**：跨月查询时会检查月份数是否超过限制

### 5. 补偿机制边界
- **最大重试次数**：单个补偿请求最多重试 3 次，超过后标记为永久失败
- **幂等性**：写入操作默认是非幂等的，重复写入需要先检查 pendingCompensations
- **补偿顺序**：补偿请求按创建时间顺序处理，遵循先进先出（FIFO）原则

### 6. 冲突解决边界
- **双读冲突**：当旧分片和新分片数据不一致时，默认进入 pending 状态，不自动选择任一边
- **迁移完成后**：迁移结束日期之后，冲突默认使用新分片数据（use_new）
- **冲突字段**：只有实际值不同的字段才会被标记为冲突，null/undefined 比较时会被忽略

## 二、一个失败路径（One Failure Path）

### 场景：租户 10001（迁移中）的订单写入失败

#### 失败路径步骤
```
1. 调用 POST /api/route/write
   ├─ 输入：{ tenantId: "10001", orderId: "ORD-FAIL-001", createdAt: "2025-04-15T10:00:00Z" }
   └─ 路由引擎计算：DUAL_WRITE 策略，写入两个分片

2. 实际写入执行（外部数据库操作）
   ├─ 写入新分片（tenant_10001_new）：✓ 成功
   └─ 写入旧分片（tenant_10001_old）：✗ 失败（数据库连接超时）

3. 错误处理
   ├─ 捕获数据库异常
   ├─ 调用 compensationService.createCompensationRequest()
   └─ 返回给调用方：{ success: true, requiresCompensation: true }

4. 后续影响
   ├─ 订单数据在新分片存在，旧分片缺失
   ├─ 下次查询（DUAL_READ）可能触发数据冲突
   ├─ 需要人工或定时任务处理补偿队列

5. 补偿执行（假设第 3 次重试仍然失败）
   ├─ 调用 POST /api/compensation/process
   ├─ 第 1 次重试：✗ 失败
   ├─ 第 2 次重试：✗ 失败
   └─ 第 3 次重试：✗ 失败 → 标记为永久失败

6. 最终状态
   ├─ 补偿请求从 pending 队列移除
   ├─ 审计日志记录 COMPENSATION_FAILED_PERMANENTLY
   └─ 需要人工介入检查数据库连接和数据一致性
```

#### 关键错误点
- **错误位置**：`routingEngine.ts` 中的 `routeWrite()` 方法返回路由结果后，实际数据库写入发生在调用方，补偿机制依赖调用方正确调用
- **依赖外部系统**：补偿服务的重试机制假设数据库问题是临时的，如果是永久性问题（如旧分片已下线），需要人工干预
- **数据一致性风险**：双写失败导致新旧分片数据不一致，双读时会返回冲突，需要人工判断正确版本

## 三、一次重复执行路径（One Re-execution Path）

### 场景：订单 ORD-RETRY-001 的写入操作由于网络超时被重复调用

#### 重复执行路径步骤
```
第一次调用（T0）
├─ 客户端调用 POST /api/route/write
│  └─ { tenantId: "10001", orderId: "ORD-RETRY-001", createdAt: "2025-04-16T14:00:00Z" }
├─ 路由引擎计算：DUAL_WRITE 策略
├─ 返回路由结果：{ writeTargets: [新分片, 旧分片], requiresCompensation: true }
└─ 客户端开始执行实际写入...
   ├─ 写入新分片：✓ 成功
   └─ 写入旧分片：网络超时（客户端不确定是否成功）
      └─ 客户端未收到确认 → 决定重试

第二次调用（T+5s，客户端重试）
├─ 客户端再次调用 POST /api/route/write
│  └─ 相同的参数 { tenantId: "10001", orderId: "ORD-RETRY-001", ... }
├─ 路由引擎计算
│  ├─ 先调用 compensationService.handleDuplicateWrite()
│  │  ├─ 检查 pendingCompensations
│  │  └─ 发现：尚无待处理补偿（第一次调用的客户端未创建补偿）
│  └─ 返回：{ shouldProceed: true, recommendation: "无冲突，可以执行写入" }
├─ 路由引擎再次返回 DUAL_WRITE 策略
└─ 客户端再次执行实际写入...
   ├─ 写入新分片：可能导致重复数据（如果数据库没有唯一约束）
   └─ 写入旧分片：这次成功 ✓

数据状态检查
├─ 新分片：可能存在 2 条相同订单数据（取决于数据库约束）
├─ 旧分片：1 条数据（第二次成功）
└─ 查询时：
   ├─ 新分片查询：可能返回多条
   ├─ 双读比较：可能触发冲突（即使字段相同，记录数不同也算冲突）
   └─ 冲突解决：进入 pending 状态，需要人工检查

问题根源
└─ 路由引擎层面没有实现幂等写入检查
   ├─ 仅检查 pendingCompensations（由调用方显式创建）
   └─ 不会查询数据库确认订单是否已存在

建议修复
├─ 方案 1：在写入前先查询数据库确认是否已存在
│  └─ 增加查询开销，但确保幂等性
├─ 方案 2：在数据库层面添加唯一约束
│  └─ (tenantId, orderId) 联合唯一索引
└─ 方案 3：使用分布式锁（如 Redis）
   └─ 对 (tenantId, orderId) 加锁防止并发重复写入
```

#### 关键重复点
- **重复触发点**：客户端由于网络超时等原因重试相同的请求
- **路由引擎限制**：当前实现仅检查 pendingCompensations 队列，不查询数据库确认数据是否已存在
- **依赖调用方**：幂等性保障依赖调用方的实现（如使用唯一索引）和正确创建补偿请求
- **数据风险**：如果数据库没有唯一约束，可能导致数据重复，影响后续查询和统计

## 四、关键设计决策

### 1. 路由引擎不执行实际数据库操作
- **原因**：保持路由引擎的纯粹性，专注于路由计算逻辑
- **影响**：调用方需要负责实际的数据库读写、事务管理和异常处理
- **补偿机制**：调用方在失败时需要显式调用 compensation API 创建补偿请求

### 2. 双读冲突默认进入 pending 状态
- **原因**：无法自动判断哪个版本是正确的，避免数据丢失
- **影响**：需要人工或额外的业务规则来解决冲突
- **例外**：迁移完成后默认使用新分片数据

### 3. 补偿重试有上限
- **原因**：避免无限重试导致资源耗尽
- **影响**：超过 3 次重试后需要人工介入
- **审计**：所有重试过程都有审计记录，方便问题追踪

### 4. 查询范围有软限制和硬限制
- **软限制**：3 个月，超过给出警告但继续执行
- **硬限制**：36 个月，超过直接拒绝
- **原因**：平衡灵活性和性能，避免大范围查询拖垮系统

## 五、调试建议

### 查看详细路由决策
```bash
# 使用 explain 端点获取完整的路由分析
curl -X POST http://localhost:3000/api/route/explain \
  -H "Content-Type: application/json" \
  -d '{
    "tenantId": "10001",
    "orderId": "ORD-DEBUG-001",
    "createdAt": "2025-04-01T10:00:00Z",
    "operation": "write"
  }'
```

### 检查审计日志
```bash
# 查看最近的路由和补偿操作
curl http://localhost:3000/api/audit/recent?limit=50
```

### 检查待处理补偿
```bash
# 查看某个租户的所有待处理补偿
curl http://localhost:3000/api/compensation/pending/10001
```
